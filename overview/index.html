    🧭 Furive OS 한눈에 보기¶

    각 팀은 프로그램을 개발하고, Furive OS는 지원 차량에서 그 프로그램의 설치·실행·업데이트를 맡습니다. 이 문서는 그 관계가 궁금할 때 읽는 자료입니다. 바로 코드를 고치려면 개발 시작, 차량에 설치하려면 차량 PC 설치를 봅니다.

    처음 알아둘 세 가지¶

    이름 뜻 예
    패키지 독립 프로그램에 Furive가 읽을 이름·버전·실행 방법을 붙인 운용 단위 센서 드라이버, 녹화 프로그램, 차량 화면
    플랫폼 차량·센서 모델과 사용할 패키지의 조합 같은 구성을 쓰는 차량들이 공유하는 설정
    설치할 PC 플랫폼이 정한 장비와 기능 배정 A-ECU는 자율주행·기본 운영, HMI-ECU는 로깅·부가 기능

    각 팀은 기존 언어·프레임워크·저장소를 그대로 사용합니다. 일반 패키지는 package.yaml의 이름과 버전, 실행할 run.sh로 연결합니다. 기본값은 부가 기능 역할에서 실행하고 프로세스 상태를 확인하는 것입니다. 추가 요구가 생길 때만 연결 설정을 늘립니다. 실제 절차는 프로그램 연결에 있습니다.

    Autoware 소스와 모델은 별도 작업 공간에서 개발합니다. Furive OS는 플랫폼별로 사용할 소스 버전과 실행 구성을 연결합니다. 새 차량·센서는 차량 플랫폼 만들기를 따릅니다. 같은 구성을 지원할 때 installer나 updater를 복사하지 않습니다.

    누가 무엇을 하는가¶

    권장 구조는 A-ECU와 HMI-ECU로 부하를 나누는 분산 엣지 컴퓨팅입니다. 플랫폼이 각 PC에서 실행할 패키지를 정하고, Furive OS가 공통 운영 기반을 제공합니다.

    flowchart LR
  Config["플랫폼<br/>차량·센서·패키지 조합"] --> Main["A-ECU<br/>자율주행·기본 운영"]
  Config --> Edge["HMI-ECU<br/>데이터 로깅·부가 기능"]
  Main --> MainPackages["배정된 패키지"]
  Edge --> EdgePackages["배정된 패키지"]
  Main <-->|"등록·상태·업데이트 조정"| Edge

    각 PC의 패키지 실행 관리자가 프로그램을 순서대로 시작하고 중지·상태 확인·재시작을 맡습니다. 위 장비 이름은 분산 구성의 예입니다. A-ECU의 자율주행 연산을 보호하도록 부가 기능의 부하를 별도 PC에 배정하며, 그 PC가 없다고 A-ECU로 자동 이동시키지 않습니다. 개별 프로그램의 기능은 그 패키지가 담당합니다. 운영 화면은 상태를 보여주고 사용자 입력을 담당 프로그램에 전달합니다.

    필요한 패키지는 한 PC에도 함께 설치할 수 있습니다. 구체적인 배정과 지원 범위는 PC 구성 기준을 따릅니다.

    바꾸려는 동작 담당
    패키지 시작·중지·상태 확인 패키지 실행 관리자
    녹화·센서 처리·차량 제어 같은 기능 해당 기능 패키지
    Autoware 실행·종료 Autoware 실행 프로그램(Launcher)
    업데이트·이전 정상판 복구 공통 OTA 흐름
    상태 표시·사용자 입력 운영 화면

    같은 상태와 실행 규칙은 한 곳에서만 관리합니다. 화면이나 각 패키지에 별도의 업데이트·재시작 규칙을 만들지 않습니다. 정확한 담당 파일은 개발 계약에 있습니다.

    ⌨️ 화면과 CLI로 같은 기능 사용하기¶

    운영 화면과 터미널의 furive 명령은 같은 실행 관리자와 기능 설정을 사용합니다. 설치된 장비 배정은 자동으로 읽습니다. CLI를 쓰기 위해 운영 화면을 열어 둘 필요는 없습니다.

    flowchart LR
  UI["🖥️ 운영 화면"] --> Owners["공통 실행 관리자와 기능 담당"]
  CLI["⌨️ furive CLI"] --> Owners
  Owners --> Package["📦 패키지 시작·중지·로그"]
  Owners --> AW["🚘 Autoware 실행·빌드"]
  Owners --> OTA["🔄 업데이트·복구"]
  Owners --> Topic["📡 토픽 전달·DLS 녹화 요청"]

    활용 팁

    furive help로 현재 PC에서 가능한 작업을 확인하세요. CLI 명령어 표에 기능별 명령, 실행 범위와 결과 확인 방법이 있습니다.

    프로그램끼리 통신하기¶

    같은 PC의 프로그램은 Integration Gateway라는 공용 메시지 통로로 요청과 이벤트를 주고받을 수 있습니다. 이 통로는 메시지만 전달하고 기능 상태를 직접 관리하지 않습니다. 현재 두 PC의 Integration Gateway를 서로 연결하지는 않습니다.

    같은 PC의 ROS2 패키지는 로컬 ROS/DDS 환경을 사용합니다. 현재 HMI도 native ROS 2 adapter로 직접 연결합니다. HMI라는 이름 때문에 별도 HMI-ECU가 반드시 필요한 것은 아닙니다.

    서로 다른 PC 사이의 ROS2 데이터는 Zenoh Bridge가 전달합니다. PC 사이의 등록·상태·업데이트 조정과 정의된 운용 요청은 별도 제어 연결을 사용합니다. 이 경로를 수정할 때만 실행 구성요소를 봅니다.

    녹화는 DLS가 선택 토픽·세션·파일 검사·NAS 전송을 소유합니다. 토픽 전달 허용 → 수신 확인 → 녹화 → 종료 → 파일 검사 결과 확인은 서로 다른 단계이며, 녹화 선택이 PC 간 전달 범위를 넓히지 않습니다. DLS 사용 가이드에서 검사 결과까지 확인합니다.

    PC 시각 보정은 호스트의 chrony가 맡습니다. PC가 여럿이면 인증된 제어 연결로 시간 표본을 교환하고, 외부 표준시·차량 내부 기준·보정 중·미확인을 구분합니다. 시간 동기화를 봅니다.

    차량에 전달할 때 알아둘 것¶

    이름 맡는 일
    배포 버전(release) 차량에서 실행·설치할 내용을 고정하고 서명한 버전
    설치 묶음(bundle) 기존 배포 버전 선택에 차량별 접근 정보·지도 같은 전달 파일을 더한 ZIP
    test / normal 차량 한 대에서 확인하는 시험판 / 여러 차량에 배포하는 공용판

    새 PC는 설치 묶음의 ./bootstrap.sh로 설치합니다. 서비스는 부팅 때 자동으로 시작하고 A-ECU 운영 화면은 로그인 뒤 자동으로 열립니다. 내부 개발 PC의 화면은 필요할 때 furive dashboard로 엽니다. 설치된 차량은 지정된 배포 버전을 원격 업데이트(OTA)로 받습니다.

    flowchart LR
  Check["변경 검사"] --> Test["한 차량 test"]
  Test --> Verify{"기능·실패·복구 확인"}
  Verify -->|통과| Normal["normal 배포"]
  Verify -->|수정 필요| Fix["수정 후 재검사"]
  Fix --> Check

    차량 배포 저장소의 서명된 버전을 별도 폴더에 준비하고, 재시작 때 전환합니다. 실행 중인 폴더에서 git pull로 덮어쓰지 않습니다. 전환 뒤 필수 패키지가 정상인지 확인하고, 실패하면 보존한 직전 코드·설정·Docker 이미지로 돌아갑니다.

    실제 발행과 차량 적용은 차량 업데이트, 내부 복구 흐름은 이전 정상 버전 기준을 봅니다.

    보안과 검증¶

    구분 기본으로 포함된 것
    프로그램 검사 패키지 설정·실행 파일과 각 프로그램 저장소의 자체 테스트
    전체 검사 공통 코드 테스트, 설정·문서 링크·배포 규칙, 저장소에 들어간 비밀값 검사
    기본 보안 PC 사이 장비 신원과 암호화 연결 확인, 필요한 프로그램에만 접근 정보 전달, 녹화·외부 전송 기본 꺼짐
    차량 업데이트 서명된 배포 대상과 내용 확인, 한 차량 test에서 실제 기능·대표 실패·이전 정상판 복구 확인

    자동 검사만으로 센서·CAN·GPU·Docker·실제 네트워크 동작까지 확인되지는 않습니다. 관련 변경은 실차 시험으로 확인합니다. 검증 범위는 변경 검증, 운영자가 해야 할 일과 현재 한계는 보안·개인정보 기준에 있습니다.
