    Launcher 실행 흐름과 스크립트¶

    Launcher 서비스는 실행 요청을 기다리며 Autoware 상태를 관측합니다. 화면에서 실행을 누르거나 furive autoware start를 호출하면 저장된 모드·맵·플랫폼으로 컨테이너 안에서 ros2 launch를 실행합니다. 이 문서는 현재 구현의 호출 순서와 파일별 작업을 설명합니다. 화면 조작은 Launcher 사용 가이드, 명령은 Autoware 명령어 표를 봅니다.

    1. 서비스 시작과 Autoware 실행¶

    설치된 PC에서는 서비스와 배정된 화면이 자동 시작 정책을 따릅니다. 미설치 source checkout의 첫 개발 실행은 저장소 루트에서 ./furive dev main을 사용합니다. 아래 스크립트 경로는 구현을 읽기 위한 것이며 개별 실행 절차가 아닙니다.

    flowchart TD
  Node["PC의 Furive OS node"] --> PM["PackageManager"]
  PM --> Run["furive-launcher/run.sh<br/>중복 실행 잠금"]
  Run --> Service["launcher_main.py<br/>제어 서비스·상태 관측"]
  UI["Launcher 화면 / furive autoware start"] --> Adapter["화면·node 요청 adapter"]
  Adapter --> Socket["core/launcher_control.py<br/>로컬 Unix socket"]
  Socket --> Service
  Service -->|실행 요청| Docker["runtime/docker_run.sh<br/>컨테이너 준비"]
  Docker --> Start["컨테이너 안의 runtime/start.sh<br/>지도·모델·ROS 환경 확인"]
  Start --> ROS["ros2 launch autoware_launch<br/>선택한 모드.launch.xml"]

    run.sh는 /tmp/furive-launcher.lock을 flock으로 잠근 뒤 exec python3 -u launcher_main.py로 프로세스를 교체합니다. 이미 잠겨 있으면 중복 시작을 건너뜁니다. PackageManager는 이 런처 프로세스를 감독합니다. 패키지는 그래픽 세션 준비가 필요하다고 선언합니다.

    launcher_main.py:main()은 FuriveLauncher와 LauncherControlServer를 만들고 요청을 기다립니다. 기본 소켓은 /tmp/furive-launcher-control-<UID>.sock이고 접근 권한은 해당 사용자에게만 줍니다. 상태 관측 스레드도 시작하지만 이 초기화에서 Autoware 시작 함수를 호출하지는 않습니다. Launcher 앱을 열면 상태를 조회하며, 이미 실행 중인 Autoware가 있으면 그 상태를 표시합니다. 화면을 닫는 동작도 Autoware 중지 요청과 별개입니다.

    2. 실행 요청을 받았을 때¶

    실제 시작 진입점은 FuriveLauncher.runtime_command("start")입니다.

    1. 현재 컨테이너와 추적 중인 실행 프로세스를 확인합니다. 이미 실행 중이거나 시작 중이면 그 상태를 반환하고 중복 프로세스를 만들지 않습니다. Compose 구성·프로젝트 조회 또는 Docker 접근 오류는 시작 실패로 반환합니다.
    2. 빌드·빌드 정리·소스 동기화가 진행 중인지, workspace와 빌드된 autoware_launch가 있는지 확인합니다. 준비되지 않았으면 시작을 거부합니다. 시작 버튼이 소스 동기화나 빌드를 대신 실행하지 않습니다.
    3. 저장된 실행 모드가 workspace에서 발견한 최상위 *.launch.xml 후보인지 검사합니다. 소스의 src/launcher/autoware_launch/autoware_launch/launch를 먼저 찾고, 해당 디렉터리가 없으면 install/autoware_launch/share/autoware_launch/launch를 찾습니다.
    4. 현재 설정에서 컨테이너·workspace·선택 파일·Compose 경로와 모드를 실행 환경에 전달합니다.
    5. bash runtime/docker_run.sh를 별도 프로세스 세션으로 시작합니다. 표준 출력과 오류는 Furive OS 실행 루트의 logs/furive_launcher_autoware.log에 이어 씁니다.

    이때 반환되는 status: ok와 PID는 실행 스크립트를 시작했다는 뜻입니다. 이후 컨테이너 준비나 지도 검사, ROS launch가 실패할 수 있으므로 상태와 로그를 확인해야 합니다.

    3. docker_run.sh: 실행할 컨테이너 준비¶

    Launcher가 선택하는 기본 runtime은 docker_compose입니다. 같은 파일 안에 기존 docker run 경로도 있으므로 파일 이름만으로 어느 경로가 실행되는지 판단하지 않습니다.

    기본 Compose 경로¶

    1. host workspace의 존재를 확인하고 .devcontainer/compose.yaml을 읽습니다. 같은 위치의 devcontainer.json이 Compose 파일 목록을 선언하면 그 순서와 추가 파일도 사용합니다. 프로젝트 선택은 core/autoware_runtime.py에 맡깁니다.
    2. 기본 furive 서비스에는 compose.workspace-override.yaml을 더합니다. host의 Autoware 폴더와 workspace를 컨테이너에 연결하고, Furive OS 루트를 /opt/furive-os에 읽기 전용으로 연결합니다. 생성하는 서비스에는 io.furive.launcher=autoware 소유 표시를 붙입니다.
    3. 해당 Compose 서비스의 기존 컨테이너를 확인합니다. 런처 소유 표시가 없는 기존 컨테이너는 실행 중이면 재사용하고, 멈춰 있으면 compose start로 다시 켭니다. 이 분기에서는 재생성하지 않습니다. 런처 소유 컨테이너는 Compose 설정 hash가 달라지면 재생성하고 compose up -d로 준비합니다.
    4. 같은 이름을 다른 컨테이너가 사용하면, 실행 중인 컨테이너와의 충돌은 오류로 끝냅니다. 멈춘 충돌 컨테이너는 이름 뒤에 -furive-stopped-<ID 일부>를 붙여 보존합니다.
    5. 컨테이너에 CycloneDDS 설정이 있는지 확인합니다. 기존 컨테이너에 없으면 Furive OS의 설정 파일을 컨테이너의 /tmp/furive-os/cyclonedds_config.xml로 복사하고 그 경로를 전달합니다.
    6. compose exec -T로 실행 모드·선택 파일·ROS Domain·CAN 설정을 전달합니다. 기본 경로에서는 패키지의 runtime/start.sh 내용을 표준 입력으로 보내 컨테이너의 bash -s로 실행합니다. compose.start_script가 별도로 지정된 기존 구성은 그 명령을 사용합니다.

    컨테이너의 실제 image·기본 장치·권한은 Autoware workspace의 Compose 선언을 함께 읽어야 알 수 있습니다. 런처의 workspace override가 이 선언 전체를 대체하지는 않습니다.

    기존 Docker 경로¶

    runtime이 docker인 구성은 같은 이름의 컨테이너 충돌을 확인한 뒤 docker run으로 생성합니다. 현재 스크립트는 GPU, host network/PID/IPC, privileged 권한과 /dev, X11, 오디오, workspace 등의 mount를 지정합니다. 컨테이너 안의 /opt/furive-launcher/start.sh를 실행하고 --rm으로 종료 시 컨테이너를 제거합니다. 이 경로는 NVIDIA runtime과 특정 장치·host 경로를 전제하므로 기본 Compose 경로와 동일한 실행 조건으로 설명하면 안 됩니다.

    4. start.sh: 지도와 모델을 ROS launch에 연결¶

    이 스크립트는 컨테이너 안에서 다음 순서로 진행합니다.

    1. 실행 모드 이름 형식과 Autoware의 install/setup.bash 존재를 확인합니다.
    2. 저장된 플랫폼을 읽습니다. 값이 없으면 환경변수와 자동 탐색 결과를 사용합니다. 탐색 순서와 모델 이름은 플랫폼 탐색에 있습니다.
    3. 저장된 지도를 경로로 풉니다. 상대 이름은 컨테이너 Autoware 폴더의 furive_map 아래로 해석합니다. 지도 디렉터리와 lanelet2_map.osm, pointcloud_map.pcd, map_projector_info.yaml 세 파일이 없으면 종료합니다. 화면의 지도 후보 목록은 폴더 목록이므로 후보 표시만으로 이 검사를 통과한 것은 아닙니다.
    4. install/setup.bash를 읽어 ROS 실행 환경을 불러옵니다. 전달받은 ROS Domain과 RMW를 적용하고 CycloneDDS 설정 경로를 확인합니다. 지정한 파일도 기본 대체 파일도 없으면 종료합니다.
    5. 실행 모드가 autoware이고 CAN 준비가 활성화되어 있으면 CAN 인터페이스를 확인합니다. 전달된 인터페이스 목록을 사용하며 스크립트의 대체값은 can0 can1입니다. 없는 장치와 이미 UP인 장치는 건너뛰고, 나머지는 sudo ip link set … up type can bitrate 500000을 시도합니다. 현재 구현은 CAN 설정 실패를 경고로 남기고 계속 진행합니다. launch 시작을 CAN 준비 성공으로 해석하지 않습니다. 다른 실행 모드에서는 이 CAN 준비 단계를 건너뜁니다.
    6. 관리 대상 표시 FURIVE_LAUNCHER_MANAGED=1과 컨테이너의 /tmp/furive-launcher/autoware.pid를 기록합니다. 중지 시 해당 프로세스를 찾는 데 사용합니다.
    7. 차량·센서 모델 이름을 결정하고 선택 모드의 launch 파일이 남아 있는지 다시 확인한 뒤 아래 형태로 프로세스를 교체합니다.
    exec ros2 launch autoware_launch <실행 모드>.launch.xml \
    map_path:=<컨테이너 안 지도 경로> \
    vehicle_model:=<차량 모델> \
    sensor_model:=<센서 모델>

    예를 들어 autoware 모드, ioniq5 플랫폼, dgist 지도를 선택하고 별도 모델 override가 없다면 autoware.launch.xml에 ioniq5_vehicle, ioniq5_sensor_kit, 컨테이너의 furive_map/dgist 경로를 전달합니다. AWSIM은 sample_vehicle과 awsim_sensor_kit을 사용합니다. 기존 _trailer_tracker 선택은 접미사를 제거해 모델 이름을 만들지만, 현재 실행 명령에는 trailer_tracker_mode 인자를 전달하지 않습니다.

    센서·localization·planning·control·RViz 중 무엇이 실제로 켜지는지는 선택한 Autoware revision의 launch 파일과 그 파일이 포함하는 차량·센서 launch 구성이 결정합니다. 이어 읽을 곳은 해당 workspace의 autoware_launch/launch/<실행 모드>.launch.xml입니다. 런처 스크립트 자체에 전체 ROS node 목록이 고정되어 있지는 않습니다.

    5. 선택값·파일·로그의 위치¶

    다음은 별도 경로 설정이 없는 기본값입니다. 실제 선택과 상태는 furive autoware config, furive autoware status로 확인합니다. 설치 상태와 플랫폼에서 전달한 경로가 있으면 그 값을 따릅니다.

    파일·위치 쓰임
    host의 ~/Documents/Autoware/furive_autoware_main Autoware source와 install 빌드 결과
    host의 ~/Documents/Autoware/furive_map 선택할 지도 폴더
    host의 ~/Documents/Autoware/scripts/selected_map.txt 저장된 지도 이름 또는 경로
    같은 폴더의 selected_platform.txt 저장된 플랫폼
    같은 폴더의 selected_launch_type.txt 저장된 실행 모드. 런처가 읽어 환경변수로 전달
    컨테이너의 /home/fd/Documents/Autoware 기본 mount 대상. Compose 실행은 이 위치의 scripts에서 지도·플랫폼 선택 파일을 읽음
    Furive OS 루트의 logs/furive_launcher_autoware.log 컨테이너 준비부터 ROS launch까지의 출력·오류
    host의 ~/.cache/furive-launcher/compose-<서비스>.hash Compose 설정 변경 확인용 hash. 선택 설정 원본은 아님

    설정 저장은 다음 실행에 쓸 선택 파일을 씁니다. 실행 중인 ROS node에 지도를 즉시 다시 적용하는 작업은 아닙니다. 런처는 host 경로로 workspace를 검사하고, 컨테이너에서는 mount된 경로를 사용하므로 지도·설정 파일 오류는 양쪽에서 같은 파일이 보이는지도 확인합니다.

    6. 상태 관측과 중지¶

    runtime_status()는 추적하는 host 프로세스의 종료 코드, Docker 상태, 컨테이너 안의 autoware_launch 실행 프로세스와 rviz2를 확인합니다. launch_failed는 추적 프로세스가 오류 코드로 종료한 상태이고, container_idle은 추적 프로세스가 없는 상태에서 컨테이너만 켜져 있고 Autoware 프로세스는 발견하지 못한 경우입니다. 이 관측은 ROS node의 준비 완료나 자율주행 가능 여부 검사가 아닙니다.

    runtime_command("stop")은 다음 작업을 수행합니다.

    1. 설정된 컨테이너 안에서 PID 파일과 관리 대상 표시를 확인해 Autoware 프로세스를 찾습니다. 해당 PID를 확인할 수 없으면 ros2 … launch … autoware_launch 패턴으로 찾습니다. TERM을 보낸 뒤 제한 시간 내 종료하지 않으면 KILL하고 결과를 확인합니다.
    2. 런처가 추적하는 host 실행 프로세스 그룹을 종료합니다.
    3. Compose의 경우 런처 소유 컨테이너는 기본적으로 stop 후 rm합니다. 기존 stop_mode: down 구성에서는 down을 사용합니다. 런처 소유 표시가 없는 기존 Compose 컨테이너는 중지만 하고 보존합니다. Docker 경로는 지정 컨테이너를 중지·제거합니다. host의 source·지도·빌드 결과는 남습니다.
    4. 정리 실패는 호출자에게 오류로 반환합니다. 성공 후에는 node에 autoware_stopped 이벤트를 보냅니다. 상태 관측에서도 실행 중 → 중지 전이를 감지하면 같은 이벤트를 예약합니다. node의 PackageManager가 autoware_stop lifecycle을 선언한 실행 중 패키지만 재시작하며 연결된 상대 PC에도 이벤트를 전달합니다. 이벤트 전송과 상대 PC에서의 처리 완료는 Autoware 중지 응답과 별도로 확인해야 합니다.

    화면 닫기, Launcher 제어 서비스 종료, Autoware 중지는 서로 다른 동작입니다. 현재 런처의 signal handler는 제어 소켓과 상태 관측을 닫으며 runtime_command("stop")을 호출하지 않습니다. Autoware 중지는 운용 가이드의 중지 절차로 요청합니다.

    7. 구현을 읽는 순서¶

    파일 담당 작업
    package.yaml 실행 진입점·배정·그래픽 세션 요구·런처 프로세스 health 선언
    run.sh 중복 실행 잠금과 Python 제어 서비스 실행
    launcher_main.py 선택 저장, 시작 조건 확인, 실행 프로세스 추적, 상태·중지, 빌드·동기화 요청 처리
    launcher_control.py 화면·CLI가 같은 런처에 요청하는 로컬 제어 통신
    docker_run.sh Compose/Docker 컨테이너 준비와 컨테이너 안 시작 스크립트 호출
    compose.workspace-override.yaml 기본 Compose 서비스의 workspace mount와 소유 표시
    start.sh 지도·모델·ROS·CAN 확인과 최종 ros2 launch
    record_start.sh 기존 ROS recorder 실행 스크립트. 현재 runtime_command("start")에서는 호출하지 않음

    configs/set_2_run_with_recorder.json에 recorder 항목이 있어도 현재 Autoware 시작 함수는 recorder를 자동 실행하지 않습니다. DLS 녹화는 별도 패키지의 기능이므로 Data Logging System 가이드를 따릅니다.
