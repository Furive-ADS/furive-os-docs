    CI/CD 기준¶

    이 문서는 배포 자동화의 세부 입력·산출물과 현재 보장 범위를 조사할 때 보는 자료입니다. 평상시 발행 절차는 차량 업데이트를 따릅니다.

    처음부터 끝까지 읽을 필요는 없습니다.

    알고 싶은 것 볼 곳
    지금 변경에 배포 버전이나 설치 묶음이 필요한가? 릴리즈 여부 결정
    일상 개발·차량 시험·고객 배포에서 무엇을 확인하는가? 변경 검증
    CI가 자동으로 검사·생성·수정하는 것은 무엇인가? 한눈에 보기부터 필요한 절
    workflow 구현을 어디서 읽고 수정하는가? 워크플로 코드 위치
    차량에서 버전을 발행·적용하는 명령은 무엇인가? 차량 업데이트

    차량 실행 내용이 바뀌었는지는 scripts/release/deploy_impact.py가 판단하고, 차량용 파일은 배포 자동화가 만듭니다. 패키지나 설치 묶음에 같은 판단 규칙을 다시 만들지 않습니다.

    flowchart LR
  Change["🧑‍💻 코드 변경"] --> Test["✅ 코드·패키지 검사"]
  Test --> Impact{"❓ 차량 산출물이<br/>바뀌는가?"}
  Impact -->|아니요| Merge["✅ 코드 변경만 완료"]
  Impact -->|설치 묶음만| Bundle["📦 기존 배포 버전으로<br/>설치 묶음 생성"]
  Impact -->|실행 내용| Build["⚙️ 차량용 파일과 Docker 이미지 생성"]
  Build --> Verify["✅ 구조·업데이트 경로 검사"]
  Verify --> Publish["🧪 test/RC 발행"]
  Publish --> Vehicle["🚘 차량 한 대 기능·복구 시험"]
  Vehicle --> Normal["🏷️ normal 승격"]
  Normal -->|설치 전달물도 바뀜| Bundle

    CI는 코드·패키지 검사와 배포 파일 구조를 자동 확인합니다. 실제 ROS/API/장치 기능, 보호된 시험 차량 배포와 HIL은 아직 모두 자동화되지 않았습니다. 따라서 CI 통과만으로 실차 기능까지 검증됐다고 판단하지 않습니다.

    활용 팁

    관련 기준

    운영/품질 기준 전체는 변경 검증을 따릅니다.

    이 문서는 그중 GitHub Actions가 자동으로 해주는 일만 정리합니다.

    워크플로 코드 위치¶

    릴리즈 흐름은 deploy-repo-release.yml에서 읽습니다. 이 파일은 trigger, 작업 순서, 조건, runner, 권한과 단계 간 입출력을 소유합니다. 긴 실행 구현은 기존 scripts/release/ 안에서 책임별로 관리하며, source 저장소 루트를 cwd로 사용합니다.

    수정할 책임 구현 위치
    source 검증 증거 선택·검증·보존 ci-locate-source-evidence.sh, ci-verify-source-evidence.sh, ci-save-source-evidence.sh
    architecture·기존 deploy 상태 ci-resolve-architectures.sh, ci-prepare-deploy.sh
    공통·package image build ci-build-base-image.sh, ci-build-package-images.sh
    deploy 산출물과 서명 전달물 준비 ci-stage-deploy.sh, ci-prepare-signing-handoff.sh
    실패한 OTA 검증 재개 ci-locate-staged-checkpoint.sh, ci-resume-staged-release.sh
    발행 대상·완료 증거 검증 ci-validate-publication.sh, ci-validate-transition.sh
    보호된 서명·발행 deploy-repo-sign.yml

    서명 workflow는 호출한 workflow와 같은 commit에서 실행되는 내부 workflow_call입니다. 직렬 실행과 선행 검증 조건은 호출자가, production-signing Environment와 서명 key 사용은 호출된 job이 소유합니다. 등록된 secret 이름과 기존 전달물 identity만 연결하며 새 운영자 입력은 없습니다. GitHub의 재사용 workflow 규칙에 따라 Environment secret은 호출된 job에서 해석됩니다.

    서명 코드는 보호된 runner가 source를 checkout하거나 전달물 안의 실행 코드를 사용하지 않도록 전용 YAML 안에 유지합니다. 짧은 signer 사전 검사와 source 쓰기 권한을 갖는 transition 기록도 기존 checkout 없는 경계를 유지합니다. 일반 build·검증 구현을 이 경계로 옮기지 않습니다.

    검증·build 구현 또는 서명 workflow가 바뀌면 이전 package 증거를 자동 재사용하지 않습니다. checkpoint 재개는 검증 구현의 제한된 변경만 허용하며 image·deploy 생성 코드 변경은 새 실행이 필요합니다. 코드 위치가 바뀌어도 증거를 다시 확인해야 하는 조건은 유지합니다.

    릴리즈 여부 결정¶

    배포 버전은 Git commit을 보관하기 위해 만드는 것이 아닙니다. 어떤 파일을 수정했는지가 아니라 차량이 실행할 내용과 설치 때 전달할 내용이 바뀌었는지로 판단합니다.

    바뀐 산출물 해야 할 일 대표 사례
    차량의 실행·설치 내용 furive release test ... 설치 코드, 업데이트 코드, 패키지·Docker 이미지 버전, 플랫폼·Autoware 버전, 차량 설정 변경
    설치 묶음의 전달 내용만 furive bundle <차량-ID> 접근 정보 교체, 지도 추가, 기존 배포 버전 선택, 같은 Docker 이미지 파일의 재포장
    둘 다 먼저 release, 성공 후 bundle 새 실행 내용을 새 차량 설치 묶음으로 전달
    둘 다 아님 코드 검사와 merge만 수행 문서·테스트, 검사 속도 개선, 개발 도구 내부 개선

    판단 기준은 차량 실행 파일, Docker 이미지, 패키지와 Autoware 버전이 달라지는지입니다. Git commit이 달라졌다는 이유만으로 새 배포 버전을 만들지 않습니다. 반대로 차량 실행 결과가 달라지면 생성 도구를 직접 수정하지 않았어도 새 배포 버전이 필요합니다. 이미 발행한 버전의 내용은 바꾸지 않습니다.

    설치 묶음이 설치 결과에 영향을 줄 때¶

    설치 묶음은 기존의 서명된 배포 버전을 선택하고 접근 정보, 지도와 Docker 이미지 파일을 전달합니다. 이 전달 방식만 바뀌면 설치 묶음만 다시 만듭니다.

    다음 경우에는 설치 묶음만 바꾸면 안 됩니다.

    • bootstrap.sh가 패키지·플랫폼·Autoware 버전을 새로 선택한다.
    • 설치 묶음이 설치 옵션을 넘겨 계속 유지되는 실행 상태를 바꾼다.
    • 전달한 Docker 파일이 배포 버전에 적힌 이미지와 다른 내용을 선택한다.
    • 같은 배포 버전인데 설치 묶음에 따라 서비스나 설정이 달라진다.

    이때는 설치와 실행 결정을 기존 설치·배포 설정으로 옮깁니다. 차량 실행 내용이 달라지면 배포 버전을 먼저 발행하고, 그 버전을 선택한 설치 묶음을 만듭니다.

    실행 전 네 가지 질문¶

    1. 차량이 실행할 코드·패키지·Docker 이미지·Autoware 버전이 달라지는가? 배포 버전을 만듭니다.
    2. 같은 배포 버전에서 접근 정보·지도·전달 방식만 달라지는가? 설치 묶음만 만듭니다.
    3. 설치 묶음이 계속 유지될 실행 설정을 정하는가? 그 설정을 배포 버전으로 옮긴 뒤 둘 다 만듭니다.
    4. 두 산출물이 모두 같은가? release와 bundle을 만들지 않는다.

    release + bundle인 경우 순서는 반드시 signed deploy release 발행·검증 완료 후 bundle 생성이다. bundle은 성공한 기존 release만 pin하며, 아직 게시되지 않은 source commit을 release처럼 전달하지 않는다.

    이 판단은 scripts/release/deploy_impact.py 한 곳이 소유한다. 알려진 문서·테스트·bundle-only 경로만 명시적으로 제외하고, exporter 입력·image build 입력·package gitlink·release workflow와 새로 생긴 미분류 경로는 기본적으로 deploy 영향으로 판정한다. 따라서 새 경로를 잘못 제외해 release가 빠지는 방향이 아니라, 소유권을 확인할 때까지 release가 필요하다고 보는 방향으로 실패한다.

    • furive release ... --run은 직전 같은 channel source tag 이후 deploy 영향 경로가 없으면 발행을 거부한다.
    • furive bundle은 선택한 signed deploy manifest의 source_ref부터 현재 clean HEAD까지 검사한다.
    • bundle-only·문서·테스트 변경만 있으면 기존 signed deploy release를 허용한다.
    • 미릴리즈 deploy 영향 변경, 분기된 source history, dirty tracked source는 bundle 생성 전에 실패한다.

    빠른 PR 검증과 전체 릴리즈 검증¶

    변경 PR·merge queue에서 실행하는 검사
    한 package의 코드·gitlink 전체 root 검사 + 변경 package와 manifest dependencies의 간접 의존 package
    root 문서 Markdown·Python test만 전체 root 검사; package suite 생략
    공통 runtime·설치·설정·shared image 입력·CI 정책 전체 root + 전체 package
    package 삭제·이름 변경, 미분류 경로, 비교 실패·dirty checkout 전체 검사로 복귀
    기존 대상의 정확한 Autoware SHA lock만 기존 Autoware lock 전용 검사

    선택 정책은 기존 scripts/checks/run-package-tests.py가 소유한다. root package 통합 계약은 계속 전부 실행하므로 checkout과 Python 공통 의존성 설치는 유지한다. Node 의존성은 선택된 package에만 설치한다. 새 commit이 들어온 PR의 이전 검사는 취소한다. merge queue와 수동 실행은 실행 도중 취소하지 않는다.

    furive check와 release는 전체 검증을 유지한다. CI 내부 비교 옵션은 검증 대상 선택에만 사용하며 새로운 사용자 절차는 없다. 부분 검사 JSON에는 전체 inventory, 선택 경로와 base/head를 기록하고, 전체 release 검증의 PASS로 재사용할 수 없다. 기존의 exact release evidence 재사용 정책은 유지한다.

    Docker 이미지는 이미 package revision + 공통 base content + architecture로 재사용한다. root commit이나 다른 package만 바뀌었다고 동일 component를 다시 빌드하지 않는다. 공통 base가 바뀌면 이를 소비하는 package image는 다시 필요하며, release alias/digest 검증은 빌드 생략 여부와 관계없이 수행한다. 빌드 분기 회귀는 workflow의 실제 Bash를 실행해 cache hit/miss와 실패 후 발행 차단을 확인한다. 실제 registry·Docker 실행 시간 단축 수치는 CI 실행 후 비교해야 한다.

    검증 lane과 현재 상태¶

    Release 승격은 다음 네 lane의 증거를 서로 대체하지 않고 누적해야 한다. 구현됨은 저장소에 실행 workflow와 fail-closed 계약이 있는 범위만 뜻한다.

    lane 필수 판정 현재 자동화 상태
    1. PR root + tracked package executable tests 검토 대상 root SHA와 그 index의 package/core, package/plugin에서 실행 가능 test를 수행한다. PR은 위 변경 범위를, release는 전체 inventory를 사용한다. no-tests, 실패, timeout, 필수 pytest skip과 Node TAP의 0건·skip·todo·cancel은 모두 실패다. .github/workflows/quality-checks.yml의 trusted job과 release source gate가 root 검사 및 내부 run-package-tests를 실행한다. runner는 Python/ROS Python, TAP Node test와 test·tests·scripts 아래 shell test-*.sh를 package별 cwd·임시 경로에서 최대 네 개 병렬 실행한다. CI에서는 package HEAD가 gitlink와 다르거나 시작·종료 worktree가 dirty이면 실패한다. 개발 검사는 큰 payload를 다시 읽지 않고 actual HEAD만 기록한다. root/package JUnit과 package JSON report를 artifact로 보존한다.
    2. RC exact artifact/image semantic smoke export된 RC commit/artifact와 repository@sha256:... image만 기동해 정상·고장 입력의 기능 결과와 cleanup을 검사한다. 정책/필수 후속. 현재 deploy artifact 검사, registry digest 확인, recovery dry-run은 구조 검증이다. updater 검증도 합성 health를 사용하며 실제 package semantic smoke가 아니다.
    3. 보호된 test 배포 normal 기준판의 등록 차량을 preview/<vehicle_id> test release로 올려 실제 ROS/API/장치 probe를 통과시키고 normal 기준판으로 rollback한다. Autoware revision 변경도 적용·복원 SHA로 입증한다. 정책/필수 후속. preview route, candidate/rollback 코드와 합성 회귀는 구현됐지만 보호된 시험 차량에서 이 순서와 증거 수집을 수행하는 workflow는 없다.
    4. nightly/bench HIL CAN, 센서, GPU/display, NAS 등을 연결한 bench에서 장시간·재부팅·단절·복구 시나리오를 실행한다. 정책/필수 후속. bench inventory, 예약, probe/JUnit 수집과 release 차단 연결이 필요하다.

    보호된 test 배포 host의 내부 post-apply gate는 다음과 같이 호출한다. --expected-version과 --expected-source-ref를 항상 함께 넘겨야 형식이 올바른 임의 release가 아니라 CI가 선택한 exact 대상을 증명한다.

    python3 scripts/checks/verify-ota-update.py --strict-runtime \
  --expected-version <release-tag> \
  --expected-source-ref <40-character-lowercase-source-commit> \
  --json

    이 gate는 최신이며 실행 중인 OTA 상태, canonical manifest identity의 형식과 exact match, active systemd service, 실행 가능한 package entrypoint/binary, release lock의 Docker image와 그 image ID로 실행 중인 container를 확인한다. 상태를 조회할 수 없거나 증거가 없으면 warning으로 통과시키지 않고 nonzero로 종료한다. 다만 이는 runtime liveness/identity gate이며 ROS/API/장치의 semantic probe는 아니다. Release source gate는 release branch가 선택한 Autoware 플랫폼의 root commit과 .repos 하위 저장소가 모두 source-owned 40자리 SHA로 고정됐는지만 확인한다. Generic release runner는 플랫폼마다 다른 의존성·container·장치를 재현할 수 있다고 가정하지 않으며 Autoware를 build하지 않는다. 생성된 release/external-workspaces.yaml에는 build_validation: not_performed가 명시된다. 이미 존재하는 deploy tag도 source에서 다시 생성한 external-workspace lock의 hash가 실제 tag blob 및 manifest hash와 같을 때만 up-to-date로 처리한다. 따라서 사람이 계산한 fingerprint나 이전 tag의 source SHA만으로 release를 통과시킬 수 없다. furive check --platform <플랫폼>은 해당 플랫폼을 build할 수 있는 PC에서 쓰는 선택적 로컬 진단이며 release receipt를 만들지 않는다. 고객용 normal의 실행 증거는 시험 차량에서 launcher가 고정 revision을 실제 기동한 SHA와 launch/ROS probe로 남긴다.

    기존 ipg-g80과 furive-niro는 root SHA만 고정돼 차량 적용 때 manifest branch tip을 다시 해석하던 상태였다. 이번 source lock부터 각 pinned root manifest의 현재 해석 결과를 nested SHA로 직접 고정해 같은 release가 이후 다른 source를 받지 않게 했다. 이 결정성 보강은 build 검증을 뜻하지 않으며 세 플랫폼 모두 artifact의 build_validation: not_performed 계약을 따른다.

    fork PR은 private submodule credential을 받지 않으므로 gitlink fixture로 gate 자체의 fail-closed 동작만 검사한다. 실제 package source를 포함하는 lane 1은 같은 저장소 PR, merge queue 또는 승인된 수동 실행의 trusted job에서 수행한다. tracked gitlink checkout이 누락되거나 다른 SHA이면 이 job은 먼저 실패한다.

    개발 속도와 실행 경계¶

    테스트 개수나 전체 build 반복을 안전성의 대리 지표로 쓰지 않는다. 설치 script 변경은 source 문자열 존재만 확인하지 않고 installer 함수의 실제 분기와 외부 명령 경계를 짧은 fake host/Docker로 실행한다. 예를 들어 Autoware bootstrap 계약은 pin된 Dockerfile/Compose의 최종 bundle seed 선택, registry pull 금지, tracked devcontainer.json Compose 목록과 checkout 무변경, 선택 BASE_IMAGE만 --build-arg로 넘긴 .devcontainer/Dockerfile 파생 image build, identity-bound local tag, ROS setup 후 그 image의 docker run과 install 결과 확인을 한 흐름으로 검증한다. 이 계약은 실제 차량 장치 시험을 대체하지 않지만 shell 환경 누락을 full Autoware build 전에 잡는 빠른 실패 경계다.

    furive check의 root suite와 package suite는 서로 상태를 소유하지 않는 독립 lane이므로 동시에 실행한다. 어느 한쪽도 다른 쪽의 성공을 대신하지 않으며 두 종료 코드가 모두 성공해야 다음 artifact 검사로 간다. 플랫폼 전체 Autoware build는 일상적인 root script·문서·테스트 변경마다 반복하지 않고, Autoware revision, image 또는 build recipe가 바뀐 경우와 명시적인 플랫폼 진단에서 수행한다. 재사용 증거는 exact source/image identity에 결박하며 identity가 다르거나 판단할 수 없으면 재실행한다.

    PR 또는 release delta가 config/external-workspaces.yaml 한 파일뿐이고 YAML 의미 비교 결과가 기존 target의 root commit과 repositories exact SHA 값 변경으로만 증명되면 autoware-lock-only lane을 사용한다. 이 lane은 private package submodule·LFS·Node 의존성을 받지 않고 Autoware source 선택·render·credential·release 계약만 실행한다. target 추가, branch·workspace·build metadata 변경, 다른 파일 변경, 잘못된 SHA 또는 base revision을 확인할 수 없는 경우에는 자동으로 전체 root/package 검증으로 돌아간다. 이 최적화는 deploy release 필요 여부를 바꾸지 않으며 generic runner가 Autoware build 성공을 주장하게 만들지 않는다.

    bundle 생성도 같은 원칙을 따른다. 서로 독립인 main/edge bootstrap smoke는 같은 read-only deploy object cache를 shared lock으로 읽으며 병렬 실행하고, cache 갱신만 exclusive lock이 소유한다. 실제 차량 bootstrap은 branch와 exact signed tag를 한 fetch transaction으로 받고, desired와 landing release identity가 같은 fresh install에서는 같은 서명 검사를 반복하지 않는다. 어느 최적화도 exact commit/tag 검증, 원격 branch 재확인 또는 ZIP byte/mode 전수검증을 생략하지 않는다.

    승격 증거 묶음¶

    증거 결박할 대상
    source identity root SHA와 모든 대상 package gitlink SHA
    deploy identity deploy commit/artifact hash와 실제 실행 OCI image digest
    Autoware identity 플랫폼 이름, Autoware root SHA와 관리 대상 하위 저장소 SHA
    자동 test root/package JUnit, package test report, 종료 코드와 전체 log

    각 파일은 release ID, workflow run, lane과 시간을 함께 기록한다. PID/container 생존이나 source 문자열 검사는 보조 구조 증거일 뿐 semantic PASS가 아니다. 필수 test 또는 probe의 skip은 PASS나 조건부 성공이 아니라 FAIL이다. 현재 PR job은 package gitlink와 stdout/stderr를 담은 JSON report, package Python suite별 JUnit과 root pytest JUnit을 함께 보존한다.

    언제 실행되나¶

    방식 조건
    자동 실행 main branch push. 기본은 job skip이며 release 작업은 하지 않음
    자동 실행 canonical vYYYY.MM.DD.N tag push 한 건
    수동 실행 GitHub Actions workflow_dispatch

    branch push release job은 기본적으로 skip되어 source submodule checkout, LFS hydrate, Docker build, deploy repo export를 수행하지 않는다. 따라서 scripts/release/release-sync.py 기본 실행은 main과 canonical tag 한 건만 발행한다. 운영상 branch push에서도 release 작업을 허용해야 하는 경우에만 repository variable ENABLE_BRANCH_PUSH_RELEASES=true를 설정한다.

    일회성 전환처럼 source release tag가 여러 개인 경우에는 alias tag를 먼저 한 번의 atomic push로 발행하고 canonical main tag를 마지막 단독 push로 발행한다. GitHub는 한 push에서 tag를 3개 넘게 만들면 push event를 생성하지 않으므로, 마지막 canonical tag가 전체 tag 집합의 공개 barrier이자 workflow trigger다. Resolver는 canonical event에서 같은 source commit의 alias가 하나라도 빠지면 실패한다. 따라서 자동 발행에는 source repo Git SSH 쓰기 권한만 필요하며 로컬 gh API token은 필요하지 않다. 수동 workflow_dispatch와 CLI로 run 상태를 조회할 때는 유효한 gh 인증 또는 GitHub Actions UI가 별도로 필요하다. 자세한 event 제한은 GitHub Actions의 push event 문서를 따른다.

    수동 실행 입력값:

    입력 하는 일
    version 특정 release tag만 처리
    deploy_branch 기본 main. 과거 branch 복구 작업에서만 명시
    staged_release_run_id, staged_release_run_attempt 내부 복구 전용. 실패 run의 exact staging checkpoint에서 OTA 검증만 다시 시작
    target_arch build 대상 architecture 선택: auto, amd64, arm64, all

    OTA upgrade 검증이 실패해도 이미 통과한 source/package 검증, image build/push, deploy export를 다시 실행하지 않는다. 실패 run이 서명 전 업로드한 7일 보존 checkpoint를 지정하면 현재 main의 OTA verifier와 release test 변경만 허용해 재검증하고, 동일 source SHA·release set·staged commit을 그대로 서명 경계에 전달한다. 그 밖의 source·package·config 변경이 섞이면 checkpoint 재사용은 실패한다.

    같은 source SHA의 앞선 run에서 clean source/package 증적 artifact가 남아 있으면 preview와 normal 재시도 모두 그 exact artifact를 사용한다. 이때 Python/Node setup, private package/LFS hydration과 11분 source/package matrix를 다시 실행하지 않는다. 새 source SHA이거나 artifact가 만료·불완전하면 자동으로 전체 gate로 돌아간다. Release image는 component content identity의 registry manifest가 이미 있으면 다시 build/push하지 않으므로, 24분 image 작업도 동일 입력에서 반복하지 않는다.

    새 test tag에서 package gitlink가 모두 같고 package test runner·hydration·workflow 계약도 바뀌지 않았다면 직전 성공 artifact의 전체 package clean 증적을 상속한다. Root release/OTA 파일만 바뀐 좁은 변경은 해당 회귀 묶음을 다시 실행하고, 그 밖의 root 코드·설정·문서 변경은 package source를 exact gitlink로 준비한 뒤 root pytest와 보안·layout·문서 링크·구버전 설정 변환·manifest 검사를 모두 다시 실행한다. 두 경우 모두 unchanged package의 native/Node/Python suite는 반복하지 않는다. Package gitlink나 검증 owner가 바뀌었거나 증적이 없거나 만료·불완전하면 자동으로 full source/package 검증으로 돌아간다. Full package lane은 서로 격리된 네 worker로 실행하며 scripts/check.py log에는 각 gate와 전체 소요시간을 남긴다.

    tag deploy branch
    v2026.08.04.1 main

    주의

    branch/tag 매칭

    동시 실행과 최신성 보호¶

    canonical vYYYY.MM.DD.N tag 한 건에서 source 계약과 build/publication은 서로 다른 job이다. Source job이 성공하고 뒤 build·stage·publish job만 실패했다면 GitHub의 Re-run failed jobs를 사용한다. 이 경우 성공한 source job은 다시 실행하지 않는다. self-hosted runner는 private worktree를 매번 exact gitlink로 다시 만들지만 LFS object는 repository URL과 OID로 구분한 0700 content cache에서 먼저 복원하고 git lfs fsck 후 사용한다. 따라서 첫 실행만 큰 binary를 내려받으며, cache 손상은 exact ref를 다시 fetch해 복구한다. 이 cache의 hardlink와 checkout object가 같으면 검증한 521MB payload를 cache로 다시 복사하지 않는다. deploy repo의 Git object도 전용 release runner의 0700 bare cache에서 재사용하되, branch와 tag는 매 run read-only key로 강제 fetch한다. 빈 cache는 SHA256과 Git bundle 검사를 통과한 직전 local staging checkpoint로 seed할 수 있으며 checkpoint 자체를 최신 ref의 권위로 사용하지 않는다. 같은 SSH credential 경계 안의 GitHub 연결은 private control socket으로만 재사용하고 key cleanup 전에 master 연결을 닫는다. pip와 npm도 lock file 기반 cache를 사용한다. branch push release job은 기본 skip한다. workflow 전체는 전역 concurrency와 cancel-in-progress: false로 직렬화한다.

    Harbor의 package component 조회와 release alias 생성은 package별 독립 작업을 최대 네 개 병렬로 수행한다. 최종 deploy artifact에서 서로 독립적인 image manifest 존재 확인도 최대 여섯 개를 병렬로 조회한다. build가 실제 필요한 경우에도 이 상한을 유지해 release runner와 registry를 무제한 점유하지 않으며, 하나라도 실패하면 전체 단계가 실패한다.

    source tag 목록은 private package hydration과 분리된 짧은 read-key step에서 run-scoped cache로 한 번 조회하며, lightweight/annotated tag를 모두 commit SHA로 정규화한다. 이 조회가 실패하면 no-op으로 간주하지 않고 즉시 실패한다. deploy repo 상태 확인 단계에서는 source repo의 현재 release tag가 아직 이 run의 GITHUB_SHA를 가리키는 release pair만 pending list에 남긴다. release image alias 생성과 deploy repo atomic push 직전에도 cache를 갱신해 같은 조건을 다시 확인한다.

    자동 push 이벤트에서 이미 더 새 source commit으로 tag가 이동했으면 해당 release pair는 notice를 남기고 건너뛴다. 이 guard는 오래된 run이 늦게 끝나면서 불필요한 build를 계속하거나 Harbor release image tag, deploy repo branch/tag를 이전 source 기준으로 덮는 상황을 막기 위한 장치다. 수동 workflow_dispatch는 과거 release 재생성이 의도일 수 있으므로 이 최신성 guard를 강제하지 않는다.

    최신성 guard의 공통 구현은 scripts/release/ci-release-helpers.sh의 source_release_is_current_or_skip이다. tag 없음·이동은 stale event로 건너뛰지만 tag inventory 조회 오류는 workflow 오류로 분리해 fail-closed한다.

    SBOM·provenance 보증 범위¶

    scripts/release/generate-supply-chain-evidence.py는 package-lock.yaml의 Furive package/component와 image-digests.yaml의 모든 immutable OCI image를 release subject로 만든다. Provenance에는 source commit, workflow ref, run ID, runner environment와 image digest가 들어간다. supply-chain.json은 각 증적의 SHA-256을, manifest.json은 다시 index의 SHA-256을 고정한다. Build job의 artifact 검증과 sign_and_publish job의 source-free stdlib validator가 descriptor hash, unique immutable image subject, SPDX documentDescribes·container download/checksum map과 in-toto/SLSA source·release·branch·architecture· workflow·runner·builder invocation을 다시 확인하므로 누락되거나 바뀐 증적은 게시하지 않는다. Plan의 repository/source SHA/run ID/run attempt도 protected handoff에 결박한다. 다만 run_attempt는 provenance schema 자체에 아직 들어가지 않고 generator와 byte-for-byte deterministic export 비교도 하지 않는다. 따라서 “signer가 generator의 모든 의미를 독립 재현한다”고 주장하지 않는다.

    이 SBOM은 release가 선택한 component와 image digest 수준이다. OCI image 항목은 filesAnalyzed: false이고 index는 다음 범위를 명시한다.

    {
  "deep_image_file_inventory": false,
  "deep_image_inventory_owner": "registry-scanner"
}

    따라서 image 내부 OS package·language dependency·파일 목록과 CVE 판정은 현재 증적에 포함되지 않는다. Harbor scanner가 각 digest의 deep SBOM/SCA 결과를 만들고 severity 차단, 예외 승인, scanner DB 시각과 결과 보존을 release run에 연결해야 이 잔여 위험을 닫을 수 있다. 현재 provenance도 pipeline이 자체 생성한 build 증적이며 독립 제3자 attestation이나 특정 SLSA level 인증을 뜻하지 않는다.

    Source Unlock으로 차량에서 대체한 local checkout은 CI가 빌드·고정한 immutable subject가 아니다. Release metadata가 package 선택과 override 상태를 보고하더라도 그 local source 내용·build output은 signed release, SBOM과 provenance의 운영 보증 범위에서 제외한다. 그런 차량은 개발/진단 상태로 분류하고 공식 release 증적과 섞지 않는다.

    차량용 Docker package는 정적 manifest 검사에서 multi-stage final image의 원본 source copy를 차단하고 io.furive.runtime.source-confidential=1 metadata를 요구한다. Release workflow는 각 package image를 실제 build한 뒤 같은 label을 local image에서 읽어 Harbor push 전에 확인한다. 이는 빌드 과정에서 source를 사용하되 최종 runtime image에는 실행 결과만 남기는 경계다. 현재 검사는 image의 모든 파일을 분류하는 deep inventory가 아니며 binary, bytecode와 JavaScript bundle의 역공학 가능성을 없애지 않는다. Source Unlock으로 명시적으로 제공하는 Git checkout은 이 검사 대상이 아니다.

    온라인 하위 서명키의 현재 운영 결정¶

    게시자 서명의 첫 단계에서는 offline root가 승인하고 회전할 수 있는 온라인 subordinate release 서명키만 GitHub의 protected Environment Secret에 임시 보관한다. Workflow의 격리 서명 job과 차량의 pinned-root 검증 경로는 구현됐지만, 실제 offline root·온라인 인증서·운영키, production-signing Environment 보호 설정과 fleet trust-root 배포는 아직 구성 완료로 확인되지 않았다. 따라서 보안 보증 기준의 SEC-04는 계속 부분 충족이다.

    Secret FURIVE_RELEASE_SIGNING_PRIVATE_KEY
    허용 키 폐기·회전할 수 있고 release 서명에만 쓰는 온라인 하위키
    잔여 위험 HIGH — export 가능한 CI private key를 탈취하면 안전 삭제 증적 또는 KRL 폐기 전까지 정상 게시자로 위장 가능
    금지 GitHub Actions vars, repository/organization-wide secret, offline root 개인키, base64를 암호화로 취급하는 것
    검토 기한 2026-11-08 또는 첫 외부 production normal OTA/ISO readiness review 중 먼저 오는 시점
    단일 정책 소유자 release identity/OTA 검증 계약. CI는 검증된 대상의 서명 동작만 수행

    Self-hosted release job은 source, submodule, package build.sh와 container build를 실행한다. Source/submodule key는 private hydrate step, deploy read-only key는 remote fetch step에서만 사용하고 삭제해 이후 package build에 전달하지 않는다. Source hydrate step은 fixed PATH, 빈 shell/loader env, system/global Git config 차단, core.hooksPath=/dev/null, 빈 credential helper, local SSH/extraheader 제거와 clean submodule repository를 강제한다. 다만 같은 runner의 앞선 code가 background process나 오염 상태를 남길 수 있고 이후 Harbor push credential·Docker socket을 사용하므로, credential을 실행 package code와 완전히 격리한 ephemeral runner 증적은 아직 없어 HIGH 잔여 위험이다.

    검증된 commit과 publication plan은 bounded Git bundle로 넘긴다. Secret이 없는 GitHub-hosted validate_publication job이 exact source policy를 먼저 검사하고, 별도 sign_and_publish job만 production-signing Environment와 push key를 받는다. Protected job에는 source checkout·repository Python/module·dependency install이 없고 inline stdlib가 identity, ref lease, manifest, SBOM와 provenance의 bounded 핵심을 다시 검사한다. Source transition receipt는 서명 뒤 contents: read 전용 validation과 checkout 없는 contents: write 전용 recording job으로 나눈다. 회귀 계약은 protected job 전체에 checkout, GITHUB_WORKSPACE, scripts/, sys.path, core import가 없고, 개인키가 build/receipt job에 없으며 exact ref lease로 원자 게시되는지 확인한다. 완전한 generator/validator 동등성은 별도 pinned validator 또는 KMS API와 mutation corpus로 닫아야 한다.

    과거 v2 서명 계약 이전에 설치된 unsigned main artifact에서 처음 한 차량 test로 넘어가는 경우만 기존 generation receipt 안의 내부 legacy_baseline_attestation을 사용한다. Generation receipt가 아직 하나도 없고 등록 차량 preview가 정확히 한 개일 때, production-signing required reviewer가 승인한 protected job이 main HEAD와 기존 canonical tag, manifest SHA, source commit/tag object, package·external· image lock SHA와 immutable image ID, OTA generation을 다시 확인한다. 확인한 digest는 preview manifest와 normal principal로 서명하는 generation tag message 양쪽에 결박한다. 이후 preview와 normal은 이 exact signed generation receipt만 재사용하며 unsigned 예외를 다시 열지 않는다. 이 절차는 기존 설치판의 identity를 1회 서명 증명하는 bootstrap attestation일 뿐 build 성공, 기능 동작 또는 실차 QA 증거가 아니다. Source와 deploy는 서로 다른 repository라 두 ref를 하나의 Git transaction으로 잠글 수 없으며, protected signer는 source tag를 게시 직전 다시 확인하고 deploy refs만 atomic lease한다. 따라서 source tag 보호 규칙과 workflow run의 수동 승인 기록도 release 증적에 반드시 포함한다.

    validate_transition_receipt는 production-signing Environment와 source write token 없이 exact source SHA를 credential 비지속 방식으로 checkout하고, read-only deploy key와 root/KRL로 원격 signed receipt· branch head·canonical ancestry를 재검증한다. Root/KRL을 Environment에만 두면 이 job은 빈 값으로 실패한다. 실제 GitHub secret scope와 signing/validation job의 root/KRL fingerprint 일치는 local checkout에서 확인할 수 없으므로 최초 release 전에 운영 증적으로 남긴다.

    별도 record_transition은 checkout, repository module, deploy key, root/KRL, signing private key, deploy write key와 protected Environment가 없다. 앞 job의 크기 제한 receipt를 Python stdlib로 다시 검사하고 exact repository/run/source SHA에 결박된 legacy-transition-v2-published tag만 GitHub API로 create-only 기록한다. 이 구조에서는 reviewed source/deploy read credential과 source contents: write token이 같은 job에 존재하지 않는다. Workflow/ruleset 변경 승인과 job output provenance는 별도 운영 증적으로 확인한다.

    첫 사용 전에 다음 조건을 모두 충족해야 한다.

    1. build/검증 job과 sign_and_publish job의 분리를 유지한다. 후자는 검증된 deploy commit/tree와 release identity만 입력받고 source/submodule checkout, package code, dependency install 또는 build를 실행하지 않는다.
    2. 서명 job은 environment: production-signing과 별도 ephemeral signing runner를 사용한다. Environment에는 required reviewer, self-review 금지, canonical release tag 제한과 최소 권한을 적용한다. 같은 self-hosted build runner 재사용은 격리로 인정하지 않는다.
    3. 차량은 후보가 제공한 키가 아니라 trusted bootstrap이 host에 고정한 root/allowed signer로 서명을 staging 전에 fail-closed 검증한다. key ID, 용도, release 범위, artifact 보존 horizon과 폐기 상태도 서명 계약에 포함하고 activation 직전에 다시 검증한다. OpenSSH가 현재 시각으로 immutable tag를 검증하므로 artifact 인증서는 -5m:forever archival validity만 허용하며, protected signer가 유한 만료 인증서를 거부한다.
    4. 서명은 모든 image digest와 metadata hash가 확정된 뒤, atomic publish 전에 수행하고 같은 job에서 즉시 검증한다. 개인키는 step-local mode 0600 임시 파일 외에 log, cache, artifact와 $GITHUB_ENV에 기록하지 않는다. set -x를 사용하지 않고 job 종료 후 runner 폐기 증적을 남긴다.
    5. Environment 보호 설정, 승인자, workflow run ID, source/deploy commit, tag, artifact digest, signer key ID·public fingerprint와 서명 검증 결과를 release 증적으로 보관한다. secret 값과 개인키는 어떤 증적에도 포함하지 않는다.

    키 노출이나 비정상 서명이 의심되면 발행을 중단하고 online key를 폐기한 뒤 영향 release를 식별한다. 검증되지 않은 새 키로 자동 fallback하지 않으며 last-known-good 또는 trusted bootstrap 복구만 허용한다. offline root 개인키는 이 임시 경로를 포함해 어떠한 CI에도 넣지 않는다.

    이 임시 키의 잔여 위험은 HIGH다. 종료 조건은 차량이 offline root 공개키를 고정하고 root가 승인한 자주 교체되는 online private key의 범위·archival certificate·폐기를 검증하며, 온라인 키를 KMS/HSM 안에서 non-exportable로 생성·사용하고 CI가 정확한 repository/workflow/ref/Environment에 결박된 GitHub OIDC 단기 identity로 서명 API만 호출하도록 전환하는 것이다. Offline root의 hardware-backed 보관·이중 통제와 build/sign 격리, 키 회전·폐기 복구 훈련까지 확인한 뒤 GitHub secret과 runner 잔존물을 삭제해야 export 가능한 온라인 키 부채가 닫힌다.

    공통 release channel과 architecture, normal_platform_targets 승인 세대는 config/deploy-targets.yaml에 둔다. 차량별 profile/channel/release 할당은 config/fleet-vehicles.yaml, 고객/package 선택은 config/capability-profiles.yaml에서 관리한다. release artifact는 모든 profile에 필요한 package manifest/image lock을 포함하지만 차량 ID는 포함하지 않는다. 기본 release tag는 main의 vYYYY.MM.DD.N 하나다. main 병합 전 단일 차량 검증만 등록된 preview/<vehicle_id>와 vYYYY.MM.DD.N-preview-<vehicle_id>를 허용하며, CI는 다른 임의 suffix/branch를 무시한다.

    normal은 플랫폼별 branch나 별도 artifact를 만들지 않는다. CI는 승인 세대의 모든 플랫폼을 ota-platform-target-g<세대>-<release>-<플랫폼>-approved 서명 tag로 한 atomic push에 포함한다. release 값은 해당 세대를 처음 게시한 공용판에 영구 결박되고, 같은 세대로 뒤의 공용판을 발행해도 움직이지 않는다. 한 플랫폼을 승격할 때는 세대를 정확히 1 올리고, 시험을 통과한 플랫폼은 release, 나머지는 마지막 exact release를 적으며 모든 capability profile을 다시 명시한다. 누락, 같은 세대의 상충 tag, 세대 replay, 서명·canonical release commit·capability 불일치는 발행과 차량 OTA 양쪽에서 fail closed한다. 최초 전환 공용판은 구형 updater가 전역 최신판으로 한 번 받을 수 있으므로 지원 플랫폼 전체에서 안전한 버전이어야 한다. 이 전환 뒤에는 각 플랫폼이 독립 승인 속도를 갖는다.

    branch 확장 기준¶

    현재 허용 범위는 공통 main과 차량 목록에 등록된 임시 preview/<vehicle_id>뿐이다. 임의의 고객사 branch나 차량별 영구 branch는 source/deploy 정합성 검사에서 거부한다.

    차이는 다음 순서로 표현한다.

    1. 설치 버전만 다르면 차량의 release_pin을 바꾼다.
    2. 기능이나 추가 package만 다르면 capability와 package 선택을 바꾼다.
    3. 합치기 전 시험만 필요하면 preview/<vehicle_id>를 만들고 시험 종료 후 삭제한다.
    4. 위 세 방법으로 표현할 수 없고 독립 release 일정이 장기간 필요할 때만 고객사/제품 release channel을 추가한다.

    새 장기 channel을 추가하려면 차량 연결, 허용 branch, 배포 대상, 담당자, 공통 수정·보안 패치 반영 방식, OTA upgrade/rollback 검증을 함께 정의해야 한다. 차량 ID 하나를 영구 branch 이름으로 쓰거나 임시 preview를 승격하는 방식은 허용하지 않는다. 이 기준은 branch 수와 CI fan-out이 차량 수에 비례해 늘어나는 것을 막기 위한 운영 규칙이다.

    publish.py normal은 구형 차량용 전환판의 발행 상태를 자동 확인한다. 발행 전에는 설정된 과거 경로를 공용판과 한 번에 발행하고, CI가 모든 전환 artifact의 OTA 검증과 deploy repo 게시를 끝낸 뒤에만 내부 완료 tag를 생성한다. 실패한 run은 tag를 만들지 않으므로 다음 normal 발행이 자동 재시도한다. 완료 후에는 공용 main 하나만 빌드한다. 이 내부 tag는 release 버전이 아니며 차량 운영자가 선택하거나 이동하지 않는다.

    새 호환판·설정 변환 계약을 기존 차량에 다시 전달해야 할 때는 이전 발행 receipt를 재사용하지 않는다. 현재 v2 전환은 별도 receipt를 사용하므로 첫 furive release normal ... --run 계획에 과거 여섯 경로가 다시 포함된다. 이 일회성 범위는 release 내부 계획과 CI가 소유하며 일반 furive release 요약에는 별도 사용자 개념으로 표시하지 않는다. 사람이 개입해야 하는 차단 상태만 오류로 보고한다. Receipt는 모든 역사 OTA 검증과 atomic deploy 게시 뒤 CI만 만든다. Receipt가 생겨도 legacy_transition.enabled가 true이면 다음 normal 발행은 차단된다. 지원 대상 차량의 epoch2 수렴 또는 bootstrap 복구가 fleet inventory로 확인된 리뷰 변경에서만 이 값을 false로 바꾼다.

    고객사·차량별 버전 상태 계약¶

    모든 차량은 기본적으로 공통 main channel을 따라간다. 실제 SW 버전은 CI 성공 후 발행된 canonical immutable tag와 manifest/digest lock이다.

    필드 기준
    customer, vehicle_id, capability_profile 설치 시 생성된 차량 active config
    release_pin 차량 active config의 선택적 목표 tag. 비어 있으면 normal은 플랫폼 승인판, test는 해당 차량 최신판
    channel, release_profile 기본 main; 임시 검증 때만 등록된 preview/<vehicle_id>
    installed_release 현재 checkout의 deploy release tag/manifest
    desired_release release_pin이 있으면 고정 tag, 없으면 normal은 설치 플랫폼의 최고 서명 승인 세대가 가리키는 release
    pending_release staging까지 준비된 다음 release
    rollback_release rollback pin 또는 last-known-good 이전 release
    state, drift_reasons current/update_available/pending/drift와 branch/profile/tag 불일치 원인

    deploy 버전 검색 규칙¶

    OTA updater는 원격 furive-os-deploy tag 가운데 현재 channel과 suffix가 일치하고 해당 원격 branch에서 도달 가능한 tag만 버전 목록에 넣는다. normal은 설치 플랫폼의 최고 signed generation target이 가리키는 suffix 없는 canonical tag를 선택한다. preview/<vehicle_id>는 정확히 같은 -preview-<vehicle_id> tag, 과거 전환 deploy/<family>/<target>은 해당 target suffix tag만 허용한다.

    허용 tag는 CalVer의 연·월·일·revision을 숫자로 비교한다. release_pin이 없으면 normal은 플랫폼 승인 tag의 release, test는 해당 차량의 가장 큰 tag가 desired_release가 된다. release_pin이 있으면 형식, 원격 존재 여부, branch 연결성을 모두 검증하고 불일치 시 fallback하지 않는다. CI가 OTA와 artifact 검증을 끝내지 못한 release와 승인 세대는 deploy repo에 원자 게시되지 않으므로 차량 목표에도 노출되지 않는다.

    일반 자동 업데이트는 target > current일 때만 허용한다. updater는 HEAD에 tag가 여러 개 있어도 현재 channel과 맞는 tag 전체를 수집한 뒤 가장 높은 tag를 현재판으로 선택한다. 첫 원격 fetch 전에는 오래된 remote-tracking ref를 최신판으로 노출하지 않으며, target <= current인 staging은 상태 응답에서 숨기고 update cycle·수동 적용·부팅 전환 시점에 폐기한다. 명시적 release_pin 또는 last-known-good rollback만 이 자동 하향 차단의 예외다.

    tag는 버전 검색 키이고 실제 내용 식별은 manifest와 image digest lock이 담당한다. 차량은 선택된 tag의 release/manifest.json, package lock, digest lock 무결성이 맞지 않으면 정상 release로 취급하지 않는다.

    고정 GitHub Ed25519 host key와 signed tag는 server/publisher identity를 검증하지만 최신 release가 숨겨지지 않았다는 freshness 증명은 아니다. 현재 fresh bootstrap과 원격 목록에는 root-owned monotonic minimum 또는 외부 transparency ledger가 없어 오래된 정상 signed view의 freeze를 탐지하지 못한다. Fleet minimum을 운영 gate로 두고 차량의 monotonic floor·독립 ledger를 추가하기 전에는 rollback resistance가 완성됐다고 주장하지 않는다.
