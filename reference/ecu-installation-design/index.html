    ECU 연산 분리와 단일 설치 묶음 설계¶

    이 문서는 A-ECU의 자율주행 연산을 보호하면서, 차량 설치 묶음과 사용자 용어를 단순하게 만드는 설계 기준이다. 설치·실행 코드 변경 시 이 결정을 따른다.

    상태: source 구현, 배포·실차 검증 전. 단일 묶음 생성, 신규 PC 선택, 기존 배정 유지와 주요 CLI·대시보드 장비 표시를 구현했다. 새 계약을 포함한 signed deploy release가 있어야 단일 묶음을 생성할 수 있다. 기존 배포 버전에서 전달한 역할별 묶음도 계속 지원한다. 설치 절차는 차량 PC 설치와 bootstrap 설치 흐름을 따른다.

    1. 목적과 장비의 책임¶

    가장 중요한 목적은 데이터 로깅 등 부가 패키지의 연산·메모리·디스크 부하와 장애가 자율주행에 미치는 영향을 줄이는 것이다. 전달 파일을 하나로 합쳐도 ECU별 실행 경계는 유지한다. 물리적 PC 분리만으로 자율주행 안정성이 보장되지는 않으며, 데이터 전달과 장애 의존성도 검증한다.

    사용자에게 보이는 장비 담당 기능 기본 동작
    A-ECU — 자율주행 PC 자율주행, 기본 운영 대시보드, 차량 전체 상태·업데이트 조정 신규 설치의 기본 선택. 지원하는 단독 구성에서 한 대로 운용 가능
    HMI-ECU — 데이터 로깅·부가 기능 PC 데이터 로깅과 해당 플랫폼이 배정한 부가 패키지 별도 PC에 설치하여 A-ECU의 부하를 분담

    HMI-ECU라는 이름이 운영 대시보드의 소유권을 뜻하지 않는다. A-ECU 단독 설치가 일반적인 사용 경로이므로 기본 운영 대시보드는 A-ECU에 남긴다. HMI-ECU를 추가해도 대시보드나 운영 통제권을 자동으로 옮기지 않는다. HMI-ECU에서 실행할 구체적인 화면·기능은 플랫폼의 패키지 배정을 따른다.

    1PC 함께 설치하기와 분산 배정¶

    PC 한 대에 자율주행·기본 운영과 부가 패키지를 함께 설치·실행할 수 있다. A-ECU·HMI-ECU로 나누는 분산 엣지 컴퓨팅은 자율주행 연산과 로깅 등의 부하를 분리하기 위한 권장 배치이며, Furive OS 자체의 최소 PC 수가 두 대라는 뜻은 아니다. 1PC에서도 패키지는 독립 프로그램으로 남고 공통 실행 관리자를 사용한다.

    배치 설치와 실행 자원·장애 경계
    1PC A-ECU 역할의 한 설치에 필요한 패키지를 함께 배정 자율주행·화면·녹화가 같은 CPU·GPU·메모리·디스크를 공유
    분산 A-ECU와 HMI-ECU에 각각 배정된 패키지를 설치 로깅·업로드 등의 부하를 별도 PC로 분리; PC 간 전송 부하는 별도 확인

    현재 구현과 배포 범위는 다음처럼 구분한다.

    1. core/capability_profile.py는 기존 플랫폼의 node_configs.master.packages 등으로 실행 목록을 해석한다. nodes/master.py는 이 목록에 명시된 부가 역할 전용 패키지가 있으면 발견 범위를 확장한다. 한 PackageManager가 의존성과 함께 시작하므로 같은 PC에 두 역할의 서비스를 중복 설치할 필요가 없다.
    2. 현재 master.default.yaml과 lotte-ohmio의 A-ECU 목록에는 HMI·DLS가 포함되어 있지 않다. 기본 A-ECU 설치만으로 모든 부가 기능까지 설치됐다고 안내하지 않는다. 한 PC에서 함께 쓸 패키지, 장치·DDS 환경·화면·포트와 의존성은 플랫폼 담당자가 기존 구성에서 명시하고 검증한다.
    3. 1PC 로깅은 그 PC에 배정된 DLS 화면과 로컬 ROS 환경을 사용한다. 현재 furive topic의 중앙 전달 변경 및 녹화·검사 요청은 연결된 수신 PC 한 대를 대상으로 한다. 패키지 동시 실행 지원을 모든 원격 운용 명령의 1PC 지원으로 확대해 설명하지 않는다.
    4. 차량 배포의 패키지 배정을 바꾸면 기존 deploy 소유자에서 release를 만들고 그 버전으로 bundle을 만든다. 설치 ZIP의 목록을 고치거나 A-ECU 설치 위에 HMI-ECU 설치를 덧씌우지 않는다.

    단독 구성은 지원 플랫폼의 실제 필수 장치·기능 조건 안에서 성립한다. 위 발견·배정 코드 경로는 모든 패키지 조합의 동시 실행 성능이나 실차 검증을 뜻하지 않는다. HMI-ECU가 필요한 차량 기능을 생략하거나, 부가 PC가 없을 때 패키지를 A-ECU에 자동 재배치하지 않는다.

    2. 사용자 이름과 공통 코드의 정합성¶

    사용자는 설치할 장비 이름과 하는 일만 이해하면 된다. 일반 설치 화면·대시보드·사용자 문서는 해당 차량의 장비 이름을 일관되게 사용하고 main/edge 대응표를 온보딩에 추가하지 않는다. 설치 후 furive status, furive service, furive dashboard 등은 기존 설치 배정을 자동으로 사용한다.

    현재 대상 구성의 장비 운영 역할 기존 config/API 호환 이름
    A-ECU main: 차량 전체 조정과 로컬 실행 master
    HMI-ECU edge: 배정된 기능의 로컬 실행과 상태 보고 agent

    이 표는 개발자를 위한 현재 구성의 대응이다. 운영 역할은 공통 코드가 다루고, 실제 장비 이름과 패키지 배정은 기존 플랫폼·차량 구성 경계에서 정의한다. 모든 차량이 같은 ECU 이름이나 두 대의 PC를 가진다고 공통 코드에 고정하지 않는다. 화면마다 별도의 이름 변환표를 만들지 않는다.

    현재 CLI의 main/edge 인자와 기존 config/API는 호환을 유지하며 단계적으로 사용자 노출을 줄인다. 문서만 바꿔 존재하지 않는 A-ECU CLI 인자를 안내하지 않는다. 기존 내부 역할을 전면 개명하거나 peer라는 새 공개 개념을 도입하지 않는다. 런타임 코드 통합은 실제 중복을 줄이는 범위에서만 한다.

    정합성은 이름이 모두 같은지가 아니라, 선택한 장비와 설치 역할·패키지 배정·인증 신원·상태 표시·OTA 대상이 일치하는지로 확인한다. 내부 역할을 유지한다는 이유로 서로 다른 매핑을 허용하지 않는다.

    3. 목표 설치 흐름¶

    배포 담당자는 기존 furive bundle <차량-ID>로 차량용 설치 묶음 하나를 만든다. 설치자는 각 PC에 같은 묶음을 전달하고 ./bootstrap.sh를 실행한다. 한 PC에서 실행하면 다른 PC까지 원격 설치하는 기능은 이 설계 범위에 포함하지 않는다.

    새 PC에서는 장비 선택을 먼저 제공한다. 읽기 전용 사전 확인으로 기존 설치가 확인되면 그 배정을 사용하고 신규 선택 화면을 건너뛴다. 선택 화면은 플랫폼에서 받은 장비 이름을 사용한다.

    지금 설치하는 PC는 무엇인가요?

  > 1. A-ECU [기본]
       자율주행·운영 대시보드
    2. HMI-ECU
       데이터 로깅·부가 기능

장비 라벨을 확인하세요. ↑/↓: 이동, Enter: 선택, q: 취소

    이 예시는 단독 운용을 지원하는 현재 대상 구성의 문구다. 선택지는 차량의 지원 구성에서 가져오고, 지원하지 않는 장비를 표시하거나 단독 운용을 보장하지 않는다. 실제 장비 라벨과 같은 이름을 쓴다.

    1. 신규 설치: A-ECU를 기본 선택한다. 대부분의 설치자는 Enter로 진행하고, HMI-ECU에서는 위·아래 방향키로 선택을 바꾸고 Enter로 확정한다. 최초 PC 선택은 일반 경로에서 허용하는 하나의 구성 질문이다.
    2. 계획 확인: 선택한 장비와 설치 영향을 기존 계획·승인 화면에 함께 표시한다. 기존 호스트 변경 승인을 유지하되 장비 선택 확인용 질문을 추가로 쌓지 않는다.
    3. 자동 적용: 차량·플랫폼·버전·패키지를 다시 묻지 않는다. 선택에 대응하는 검증된 배포 구성을 적용하고 기존 설치 상태가 PC 배정을 소유한다.
    4. 자동 시작: 서비스와 해당 PC에 배정된 운영 화면을 기존 자동 시작 정책에 따라 시작한다. 단독 구성의 A-ECU는 HMI-ECU 연결을 기다리며 설치를 막거나, 그 부재만으로 장애를 표시하지 않는다.
    5. 재실행·재부팅·업데이트: 저장된 배정을 이어받는다. HMI-ECU에서 A-ECU 기본값이 다시 적용되면 안 된다. 불일치는 중단하고 명시적인 역할 변경 절차로 안내한다.

    설치 표식이나 서비스 등록이 생기기 전에 첫 설치가 중단됐다면 아직 저장된 PC 배정이 없으므로 다시 실행할 때 장비를 선택한다. 이 경우도 입력 없이 기본값을 자동 적용하지 않는다. 기존 배정 조회 자체가 실패하면 설치를 중단한다. 조회 오류를 설치 기록이 없는 신규 PC로 처리하지 않는다.

    GPU 유무, 연결된 모니터, IP 주소나 부팅 순서로 PC 역할을 추측하지 않는다. 사전 장비 식별 등록은 일반 설치의 필수 조건으로 추가하지 않는다. 비대화형 설치는 확정된 대상이나 기존 설치 상태를 사용하며, 입력이 없다는 이유로 신규 PC에 A-ECU를 무조건 설치하지 않는다. 역할 변경은 일반 재설치와 구분하고 필요한 예외 선택만 기존 --customize 경계에서 다룬다.

    4. 연산·장애 분리 규칙¶

    • A-ECU에는 자율주행과 단독 운용에 필요한 패키지를 배정한다. 부가 패키지를 공통 기본값에 계속 추가하지 않고 플랫폼별 목적과 실행 위치를 검토한다.
    • HMI-ECU가 없거나 중지되어도 그 패키지를 A-ECU에 자동 이동시키지 않는다.
    • 녹화·외부 전송 소비자의 처리 지연, 저장공간 부족이나 재시작이 자율주행 생산자의 실행을 동기적으로 기다리게 하지 않도록 데이터 경계를 설계한다.
    • 통신·기능의 기존 소유자가 큐 상한, 전송량, 데이터 누락·버퍼 포화 시 행동을 필요한 범위에서 정한다. 공통 역할 계층에 별도의 녹화 상태나 재시작 loop를 만들지 않는다.
    • PC 간 데이터 전송이 A-ECU에 만드는 CPU·메모리·네트워크 부하도 확인한다. 무거운 처리를 다른 PC로 옮겼다는 사실만으로 영향이 없다고 판단하지 않는다.
    • 연결 단절 시 계속할 기능과 중지할 기능은 해당 기능의 기존 정책이 소유한다. 안전에 필요한 필수 기능의 상실을 단순한 부가 PC 단절로 숨기거나, 모든 단절에 같은 중지 규칙을 적용하지 않는다.

    자동 통제권 인계, 리더 선출, 동적 패키지 스케줄러는 도입하지 않는다. 각 PC의 PackageManager는 계속 로컬 실행을 담당하고, 차량 전체 운영 조정은 현재 A-ECU의 역할에 남긴다.

    5. 정책의 단일 소유자¶

    결정할 내용 기존 소유자와 수정 위치
    장비 이름·역할 대응, 플랫폼별 패키지 배정 core/fleet_assignment.py, core/capability_profile.py, config/capability-profiles.yaml, config/fleet-vehicles.yaml
    장비 선택 해석·설치 배정 확정·재실행 처리 install.sh, core/installer/, 공개 CLI 연결은 core/cli.py
    묶음 전달과 기존 signed release 선택 scripts/create-credential-bundle.sh, scripts/credential-bootstrap/
    PC 등록·신원과 상태 보고 기존 node 인증 계약, nodes/master.py, nodes/agent.py
    패키지 발견·로컬 실행·health core/package_discovery.py, core/package_manager.py
    Autoware lifecycle core/launcher_control.py, package/core/furive-launcher
    업데이트 목표·순서·검증·복구 core/ota_policy.py, core/self_updater.py, package/core/ota-updater
    사용자 장비 이름·상태 표시 CLI와 Dashboard가 기존 배정 정보를 표시

    묶음은 선택 가능한 구성을 전달할 수 있지만 패키지·플랫폼·지속 실행 상태를 별도로 결정하지 않는다. 장비 선택의 정책과 검증은 기존 deploy 설치 소유자에 두고 bootstrap은 그 계약에 연결한다. 현재 구현은 기존 node_name·node_id와 설치 표식·서비스 등록을 재사용한다. 장비 이름을 보관하는 새 config field나 영구 상태 파일은 추가하지 않았다. core/fleet_assignment.py가 PC 선택과 기존 배정 확인을 소유하며, 그 파일을 signed deploy에서 그대로 가져와 묶음의 installation-policy.py로 전달한다. 별도 wrapper나 bundle 전용 정책 구현이 아니며 배포 검증 단계에서 원본과 바이트를 비교한다.

    전달 계약은 기존 고정 역할의 v2/v3과 구분하여 bundle.env v4를 사용한다. 이때 MODE와 NODE_ID의 select는 설치 전 전달 표식일 뿐 runtime 역할이 아니다. 기존 manifest.yaml에 PC 선택 목록을 서명된 플랫폼 설정의 영수증으로 포함하고, 새 별도 매핑 파일은 만들지 않는다. 초기 PC 선택에서 추가 Python 패키지를 설치하지 않도록 이 영수증은 JSON(YAML 호환 형식)으로 기록한다. 필요한 이유는 고정된 한 역할 계약으로 두 PC 선택을 표현할 수 없기 때문이며, 단일 소유자는 기존 차량 배정 코드다. 사용자는 기존 장비 이름 선택 외에 새 옵션이나 파일 형식을 배울 필요가 없다.

    6. 인증·업데이트와 기존 설치 호환¶

    선택된 장비와 인증 역할·node ID가 일치해야 하며, 두 PC에 같은 node 신원을 설치하면 안 된다. 현재 통합은 설치 담당자가 두 PC의 인증 자료를 관리하는 기존 신뢰 범위를 사용한다. 단일 묶음의 node-identities/master/, node-identities/agent/에 서로 다른 키와 상대 인증서를 두고 선택한 PC의 자료만 기존 /etc/furive-os/node-identity에 설치한다. 공용 자료와 bootstrap은 하나만 둔다.

    단일 묶음과 압축 해제본에는 두 PC의 개인키가 있으므로 민감한 설치 자료로 관리하고 설치 뒤 정리한다. 장비 선택은 운영 경로에 적용할 신원을 정하며, 설치 묶음에 접근 가능한 사람으로부터 상대 키를 격리하지 않는다. 묶음 자체에서도 장비별 키 접근을 분리하려면 별도의 장비 인증 또는 전달 절차가 필요하며, 이번 구현은 그 보장을 제공하지 않는다. 두 역할의 인증서·개인키 일치와 상대 신원 확인은 기존 설치 인증 검증을 계속 사용한다.

    기존 역할별 묶음과 설치 상태는 계속 읽을 수 있어야 한다. 사용자 표시명을 바꿨다는 이유로 인증서, 설치 역할이나 서비스 이름을 자동 교체하지 않는다. 설치 기록과 전달 대상이 충돌하면 적용 전에 멈춘다.

    각 PC는 상대 PC가 아직 설치되지 않았어도 자기 설치를 마칠 수 있어야 한다. 차량 전체 기능의 준비 여부는 로컬 설치 성공과 구분한다. 운영 중 업데이트는 기존 OTA가 각 PC의 정확한 목표와 적용 결과를 관리하고, 일부 PC만 성공한 경우도 기존 호환성·복구 정책에 따라 처리한다. 묶음에 별도 OTA 정책을 만들거나 여러 PC의 동시·원자적 업데이트를 보장한다고 표현하지 않는다.

    7. 구현 순서와 완료 기준¶

    순서 작업 확인할 결과
    1 기존 역할·패키지·설치 상태·인증 경로를 기준으로 장비 대응을 정리 표시·설치·실행·인증이 같은 배정을 사용하고 전환용 중복 상태가 생기지 않음
    2 기존 deploy 설치 소유자에 신규 선택과 기존 설치 재사용 계약 구현 신규 A-ECU 기본값, HMI-ECU 선택, 재실행·재부팅 시 배정 유지, 충돌 차단
    3 신원 자료 전달 방식을 확정하고 단일 묶음에 연결 각 PC에 자기 신원만 적용, 기존 역할별 묶음 호환, 상대 PC 없이 로컬 설치 가능
    4 CLI·대시보드·일반 문서의 장비 표시 통일 사용자는 main/edge를 배우지 않고 장비 선택과 일상 운용을 수행
    5 한 차량에서 실행·복구와 부하 분리 확인 단독 운용, 두 PC 연결, 로깅 부하·장애·단절 영향, OTA 일부 실패 처리 확인

    코드 변경 시 작은 테스트를 먼저 실행하고 마지막에 ./furive check를 실행한다. 새 사용자 동작은 tests/contracts/test_user_cli.py, 묶음·설치·인증 동작은 기존 관련 테스트에 회귀 계약을 추가한다. 실차 시험은 로깅 부하·저장공간 부족·연결 단절 전후의 자율주행 처리 지연과 자원 사용을 비교하고, 허용 기준은 해당 지원 플랫폼의 요구에서 정한다. 확인하지 않은 실차 안정성을 달성했다고 기록하지 않는다.

    현재 검증은 합성 인증 자료를 사용한 단일 ZIP 생성·양쪽 PC 선택·상대 인증서 pin·공용 자료 중복 방지, 기존 설치 재사용·충돌·비대화형 입력 차단과 HMI-ECU의 Autoware 이미지·지도 미적용을 포함한다. 실제 설치·systemd 변경·Docker 실행·실차 부하와 복구 시험은 아직 수행하지 않았다. 위 순서의 1~4는 source 구현 범위이며, 5의 실차 안정성은 이 코드 검사 결과로 대체하지 않는다.

    역할 선택·설치 상태 정책이 바뀌므로 단순 포장 변경으로 처리하지 않는다. CI/CD 발행 기준에 따라 deploy release를 먼저 검증·발행한 뒤 그 버전을 사용하는 단일 묶음을 만든다. 이번 source 작업에서 실제 release나 차량 설치 묶음을 발행하지 않는다. 기존 source 개발·자동화의 main/edge 인자와 기술 reference는 호환 이름을 유지한다.
