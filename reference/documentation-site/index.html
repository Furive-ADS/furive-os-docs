    문서 사이트 관리¶

    문서 작성자가 기존 Markdown을 웹사이트로 확인하고 정적 파일로 만드는 방법입니다. 설치·운용 절차는 각 가이드가 맡고, 사이트는 탐색과 표시만 맡습니다.

    미리 보기¶

    source 저장소 루트에서 문서 전용 Python 환경을 한 번 준비합니다. 차량에 설치하는 작업은 아닙니다.

    python3 -m venv .runtime/docs-venv
.runtime/docs-venv/bin/pip install -r docs/site/requirements.txt
.runtime/docs-venv/bin/mkdocs serve --dev-addr 127.0.0.1:8000

    브라우저에서 http://127.0.0.1:8000을 엽니다. Markdown과 스타일을 저장하면 미리 보기가 갱신됩니다. Ctrl+C로 미리 보기를 종료합니다. 문서 도구는 Furive 실행 환경과 분리되어 있습니다.

    사이트 빌드¶

    같은 저장소 루트에서 실행합니다.

    .runtime/docs-venv/bin/mkdocs build --strict
./furive check

    완성된 HTML·검색 색인·화면 이미지는 .runtime/docs-site/에 생성됩니다. 전체 다운로드본은 같은 환경에서 다음 명령으로 만듭니다.

    .runtime/docs-venv/bin/python docs/site/build_offline.py
.runtime/docs-venv/bin/python docs/site/verify.py --offline .runtime/docs-site/downloads/furive-os-docs-offline.zip

    검증에는 Chrome 또는 Playwright Chromium이 필요합니다. Chrome이 없다면 문서 환경에서 python -m playwright install --with-deps chromium으로 준비합니다. 빌드 때 검색·다이어그램 도구를 받을 수 있어야 하며, 완성된 ZIP을 읽을 때는 인터넷이 필요하지 않습니다.

    build_offline.py는 같은 Markdown을 Material의 offline·privacy 플러그인으로 빌드해 로컬 파일 이동과 검색을 지원하고 외부 자산을 묶습니다. ZIP과 SHA-256 파일은 .runtime/docs-site/downloads/에 생성됩니다. 사이트 배포는 ZIP을 압축 해제한 뒤 네트워크를 차단한 브라우저 검증까지 통과해야 진행합니다. 이 폴더를 웹 서버로 제공하면 됩니다. 로컬 빌드는 외부 사이트에 게시하지 않습니다. 공유할 때는 조직에서 정한 문서 호스팅과 접근 권한을 사용합니다. GitBook 계정이나 별도 문서 원본은 필요하지 않습니다.

    GitHub에서 자동 게시¶

    공개 문서 사이트는 누구나 열 수 있습니다. Documentation workflow가 비공개 source 저장소에서 문서를 빌드하고, 생성된 사이트만 문서 전용 저장소에 게시합니다. 이 공개 저장소의 main 브랜치 루트를 GitHub Pages가 제공합니다.

    • 문서·사이트 설정을 바꾼 PR은 빌드와 링크 검증만 수행합니다.
    • 같은 변경이 main에 들어오면 빌드 성공 뒤 Pages에 자동 게시합니다.
    • 문서 외 변경은 문서 배포를 실행하지 않습니다. 필요한 경우 Actions → Documentation → Run workflow에서 main을 선택해 다시 게시합니다.
    • 게시 주소는 완료된 실행의 요약과 공개 저장소의 Settings → Pages에서 확인합니다.

    사이트 주소는 GitHub Pages 설정 한 곳에서 읽습니다. workflow가 빌드에만 FURIVE_DOCS_SITE_URL로 전달하므로 도메인이나 저장소 이름을 문서 설정에 중복 입력하지 않습니다. 로컬 미리 보기에는 이 값이 필요하지 않습니다. 문서 CI는 package submodule과 차량 credential 없이 빌드하며, source 링크는 GitHub 저장소로 연결합니다. 코드를 보려면 원본 저장소 접근 권한이 필요합니다.

    다른 저장소에 게시할 권한은 기본 GITHUB_TOKEN에 없으므로, 문서 저장소에만 쓰기 가능한 deploy key를 사용합니다. 공개키는 문서 저장소의 deploy key, 개인키는 원본 저장소의 Actions secret DOCS_PUBLISH_KEY 한 곳에서 관리합니다. PR 검증에는 이 키를 전달하지 않습니다. 키를 교체할 때 두 등록을 함께 갱신하며 문서나 Git에 개인키를 기록하지 않습니다. 일반 문서 작성자가 새로 입력할 값은 없습니다.

    이 사이트의 본문·화면 캡처·PDF는 공개 자료입니다. docs/를 수정할 때 공개 가능한 내용만 넣습니다. 검수 기록과 원본 코드는 사이트 산출물에 포함하지 않습니다. 공개 저장소의 HTML을 직접 고치면 다음 자동 게시에서 덮어쓰므로, 수정은 원본 Markdown에서 합니다.

    어디를 고치는가¶

    바꾸려는 것 원본
    첫 화면의 안내·바로가기 문서 홈
    작업 순서와 화면 설명 docs/guides/의 해당 Markdown
    상세 규칙 docs/reference/의 해당 Markdown
    왼쪽 메뉴·검색·테마 설정 mkdocs.yml
    색상·여백·모바일 화면 styles.css
    홈·제품 소개의 개념 일러스트 docs/assets/home/
    제품 소개의 저장소 연결·배포·검증 흐름 operating-flow.svg
    패키지·플랫폼·ECU 개념 구조도 system-map.svg
    명령어 검색·복사·캡처 확대 docs/site/interactions.js
    홈의 단계 선택·등장 효과 docs/site/interactions.js, docs/site/styles.css
    문서 위치와 다음 단계 docs/site/overrides/main.html, 각 문서의 next_steps
    실행·설치 흐름도 해당 문서의 Mermaid 코드 블록

    새 문서를 만들면 mkdocs.yml의 해당 메뉴에 한 번 등록합니다. 문서 링크는 기존처럼 상대 Markdown 경로를 사용합니다. 웹 빌드가 HTML 주소로 바꿉니다. 저장소 코드·개발 계약을 가리키는 링크는 빌드 때 GitHub의 main 소스로 연결되므로 저장소 접근 권한이 필요할 수 있습니다. 이 변환은 docs/site/hooks.py 한 곳에서 담당합니다.

    문서 구성¶

    문서 홈과 README는 제품 정의·장점 → 구체적인 사용 예시 → 사용 시작 순서로 안내합니다. 쓰던 GitHub 저장소에서 개발한 프로그램과 Autoware를 지원 차량에 연결하고 설치·실행·상태·업데이트를 관리하는 제품임을 먼저 설명합니다. 자율주행 코드 수정부터 CI/CD, 시험 차량 OTA, 실차 확인까지 한 사례로 연결하되 자동 검사와 개발팀의 Autoware 자체 검증·실차 시험을 구분합니다. 패키지·플랫폼·ECU의 상세 계약은 담당 가이드로 연결합니다.

    본문은 작업 대상 → 시작 위치 → 실행 → 결과 확인 → 다음 작업 순서로 안내합니다. 중요한 조건은 GitHub 강조 박스로, 비교는 표로, 순서와 관계는 그림으로 표현합니다. 같은 절차를 여러 문서에 복사하지 않고 해당 가이드로 연결합니다.

    사이트의 검색·기능 필터와 행별 복사는 CLI Markdown 표에서 직접 만들어집니다. 명령 목록을 별도 JavaScript 배열에 저장하지 않습니다. JavaScript를 사용할 수 없어도 전체 표를 읽을 수 있습니다. 필터는 명령 예시를 찾는 도구이며 실행 가능 여부를 확인하거나 명령을 실행하지 않습니다.

    긴 안내는 제목으로 구분하고, 일반 작업에 필요하지 않은 파일 목록 등은 펼쳐서 읽도록 구성합니다. next_steps는 다음 작업의 제목·사이트 경로·짧은 설명만 담습니다. 설치·실행 상태를 저장하지 않습니다. 화면 캡처는 확대 버튼으로 열고 Escape 또는 닫기 버튼으로 돌아옵니다. 검색과 확대는 키보드로도 사용합니다.

    문서 수정 후에는 strict 빌드와 전체 링크 검사를 먼저 실행합니다. 게시 CI의 웹 검사는 주요 화면·문서 이동·검색·모바일·테마·3D 로딩을 확인하고, 오프라인 검사는 전체 로컬 링크·검색·대표 3D 및 흐름도 로딩·외부 요청 부재만 확인합니다. 애니메이션 순서·영상 세 구간·일시정지·세부 대비의 긴 회귀 검사는 모션을 크게 바꿀 때 python docs/site/verify.py --full로 별도 실행합니다. 같은 검사를 오프라인에서 반복하지 않습니다. 명령어 필터를 수정했다면 검색·기능 선택·결과 없음·초기화·복사를, 캡처 확대를 수정했다면 키보드 열기·닫기·포커스 복귀를 확인합니다.

    시각자료 원칙¶

    • 홈은 제품이 맡는 일과 구체적인 자율주행 변경 사례를 함께 설명합니다. 설명용 상황·실제 UI·실차 시험 증적을 구분합니다.
    • GitHub 연결은 이름과 기존 GitHub 브랜드 아이콘을 함께 사용합니다. site/github.svg는 테마의 Font Awesome 아이콘(CC BY 4.0)입니다.
    • 홈의 Three.js 장면은 코드로 만든 차량·클라우드 배포 서버·보행자·LiDAR 스캔입니다. Furive OS는 차량에 탑재된 모듈로 표현합니다. 실제 차량 상태나 전송 속도를 나타내지 않습니다. OTA는 수신 → 검증 → 적용·실행 → 정상 확인 순서로 보여주며 자동 복구 조건을 옆에 설명합니다.
    • 3D 소스는 docs/site/graphics/scene.js(배포), driving.js(주행 예시), security.js(보호 경계), assets.js(공용 차량 모델)이며, 고정 의존성은 같은 폴더의 package.json과 lockfile입니다. 이 폴더에서 npm ci 후 npm run build로 docs/site/home-3d.js를 재생성하고 생성물도 함께 commit합니다. Three.js MIT 라이선스는 docs/site/three-LICENSE에 보관합니다. 빌드 도구와 원본 폴더는 사이트에서 제외합니다.
    • 홈에서만 로컬 3D 번들을 불러옵니다. 외부 CDN 없이 오프라인 ZIP에서도 실행합니다. 각 장면이 화면에 가까워질 때 렌더러를 초기화해 첫 화면에서 다른 장면의 준비를 기다리지 않습니다. 화면 밖·숨긴 탭·일시정지 상태에서는 렌더링을 멈추고 페이지 전환 시 이벤트·관찰자·GPU 자원을 정리합니다. 픽셀 비율은 최대 1.5로 제한합니다. WebGL 사용 불가 시 기존 설명용 차량 이미지로 대체합니다.
    • 개선 사례는 이슈 발견 → 코드 수정 → 자동 검사 → 원격 배포 → 개선 확인의 다섯 단계를 한 카드에서 선택합니다. 이전·다음 버튼과 단계 버튼의 방향키·Home·End로 이동하며, 선택한 설명과 그림만 표시합니다.
    • prefers-reduced-motion에서는 3D를 정지 화면으로 보여줍니다. 장면 밖에 공통 모션 일시정지 버튼을 두며, 코드 수정은 14초, OTA는 15초, 주행은 17초 주기로 자동 반복하며 장면별 다시 보기 버튼을 두지 않습니다. 모션을 멈춰도 선택한 단계의 설명과 링크를 읽을 수 있습니다. 인쇄에서는 그림을 생략하고 단계별 설명을 표시합니다.
    • 초기 개념 일러스트는 docs/assets/home/의 WebP이며 AI 생성 여부를 표시합니다. 관리 패널·프로그램·장점·개선 단계의 SVG는 같은 경로의 직접 작성한 벡터 에셋입니다. 생성 프롬프트는 docs/site/visual-prompts.txt에 기록합니다.
    • CI/CD와 같은 정확한 흐름은 HTML·SVG·Mermaid로 작성합니다. 단계 이름·분기·검사 범위는 현재 구현과 맞춥니다. 홈은 개발자 PC → GitHub Push → 서버 Checkout·Build → 검사 작업 → Report → 서명·클라우드 배포를 움직이는 패킷으로 연결합니다. 코드 편집 장면은 수정 완료 → 커밋 → Push 명령 → 전송 로그 → GitHub 반영 순서로 재생한 뒤 잠시 완료 상태를 보여주고 반복합니다. 실패는 코드 수정으로 돌아가며, 주행 확인 뒤 다음 개선으로 이어집니다. CI의 작은 주행 그림은 프로그램 테스트 예시이며 현재 실차·HIL 전체가 자동화됐다는 뜻이 아닙니다.
    • 홈은 배포·실행 관리 개념 → 이슈 발견부터 개선 확인까지 → 반복 개선 → 보안 → 핵심 관리 도구 → 실제 사용 영상 → 부가 프로그램 → 시작 가이드 순서입니다. 명령어 목록·문서 관리·다운로드의 세부 설명은 담당 가이드에서 제공합니다.
