    실행 구성요소¶

    이 문서는 Furive OS 안에서 어떤 프로그램이 무슨 일을 맡는지 설명한다. 이름을 모두 외울 필요는 없다. 평소에는 차량이 부팅되면 서비스와 운영 화면이 자동으로 시작되고, 문제가 있을 때만 이 문서를 찾으면 된다.

    전체 흐름¶

    운영 명령과 상태를 맡는 프로그램¶

    flowchart LR
  Operator["👤 운용자"] --> Dashboard["🖥️ Dashboard<br/>표시 · 입력 전달<br/>상태와 정책은 소유하지 않음"]
  Operator --> CLI["⌨️ furive CLI<br/>기존 서비스에 요청 전달"]
  Metrics["📊 system-manager<br/>PC 지표 수집"] --> Dashboard

  subgraph Owners["실제 상태와 실행을 결정하는 소유자"]

  CLI -. "조회 · 명령 전달" .-> OTA

    운영 화면(Dashboard)은 여러 프로그램의 상태를 한곳에 보여주고 명령을 전달한다. 프로그램 실행, Autoware 실행, 업데이트 규칙은 각각의 담당 프로그램이 처리한다.

    CLI도 같은 담당 기능을 호출하며 운영 화면 실행에 의존하지 않는다. 설치된 PC 배정과 기존 node 프로세스를 사용한다. 운용자는 CLI 명령어 표, 구현 담당자는 공통 소스 찾기를 참고한다.

    PC 사이 ROS와 같은 PC 안의 메시지¶

    아래는 권장 분산 구성의 데이터 전달 경로다. 같은 PC에 배정한 패키지는 로컬 ROS/DDS와 Integration Gateway를 사용한다. domain 번호는 기본 구성 예이며 실제 값은 플랫폼과 설치 설정을 따른다.

    flowchart LR
  subgraph Main["A-ECU"]
    direction LR
    AW["🚘 Autoware<br/>ROS domain 17"] --> Domain["🔀 ROS Domain Bridge<br/>승인된 topic · service만"]
    Domain --> Shadow["🌐 전송용 shadow domain 232"] --> ZMain["🔗 Zenoh Bridge"]

    MPackageA["📦 독립 패키지 A"] <--> MGateway["🔀 Integration Gateway<br/>127.0.0.1:15003<br/>main PC 안에서만"]
    MPackageB["📦 독립 패키지 B"] <--> MGateway
  end

  subgraph Edge["HMI-ECU"]
    direction LR
    ZEdge["🔗 Zenoh Bridge"] <--> EdgeROS["📦 edge ROS 2 패키지"]

    EPackageA["📦 독립 패키지 C"] <--> EGateway["🔀 Integration Gateway<br/>127.0.0.1:15003<br/>edge PC 안에서만"]
    EPackageB["📦 독립 패키지 D"] <--> EGateway
  end

  ZMain <-->|"QUIC · mTLS"| ZEdge
  MGateway -. "전달 경계" .-> GatewayRule["🚧 Gateway는 전달만 함<br/>기능 상태 · 정책 미소유<br/>현재 main↔edge 연결 없음"]
  EGateway -. "전달 경계" .-> GatewayRule

    PC 사이 ROS 2 데이터는 ROS Domain Bridge와 Zenoh Bridge가 맡는다. Integration Gateway는 각 PC 안의 요청·응답·이벤트만 전달하며, 기능 상태나 정책을 저장하거나 두 PC를 연결하지 않는다.

    경로별 목적·방향·동작의 허용 기준과 구현 한계는 Furive OS 전체 데이터 교환 정책이 소유한다. 아래 연결도는 현재 전달 경로를 보여주며, 모든 package의 데이터 접근이 개별 인증·격리된다는 뜻은 아니다.

    HMI·MGMT·DLS가 함께 보이지만 독립적으로 동작하는 구조¶

    세 화면은 하나의 큰 프로그램이 아니다. Furive OS Package Manager가 의존 순서와 실행·중지·health·로그를 공통으로 관리하지만 HMI, MGMT, Data Logging System(DLS)은 각자의 package와 프로세스로 실행된다. MGMT의 기록 탭도 DLS가 제공한 화면을 iframe으로 보여주는 adapter일 뿐 녹화·세션·전송 정책을 복제하지 않는다.

    구간 실제 프로토콜과 경계 맡는 일
    Autoware → main Zenoh ROS 2/CycloneDDS domain 17 → ROS Domain Bridge → shadow domain 232 허용된 topic·service와 방향만 전송망으로 전달
    main ↔ edge ROS Zenoh over QUIC/UDP :7447, TLS 1.3 mutual TLS 설치가 배포한 node certificate를 검증하고 exact peer-CN ACL을 적용해 ROS 경로 전달
    main ↔ edge 제어면 UTF-8 JSON object stream over TCP :15001, TLS 1.3 mutual TLS edge 등록·heartbeat·package 상태와 승인된 명령/응답; ROS 데이터 경로와 별도 연결
    edge ROS → HMI HMI에 포함된 ROS 2 runtime과 native ROS adapter → 로컬 DDS OS가 정한 ROS domain에서 표시용 topic을 Unity HMI에 제공
    edge ROS → MGMT MGMT Telemetry Bridge → newline-delimited JSON over process stdio → Electron IPC 최신 상태 snapshot과 승인된 차량 명령; rosbridge는 명시적 fallback일 때만 사용
    edge ROS → DLS ROS 2/CycloneDDS → rosbag recorder 선택 topic을 로컬 dataset에 기록하고 세션·재생·선택 NAS 전송을 관리
    Dashboard/DLS → MGMT 같은 edge의 loopback HTTP와 server-issued iframe URL DLS 화면만 MGMT 안에 표시; DLS 상태와 설정은 DLS가 소유

    HMI는 로컬 DDS에 직접 참여하고 별도 rosbridge 서버를 요구하지 않는다. ROS domain·DDS 설정과 복구 기준은 패키지 통신·복구 계약을 따른다. rosbridge를 사용하는 경로는 자체 client 인증이 없으므로 127.0.0.1 바인딩, topic allowlist와 subscribe-only 경계를 적용한다. Dashboard surface와 Integration Gateway도 같은 PC의 loopback 경계다. 반대로 PC 사이를 건너는 Zenoh와 Furive node 제어면은 각각 별도의 TLS 1.3 mTLS 연결이며, 일반 TCP Zenoh endpoint로 낮춰 연결하지 않는다. Telemetry Bridge의 stdio와 Electron IPC는 네트워크 연결이 아닌 같은 MGMT process tree 내부 경계이므로 mTLS를 적용하는 구간이 아니다. renderer는 ROS 2나 Zenoh socket에 직접 연결하지 않는다.

    상태와 로그를 보는 기준¶

    furive status는 전체 운용 문제와 서비스·업데이트·플랫폼 상태를 요약한다. 기존 패키지·PC 상태 보고를 사용하며 최신 전체 상태를 받지 못하면 확인 불가로 표시한다.

    패키지별 상태와 로그는 furive package status, furive package logs <name> 또는 전체 Dashboard의 Package Manager에서 확인한다. 명령별 범위는 CLI 명령어 표를 따른다. 차량 PC에 로그인하면 플랫폼에 배정된 화면이 열린다. Lotte Ohmio처럼 furive-launcher 전용 화면이 먼저 열리는 구성에서 전체 진단 화면이 필요할 때 다음 명령을 사용한다.

    furive dashboard --web

    표준 패키지 실행 로그는 저장소의 logs/<package>.log, 빌드 로그는 logs/<package>.build.log에 남는다. 파일 이름에서는 하이픈이 밑줄로 바뀐다. 예를 들어 ota-updater의 로그는 logs/ota_updater.log다. 전체 서비스 기록은 furive service logs로 본다.

    Dashboard — 하나의 운영 화면¶

    목적: 여러 프로그램의 상태와 명령을 한 화면에 모은다.

    • 담당: 화면, HTTP API 연결, 사용자 입력 전달
    • 담당하지 않음: 패키지 실행·중지, 업데이트 규칙, Autoware 실행·중지
    • 시작: 화면 뒤의 서버는 서비스와 함께 시작하고, main 화면은 데스크톱 로그인 뒤 자동으로 열린다.
    • 로그: logs/dashboard.log

    사용자는 평소 설정 파일을 직접 만지지 않고 화면에서 제공하는 설정만 바꾼다. 개발자는 새 기능의 규칙을 운영 화면에 만들지 말고, 실제 담당 프로그램의 API를 연결하고 결과를 표시한다.

    desktop_surface가 지정된 플랫폼은 로그인 시 전체 Dashboard 대신 해당 패키지 화면을 연다. 차량 플랫폼의 기본 화면은 Furive Launcher다. 이는 backend나 Package Manager가 빠졌다는 뜻이 아니다.

    Package Manager — 모든 패키지의 공통 실행 관리자¶

    목적: 언어와 실행 방식이 다른 프로그램을 같은 방법으로 실행하고 관리한다.

    • 담당: 패키지 발견, 실행 순서, 빌드, 실행·중지, 정상 동작 확인, 재시작 판단, 로그
    • 입력: 각 독립 저장소의 package.yaml과 실행 진입점
    • 출력: 운영 화면과 main/edge PC가 사용하는 패키지 상태
    • 로그: logs/<package>.log, logs/<package>.build.log

    사용자가 Package Manager 자체를 설정할 일은 없다. 개발자는 프로그램 안에 별도 재시작 반복문이나 다른 패키지 제어를 넣지 말고, 필요한 차이만 package.yaml에 선언한다. 기본 패키지는 이름과 버전, run.sh만으로 시작할 수 있다. 자세한 필드는 프로그램 연결 설정을 따른다.

    Furive Launcher — Autoware 실행 준비¶

    목적: 선택된 차량·센서 모델과 지도에 맞춰 Autoware를 준비하고 시작·중지한다.

    • 담당: Autoware 빌드, 실행·중지, 시작 방식과 실행 상태
    • 실행 위치: main PC
    • 화면: 차량 플랫폼에서 로그인 뒤 기본으로 열리는 주행 준비 화면
    • 로그: logs/furive_launcher.log
    • Autoware 실행 로그: logs/furive_launcher_autoware.log
    • Autoware 빌드 로그: logs/furive_autoware_build.log

    사용자는 주행 준비 화면에서 제공하는 플랫폼·지도·실행 동작만 사용한다. 개발자는 플랫폼 정의와 외부 Autoware 소스 버전을 Furive Launcher에 복사하지 않고 각각 config/capability-profiles.yaml, config/external-workspaces.yaml에서 바꾼다.

    OTA Update — 원격으로 안전하게 계속 업데이트¶

    목적: 차량이 새 배포판을 자동으로 찾고, 서명과 호환성을 확인한 뒤 안전하게 전환하도록 한다.

    • 화면·명령 연결: package/core/ota-updater
    • 업데이트 규칙과 실행: core/ota_policy.py, core/self_updater.py, core/release_activation.py
    • 업데이트 흐름: 확인 → 내려받기와 검증 → 다음 재시작에 활성화 → 실패 시 이전 판 복구
    • 채널: 한 차량 시험은 test, 고객용 공용판은 normal
    • 로그: logs/ota_updater.log

    차량 사용자는 보통 확인 주기나 내부 branch를 바꾸지 않는다. 문제가 있으면 Dashboard의 OTA 화면과 furive status로 현재 판과 진행 상태를 본다. 개발자는 한 차량 test에서 실행과 복구를 확인한 뒤 normal로 승격한다. 배포 버전과 설치 묶음의 판단은 CI/CD 기준을 따른다.

    PC 상태 수집기 (system-manager)¶

    호스트 시간 상태는 core/time_sync.py가 관측해 공통 시스템 지표에 포함한다. 시각 보정은 chrony가 소유하고 furive system status와 furive status에서 확인한다. 준비되지 않은 호스트를 동기화 완료로 표시하지 않는다. PC 시간 동기화에 설치·보정·연결 복구 기준을 정리한다.

    목적: main PC의 자원 사용량을 가볍게 수집해 Dashboard에 제공한다.

    • 수집: CPU, 메모리, uptime, OS, 네트워크 사용량, NVIDIA GPU 정보
    • 출력: 내부 상태 파일 logs/.system_manager_state.json
    • 로그: logs/system_manager.log

    이 패키지는 차량 상태, 디스크 관리, 전원 제어, 서비스 시작·종료를 담당하지 않는다. 사용자가 설정할 항목도 없다. 개발자는 새 운영 정책을 이 수집기에 넣지 않고, 필요한 지표만 추가한다.

    Zenoh Bridge — main과 edge의 ROS 2 연결¶

    목적: 서로 다른 PC의 필요한 ROS 2 데이터를 차량 네트워크로 전달한다.

    • 흐름: main Zenoh Bridge ↔ QUIC/TLS 1.3 상호 인증 ↔ edge Zenoh Bridge
    • 연결 주소: 설치가 정한 main 주소에서 자동으로 계산
    • 보안: 설치가 배포한 PC 인증서로 상대 PC 확인
    • 로그: logs/zenoh_bridge.log

    사용자는 연결 주소나 인증 방식을 반복 설정하지 않는다. 개발자는 전달할 ROS 계약이나 네트워크 보안 경계를 바꿀 때만 이 패키지를 수정한다. 일반 TCP Zenoh 연결 주소와는 호환되지 않는다.

    ROS Domain Bridge — Autoware와 전송망 사이의 경계¶

    목적: main PC에서 Autoware의 ROS 2 영역과 Zenoh 전송용 영역을 분리하고, 승인된 경로만 잇는다.

    Autoware domain 17 -> ROS Domain Bridge -> 전송용 shadow domain 232 -> Zenoh Bridge
    • 담당: 허용된 ROS topic·service와 전달 방향
    • 실행 위치: main PC
    • 로그: logs/ros2_domain_bridge.log

    232는 제품 내부 전송용 예약값이므로 일반 사용자가 바꾸지 않는다. Autoware domain은 PC 설정에서 정한다. 통합 개발자는 HMI나 edge가 새 ROS 경로를 실제로 필요로 할 때만 허용 목록과 메시지 형식을 수정하고 main→edge 전체 경로를 검증한다.

    Integration Gateway — 같은 PC의 패키지 통합 버스¶

    목적: 독립 개발된 패키지가 서로의 내부 코드에 의존하지 않고 요청·응답·이벤트를 교환하게 한다.

    • 범위: 현재 같은 PC 안에서만 동작
    • 연결: 127.0.0.1:15003
    • 시작: 필요한 패키지가 의존 프로그램으로 지정하면 Package Manager가 자동으로 먼저 시작
    • 메시지: 패키지 이름을 대상으로 하는 요청·응답과 주제(topic)별 이벤트
    • 로그: logs/integration_gateway.log

    사용자가 주소나 별도 서비스를 설정할 일은 없다. 패키지 개발자는 상대 패키지 프로세스에 직접 붙는 대신 공용 통로의 간단한 메시지 형식을 사용한다. 일반 메시지는 내용 해석 없이 전달하며 업무 원본 상태와 정책은 기능 패키지가 소유한다. 구버전 응답 변환 예외는 패키지 계약에 한정한다. 현재 main과 edge 사이의 gateway 연결은 없다. 상세 메시지 계약은 Integration Gateway README에 있다.
