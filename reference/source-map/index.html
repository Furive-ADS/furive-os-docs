    공통 소스 찾기¶

    바꾸려는 기능의 시작 파일 하나를 열고, 필요한 연결 파일만 따라갑니다. core/는 Furive OS의 공통 구현을 담습니다. 프로그램 자체 기능과 화면은 별도 package/ 저장소에서 찾습니다. 전체 폴더는 루트 지도, 책임 경계는 개발 계약을 기준으로 합니다.

    기능으로 찾기¶

    아래 묶음은 현재 파일을 읽는 순서입니다. 별도 서비스나 새로운 설정 단위가 아닙니다.

    바꾸려는 기능 시작 파일 필요할 때 이어 읽기
    명령·도움말·개발 실행 cli.py 루트 furive, run.sh
    운용 CLI·화면 요청을 기존 기능에 전달 core/operator_control.py cli.py, main 실행기, edge 실행기; 별도 lifecycle을 만들지 않음
    중앙 ROS 전달·토픽 조회·적용 core/topic_control.py capability_profile.py, package_manager.py; 녹화 상태는 DLS 소유
    패키지 발견·실행·health·로그 package_manager.py package_discovery.py, process_watchdog.py, docker_pull_progress.py
    차량 배정·플랫폼별 패키지 선택 fleet_assignment.py capability_profile.py, config_loader.py
    PC 시작·등록·상태 보고 node_bootstrap.py main의 실행기, edge의 실행기, node_ota_status.py
    업데이트 허용·목표 선택·준비 ota_policy.py self_updater.py, version_sync.py, ota_control.py
    업데이트 적용·확정·복구 release_activation.py release_identity.py, release_images.py, deploy_targets.py
    Autoware 소스 버전·작업 공간 external_workspaces.py autoware_repositories.py
    Autoware 빌드·컨테이너 선택 autoware_builder.py autoware_devcontainer.py, autoware_runtime.py
    Autoware 실행 프로그램과 연결 launcher_control.py furive-launcher가 실제 Autoware lifecycle을 담당. 실행 흐름과 스크립트
    패키지 Source Unlock 작업 공간 source_workspaces.py 패키지 개발 가이드
    패키지에 필요한 runtime asset 준비 runtime_assets.py node_bootstrap.py
    차량 명령 전달 vehicle_control.py 해당 차량의 package/plugin/ 구현
    PC 자원·네트워크·로컬 제어 system_metrics.py network_selection.py, host_control.py, graphical_session.py, rustdesk_access.py
    제어 요청 인증·패키지 메시지 연결 control_security.py integration_gateway_client.py

    architecture.py는 CPU architecture 이름을 맞추고, json_stream.py는 JSON 스트림을 읽는 공통 도구입니다. init.py는 PackageManager를 공개합니다. 관련 기능의 파일을 읽다가 필요할 때 확인합니다.

    실행 순서로 읽기¶

    운용 명령의 사용법은 CLI 명령어 표, 구현을 조사할 때의 흐름은 다음과 같습니다.

    flowchart LR
  CLI["furive · core/cli.py"] --> Adapter["기존 node 안의<br/>operator_control"]
  Adapter --> Owner["PackageManager · OTA<br/>Launcher · host 기능"]
  Adapter --> Topic["topic_control<br/>중앙 전달 설정·DLS 요청"]

    CLI는 요청을 전달합니다. 실제 실행·업데이트·녹화 상태는 각 담당자가 소유하며 별도 daemon은 없습니다.

    전체 개발 실행은 아래 순서로 연결됩니다. 파일명은 내부 구현 경로입니다.

    furive
  → core/cli.py: command_dev → _command_dev
  → run.sh
  → nodes/master.py 또는 nodes/agent.py
  → core/node_bootstrap.py: initialize_node_runtime
  → core/package_manager.py: PackageManager
  → 선택된 패키지의 실행 파일

    패키지 하나의 furive package run은 cli.py의 run_package에서 초기화와 PackageManager를 직접 호출합니다. 전체 PC 실행 흐름을 모두 읽을 필요는 없습니다. 노드 간 통신과 OTA 적용 흐름은 기술 구조에 있습니다.

    설치를 수정할 때는 install.sh에서 시작해 필요한 단계만 엽니다. installer/의 번호는 설치 구현을 읽는 순서이며 개별 실행 명령이 아닙니다.

    설치 단계 파일
    호스트 기반 준비 10-host-foundation.bash
    소스·설정 준비 20-source-and-config.bash
    데스크톱·Autoware 준비 30-workstation-and-autoware.bash
    설치 흐름 조합 40-install-flow.bash
    패키지·서비스 등록 50-packages-and-service.bash

    차량 설치 묶음의 bootstrap.sh 생성 구현은 스크립트 안내에 있습니다.

    설정으로 찾기¶

    설정은 config/에 있습니다. 파일의 내부 호환 이름은 새 사용자 용어로 확장하지 않습니다.

    찾는 값 기준 파일 읽는 공통 코드
    main / edge 기본 설정 master.default.yaml, agent.default.yaml config_loader.py
    차량별 플랫폼·업데이트 배정 fleet-vehicles.yaml fleet_assignment.py
    플랫폼별 패키지·차량·센서 조합 capability-profiles.yaml capability_profile.py
    내부 개발 PC의 플랫폼 development-platform.yaml fleet_assignment.py
    플랫폼별 Autoware revision external-workspaces.yaml external_workspaces.py
    Autoware OS·GPU·CUDA·driver 호환 autoware-compatibility.yaml autoware_devcontainer.py
    deploy 대상 매핑 deploy-targets.yaml deploy_targets.py

    설치가 만든 역할 설정과 실행 중 로그·데이터 위치는 저장소와 런타임 위치를 봅니다.

    함수와 테스트 좁히기¶

    저장소 최상위 폴더에서 검색합니다. 패키지 자체 기능이라면 해당 패키지 폴더로 검색 범위를 바꿉니다.

    # 이름으로 파일 찾기
rg --files core nodes tests -g '*package*'

# 담당 파일의 함수와 클래스를 훑기
rg -n '^(async def |def |class |    async def |    def )' core/package_manager.py

# 호출하는 곳과 가까운 테스트 찾기
rg -n 'PackageManager|start_package' core nodes tests

    작은 테스트 실행과 전체 ./furive check의 범위는 테스트 안내를 따릅니다. 새 파일을 둘 때도 먼저 위 기능의 기존 담당 코드가 처리할 수 있는지 확인합니다.
