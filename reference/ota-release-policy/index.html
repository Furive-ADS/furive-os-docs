    업데이트 호환판과 구버전 설정 변환¶

    이 문서는 오래된 차량이 최신 버전으로 바로 갈 수 없을 때 Furive가 중간 호환판을 선택하고 복구하는 내부 계약을 설명합니다. 운용 절차는 차량 업데이트를 따릅니다.

    운용자가 알아야 할 것은 현재 버전, 목표 버전, 이전 정상 버전뿐입니다. 내부 호환 번호와 설정 변환 방식은 Furive가 자동으로 선택합니다.

    한눈에 보기¶

    flowchart LR
  Current["✅ 현재 정상 버전"] --> Direct{"❓ 목표로 바로<br/>갈 수 있는가?"}
  Direct -->|예| Target["🛰️ 목표 버전 준비"]
  Direct -->|아니요| Compat["🔄 검증된 호환판 준비"]
  Compat --> Optional["🧩 필요한 경우에만<br/>구버전 설정 변환"]
  Optional --> Health["🩺 패키지 상태 확인"]
  Health --> Direct
  Target --> Done["✅ 목표 버전 확정"]
  Optional -->|실패| Restore["↩️ 직전 정상 버전 복구"]
  Health -->|실패| Restore

    호환판은 오래된 버전과 최신 버전 사이를 잇는 중간 업데이트입니다. 코드에는 호환을 위해 kind: bridge라는 이름이 남아 있지만 네트워크 Bridge와는 관계없습니다.

    일반 normal 업데이트는 설정을 변환하지 않습니다. 현재는 구버전에서 사용자가 바꾼 설정만 골라 새 기본값에 옮기는 일회성 변환 하나만 있습니다.

    하나의 OTA 흐름¶

    흐름은 준비 → 패키지 종료 확인 → 전환 → 시작·정상 확인 → 확정 또는 복구입니다. 자동 업데이트와 수동 준비는 같은 준비 함수를 사용합니다. 자동 준비가 현재 실행 중인 프로그램을 교체하지는 않습니다.

    flowchart LR
  Prepare["SelfUpdater<br/>다음 버전 준비·복구 요청"] --> Stop["기존 runtime 감독<br/>PackageManager 종료 확인"]
  Stop --> Switch["ReleaseActivation<br/>재시작 시 전환"]
  Switch --> Run["PackageManager<br/>패키지 시작·상태 확인"]
  Run --> Decide["ReleaseActivation<br/>정상판 확정 또는 복구"]

    세 실행 책임은 다음 경계를 지킵니다.

    • SelfUpdater는 별도 폴더에서 파일·이미지·빌드를 준비합니다. 실행 중인 패키지를 제어하지 않습니다.
    • PackageManager는 패키지 시작·중지·health만 담당합니다. 업데이트 버전과 복구판을 선택하지 않습니다.
    • ReleaseActivation은 버전 전환과 확정·복구를 담당합니다. 패키지 상태는 PackageManager에 묻습니다.

    수동 이전 정상 복구도 이 경계를 따릅니다. 업데이터는 기존 activation 기록에 복구 요청만 남기고 rollback_pending, restart_required를 응답합니다. 다음 감독된 재시작에서 패키지를 모두 종료한 뒤 복구합니다. 재시작 전에는 실행 파일·설정·이미지를 바꾸지 않습니다. 별도의 자동 재시작은 예약하지 않습니다. 요청이 기록된 뒤 전원이 꺼지거나 OTA hold가 켜져도 다음 시작에서 복구를 이어갑니다.

    준비할 패키지와 시작할 패키지는 core/packages/discovery.py의 같은 의존성 계산을 사용합니다. 따라서 선택한 패키지의 의존 패키지도 먼저 준비하며, 빠진 의존성이나 순환 관계는 이미지 다운로드·빌드 전에 실패합니다. 이전 이미지 보존에도 같은 패키지 선택을 사용합니다.

    정책과 호환 정보까지 포함한 구현 위치는 다음과 같습니다.

    책임 구현 위치
    허용할 업데이트 정책 core/ota/policy.py
    목표 선택, 잠금과 별도 폴더 준비 조정 core/self_updater.py
    후보 package manifest·image·source preflight core/ota/preflight.py
    Git·LFS·submodule transport core/ota/repository_transport.py
    구버전 marker·checkout handoff 검증 core/ota/legacy.py
    폴더 교환, 설정 변경 기록, 확정과 복구 core/release_activation.py
    주기 확인과 API 연결 package/core/ota-updater
    호환 경로와 배포 버전 확인 core/release_identity.py

    개별 패키지는 자신의 시작 방법과 정상 상태만 알려줍니다. 별도 업데이트·설정 변환·복구 프로그램을 만들지 않습니다. 운영 화면도 상태 표시와 사용자 입력만 담당합니다.

    요청이 겹치거나 준비가 실패할 때¶

    자동 확인과 수동 확인·준비·적용·복구는 SelfUpdater의 같은 작업 잠금을 사용해 순서대로 실행합니다. API 서버만 잠그고 자동 작업은 별도로 진행하는 경로는 없습니다. ReleaseActivation.transaction이 기존 .staging.lock으로 준비·확정·복구 요청·부팅 전환을 직렬화합니다. 실제 전환·복구는 추가로 같은 checkout의 두 역할에 대한 기존 PackageManager 실행 잠금을 획득해야 합니다. 종료 실패나 살아남은 자식 프로세스가 잠금을 유지하면 파일 교환을 거절하며, 전환 중에는 새 runtime도 시작할 수 없습니다. 복구가 대기 중이면 다음 후보 준비도 거절합니다. 준비 전 조건이나 잠금 획득에서 거절된 요청은 기존 후보와 이미지 복구본을 정리하지 않습니다. 준비를 시작한 뒤 실패하면 미완성 후보를 정리하고 현재 실행본을 유지합니다.

    재시작 요청은 기존 요청 파일에 원자적으로 기록한 뒤 접수 응답을 보냅니다. 쓰기 실패는 호출자에게 전달하고, 손상된 요청 파일을 정상 재시작 명령으로 해석하지 않습니다. 접수 응답은 종료·전환 완료를 뜻하지 않습니다. 수동 복구 요청은 별도 상태 파일 없이 기존 rollback_switching 복구 기록을 사용합니다. 다음 준비가 이전 이미지 snapshot을 덮어쓰기 전에 기존 activation 기록의 previous_image_snapshot에 직전 정상판의 이미지를 보존합니다. 이 필드는 같은 복구 소유자의 과거 시점 증거이며, 다음 후보용 snapshot과 대상 commit이 다릅니다. 새 후보가 실제로 전환될 때 복구 기준도 교체됩니다.

    준비된 버전은 검증된 후보에서 읽으며 별도의 메모리 복사본을 유지하지 않습니다. 후보가 사라지거나 검증에 실패하면 준비 완료로 응답하지 않습니다.

    PackageManager는 OTA 전용 RPC 없이 일반 process health로 업데이터를 감독합니다. 업데이터의 작업 스레드가 중단되면 패키지 프로세스가 실패 종료하므로 기존 재시작 정책이 처리합니다. 상태 기록은 패키지의 주 대기 loop가 맡으며 별도 기록 스레드가 없습니다. 기록 실패는 로그에 남기고 이전 관측을 최신으로 다시 표시하지 않습니다. 진단용 health API는 가볍게 유지하며, 다운로드·상태 조회와 독립적으로 응답합니다. 로컬 제어 연결은 최대 8개, 요청 수신 대기는 5초이며 제어 작업 하나가 진행 중일 때 다른 작업은 명시적으로 거절합니다. 명령을 무제한 대기열에 쌓지 않습니다.

    시작 설정은 core/ota/policy.py 한 곳이 읽을 값·기본값을 결정합니다. 패키지 셸은 설정을 다시 해석하지 않고, 역할·설정 오류를 다른 PC 설정이나 기본 자동 적용으로 대체하지 않습니다. 자동 준비 기본값은 두 PC 모두 꺼짐입니다. 기존 자동화 인자와 환경 override는 패키지 진입점에서만 받아들입니다. 후보 버전은 검증된 marker의 목표를 사용하며 같은 commit에 붙은 다른 tag로 다시 추측하지 않습니다. 후보 확정에는 기존 패키지 health와 복구 검증이 계속 필요합니다. 새 서비스·설정·상태 파일은 없으며 운용자가 사용하는 명령도 그대로입니다.

    이 잠금은 정상 runtime 간 전환 권한을 강제하는 실행 계약입니다. 같은 OS 계정으로 실행하는 코드를 악성 코드로부터 격리하는 보안 경계는 아닙니다. 서명된 core 업데이터는 기존 후보·migration 기록의 인증 때문에 신뢰 영역에 남으며 기존 control credential 계약을 유지합니다. 일반 패키지에는 해당 credential을 전달하지 않습니다. 별도 계정·서비스를 추가하는 권한 격리는 이 업데이트 흐름에 숨겨 넣지 않습니다.

    유지보수할 때 확인할 경계¶

    일반 변경은 위 책임 경계 안에서 끝내고, 이미 발행한 서명·후보 기록·복구 기록의 형식은 유지합니다. 파일을 나누거나 새 상태를 추가하는 것만으로 흐름을 바꾸지 않습니다. SelfUpdater는 준비 전 조건과 작업 잠금, 목표 release 선택, activation 요청만 조정하며, candidate package preflight·repository transport·legacy handoff 검증은 각 소유 모듈에서 수행합니다. 담당 테스트는 다음과 같습니다.

    바꾸는 책임 먼저 확인할 회귀
    자동·수동 준비, 동시 요청 tests/release/test_self_updater_preparation.py
    후보 빌드·의존 패키지·이미지 보존·실패 정리 tests/release/test_self_updater_release_preflight.py
    Git·LFS·submodule transport·재시도 tests/release/test_self_updater_lfs_retry.py, tests/release/test_self_updater_submodule_paths.py
    구버전 handoff 검증·adoption tests/release/test_self_updater_legacy_handoff.py, tests/release/test_self_updater_v07_handoff.py
    패키지 시작·역순 종료·후보 필수 패키지 tests/runtime/test_package_manager_lifecycle.py
    업데이터 생존 확인·시작 설정·통신 오류 package/core/ota-updater/tests/, tests/core/test_ota_control.py, tests/core/test_ota_policy.py
    전환·확정·중단 후 복구 tests/release/test_release_activation.py

    마지막에는 ./furive check를 실행합니다. 차량에 적용할 업데이트 기반 변경은 기존 정상판에서의 적용과 실패·재시작·복구를 한 차량의 test 업데이트로 확인한 뒤 normal에 반영합니다. source 회귀 통과만으로 전원 차단이나 실제 장치 복구까지 검증됐다고 판단하지 않습니다.

    내부 호환 선언¶

    배포 설명 파일(release/manifest.json)에는 현재 버전에서 다음 버전으로 안전하게 갈 수 있는 조건이 들어 있습니다.

    사람이 이해할 의미 기존 내부 필드
    일반판인가 중간 호환판인가 kind: normal|bridge
    받을 수 있는 이전 호환 세대 source epoch/contract/config_schema/control_protocol
    적용 뒤의 호환 세대 target identity
    PC의 시작 프로그램에 필요한 최소 기능 minimum supervisor contract
    필요한 설정 변환 목록 migration catalog

    artifact_contract_version은 배포 파일 형식 번호이고, OTA epoch는 업데이트 호환 세대입니다.

    일반판은 source와 target identity가 같고 설정 변환이 0개여야 합니다. 호환 세대를 넘는 버전만 내부 bridge가 될 수 있습니다. 설정 schema까지 달라질 때만 설정 변환 파일 하나를 포함하고, control protocol만 달라지면 변환 파일은 없습니다.

    현재 artifact v2는 일반판에도 빈 migration catalog와 no-op checkpoint를 기록합니다. 이는 게시된 preview 호환 경로를 위한 기존 wire 계약이지 새 개발자가 배워야 할 제품 개념이 아닙니다. 다음 artifact contract에서는 일반판의 빈 catalog를 없애고, 호환판에만 선택적인 단일 설정 변환 정보를 두는 것이 목표입니다.

    목표까지 가는 경로¶

    Furive는 서명과 배포 설명 파일을 확인했고 내용을 바꿀 수 없게 고정한 Git tag만 사용합니다.

    1. 목표가 현재 상태를 직접 받을 수 있으면 목표를 준비합니다.
    2. 직접 갈 수 없으면 목표 버전에 적힌 호환판 중 가장 짧은 경로를 고릅니다.
    3. 한 번에 다음 버전 하나만 준비·적용·확정합니다.
    4. 호환판이 확정되면 같은 최종 목표로 경로를 다시 계산합니다.
    5. 필요한 호환판이 없거나 검증에 실패하면 현재 정상판을 계속 실행합니다.

    경로는 최대 네 단계이며 중간 호환판은 최대 세 개입니다. 순환하거나 더 오래된 호환 세대로 가는 경로, 허용된 Git 이력 밖의 tag, 발행 뒤 내용이 바뀐 버전은 거부합니다.

    release_pin은 최종 목표만 뜻합니다. 중간 호환판을 거치더라도 차량의 영구 목표 설정은 바꾸지 않습니다.

    과거 버전으로 직접 돌아가는 요청은 현재판과 목표판의 호환 조건이 같고 설정 변환이 없는 일반판일 때만 허용합니다. 그 밖의 복귀는 직전 정상판 자동 복구 또는 새 설치 묶음을 사용한 정비 설치로 처리합니다.

    임시 구버전 설정 변환¶

    현재 source에서 실행 가능한 설정 변환은 migrations/compatibility/epoch-1-to-2.py 하나뿐입니다. 일반 확장점이나 DB migration 체계가 아닙니다.

    • 새 설치와 일반판에는 변환 파일이 없습니다.
    • 이전 버전의 기본값과 현재 설정을 비교해 사용자가 바꾼 값만 보존합니다.
    • PC 명령, 네트워크 다운로드, 의존 프로그램 설치, 패키지 빌드·실행을 하지 않습니다.
    • 변경 전 설정을 보관하고 변경 전후 기록을 남깁니다.
    • 패키지를 시작하기 전에 끝나며, 실패하면 직전 정상 버전으로 돌아갑니다.
    • 파일명이나 .done 파일만으로 완료를 인정하지 않습니다.

    현재 config/deploy-targets.yaml의 구버전 전환 gate가 열려 있으므로 이 파일의 경로와 기존 wire 값을 바꾸지 않습니다. 전환판 게시와 대상 fleet의 수렴이 확인된 뒤 source의 임시 변환기와 validator를 제거합니다. 게시된 immutable 호환판은 필요한 차량이 남아 있는 동안 보존합니다.

    되돌릴 수 있는 설정만 변경¶

    설정 변환 전에 복구본을 만들고 변경 내용을 기록합니다. 복구할 때는 이번 업데이트가 바꾼 값만 되돌리며, 그사이 운영자나 다른 프로그램이 바꾼 값은 덮어쓰지 않습니다.

    새 필드는 먼저 이전판도 읽을 수 있게 추가하고, 바로 다음 버전에서 과거 형식을 제거하지 않습니다. 데이터베이스, 데이터셋, 주행 기록처럼 설정이 아닌 데이터를 되감는 작업은 이 경로에 넣지 않습니다. 그런 데이터는 해당 패키지가 별도 백업·복구 절차를 담당합니다.

    발행과 보존¶

    개별 test 채널에서는 호환판을 먼저 발행해 한 차량의 적용·전원 중단·health·rollback을 검증할 수 있습니다. 공식 공용 전환은 필요한 main과 기존 차량 channel의 호환판을 같은 source commit으로 검증한 뒤 한 묶음으로 게시합니다. 일부만 공용 최신판으로 먼저 노출하지 않습니다.

    게시 뒤에도 곧바로 구버전 지원을 닫지 않습니다. 대상 차량이 호환판에 도달했거나 새 bundle로 복구됐다는 fleet inventory가 확인될 때까지 다음 normal 발행 gate를 유지합니다. 지원 차량이 참조하는 호환판 tag, deploy artifact와 image digest도 삭제하지 않습니다.

    서명·보존·publication gate의 세부 운영은 CI/CD 기준을 따릅니다.

    화면에 보이는 말¶

    운영 화면은 내부 호환 번호나 wire 값을 보여주지 않고 다음 상태만 사용합니다.

    • 최신
    • 업데이트 있음
    • 준비 중
    • 적용 준비 완료
    • 적용·확인 중
    • 이전 정상 버전으로 복구됨
    • 설치 복구 필요
    • 오류

    내부 identity와 호환판 tag는 장애 분석용 JSON과 이 reference에서만 확인합니다.
