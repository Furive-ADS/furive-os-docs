    독립 배포 reader 계약¶

    P2-1은 독립 배포의 형식 reader와 validator를 준비한다. 기존 source exporter와 보호된 signer는 계속 artifact v2를 사용한다. 프로젝트 exporter는 v3 후보를 생성하고 P2-5의 독립 승인·인증 경로가 서명·게시한다. P2-3은 프로젝트의 조직 입력으로 계획과 후보 export를 연결하고 P2-4는 검사 결과를 후보에 결박한다. core/release_identity.py가 형식·정규화·조합 identity를 소유하며, 별도 config 파일·lock·host 상태 파일을 추가하지 않는다.

    기존 형식과 구분¶

    형식 source_ref 의미 읽기·운영 범위
    기존 source / artifact v2 공통 source commit 기존 실행·인증·복구 유지
    artifact v3 조합을 소유한 프로젝트 commit 조합·증적 검증, 후보 export·보호된 CI 서명·게시 및 host 인증·적용 source 경계. 실제 조직별 설치·복구는 별도 검증

    v3는 composition과 publication을 모두 요구한다. 이 필드를 가진 v2·버전 누락·알 수 없는 버전은 실패한다. 과거 날짜를 붙여도 legacy로 내려가지 않는다. bool·문자열 버전, 빠진 필드와 알 수 없는 하위 필드도 실패한다. v2에 새 provenance 필드를 얹고 검증된 것으로 간주하지 않는다.

    v3 최소 입력¶

    다음은 형식을 설명하는 예시다. SHA는 실제 발행·검증 증거가 아니다. 기존 manifest의 version, source_ref, lock/hash·OTA 필드는 함께 필요하다.

    {
  "artifact_contract_version": 3,
  "source_ref": "1111111111111111111111111111111111111111",
  "package_lock_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "composition": {
    "version": 1,
    "project": {
      "repository": "https://git.example/team/project",
      "commit": "1111111111111111111111111111111111111111"
    },
    "common": {
      "repository": "https://git.example/upstream/common",
      "commit": "2222222222222222222222222222222222222222"
    },
    "platform": {
      "repository": "https://git.example/team/platform",
      "commit": "3333333333333333333333333333333333333333",
      "path": "config/platform",
      "tree": "4444444444444444444444444444444444444444"
    },
    "package_lock_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "publication": {
    "version": 1,
    "deploy_repository": "https://git.example/team/deploy",
    "registry_namespace": "registry.example/team",
    "platform": "office"
  }
}

    project/common/platform의 commit과 platform tree는 소문자 40자리 Git object ID다. 플랫폼 path는 선택 입력 subtree의 repository 상대 경로이며 빈 절·.·..·절대 경로를 허용하지 않는다. publication.platform은 그 입력에서 선택한 기존 profile 이름이다. 실제 Git object 존재·tree 종류와 export 내용의 일치·dirty·선택 profile 존재 검사는 P2-2 exporter의 책임이다. reader 통과가 실제 플랫폼 지원을 뜻하지 않는다.

    project commit은 source_ref와 같아야 한다. package revision은 기존 release/package-lock.yaml에만 저장하고 composition은 그 파일 hash를 참조한다. manifest의 기존 lock hash와도 일치해야 한다. common source는 project SHA와 독립적이다. 공통 base image 입력 계산을 project 전체 SHA로 대체하지 않는다.

    load_release_source_identity는 정규화한 조합·발행 정보를 반환한다. 기존 canonical_release_payload_sha256으로 각각 composition_sha256·publication_sha256을 계산한다. 파일을 수정하지 않으며 Git·네트워크·package 명령을 실행하지 않는다. load_release_artifact_identity는 이 정보와 source_mode를 기존 결과에 additive하게 표시한다. 형식 오류는 integrity errors로 전달한다.

    repository와 publisher scope¶

    HTTPS, git@host:path.git, ssh://git@host/path.git은 소문자 host와 동일한 path를 가진 경우 https://host/path로 정규화한다. path 대소문자는 유지한다. 변환은 .git 접미사 하나와 위 전송 형식에 한정한다. 다른 SSH 사용자·인증 정보·명시적 port·query/fragment·percent escape·끝 slash·경로 탈출과 반복 .git은 실패한다. host나 repository의 별칭·redirect·GitHub 전용 경로 변환은 추론하지 않는다. registry namespace는 scheme 없는 소문자 host(선택 port)와 namespace 경로다.

    host publisher scope의 최소 데이터 형식은 다음과 같다.

    {
  "version": 1,
  "project_repository": "https://git.example/team/project",
  "deploy_repository": "https://git.example/team/deploy"
}

    validate_release_publisher_scope는 외부에서 독립적으로 신뢰를 확보한 scope와 후보의 project/deploy를 비교한다. 누락·불일치·미지원 버전은 실패하며 scope가 있는 경계에서 v2로 내려가는 것도 거부한다. root fingerprint는 기존 root 공개키에서 계산하므로 여기에 중복 저장하지 않는다. 발행자 권한은 기존 SSH CA와 principal이 소유한다. scope를 후보 checkout에서 읽어 신뢰하는 동작은 없다.

    P3-1의 host pin 설치·인증과 P3-2의 독립 launcher 인증은 아래 계약을 따른다. v3는 publisher 인증을 지원하는 supervisor 계약 3이 필요하다. publisher pin이 없는 기존 v2는 기존 root pin·인증을 유지한다.

    Host publisher pin 설치와 인증¶

    host의 /etc/furive-os/release-trust/publisher.json은 위 scope의 정규형만 저장한다. root 공개키는 CA를 인증하지만 동일 CA 아래 프로젝트·배포 대상의 허용 범위를 표현할 수 없어 이 파일이 필요하다. 기존 install_release_trust가 최초 설치를, core/release_identity.py가 형식·대조·인증을 소유한다. root fingerprint·credential·package 배정이나 runtime 설정은 중복 저장하지 않는다.

    내부 설치 입력 FURIVE_OS_RELEASE_PUBLISHER_SCOPE_FILE은 승인된 설치 전달 경로에서 확보한 scope 파일을 지정한다. 일반 사용자용 option·질문은 추가하지 않는다. 입력 파일은 설치 사용자 소유, host 파일과 디렉터리는 root 소유여야 하며 group/other 쓰기 권한과 symlink를 거부한다. 파일은 16 KiB 이하의 regular file이어야 한다. 해석·조회·module import는 pin을 설치하거나 고치지 않는다.

    설치 전 입력·기존 pin을 설치할 manifest와 대조한다. v3의 최초 입력 누락, 다른 프로젝트·배포 대상, 깨진 기존 pin과 v2로의 변경은 root/pin 쓰기 전에 거부한다. 같은 scope의 재설치는 기존 pin의 bytes와 inode를 유지한다. 최초 pin은 root:root 0644로 완성한 임시 파일을 fsync한 뒤 기존 대상을 덮지 않는 link로 게시하고 임시 파일을 정리한다. 생성 경쟁·쓰기 실패는 nonzero다. pin 쓰기 실패 전에 설치한 동일 root가 남을 수 있으며, 재실행 시 다시 검증한다. 여러 trust 파일의 원자적 동시 설치를 보장하지 않는다. 발행 CA·프로젝트 이전을 일상 재설치나 OTA가 자동 수행하지 않는다.

    require_release_tag_authenticity는 기존 CA/principal·KRL 서명을 먼저 검사하고, 인증한 exact commit의 bounded regular manifest를 Git 객체로 읽어 host pin과 비교한다. pin이 있으면 signed v2·manifest 누락으로 내려갈 수 없으며, v3는 host pin이 없거나 깨지면 실패한다. pin만 남아도 인증이 필수이고, root가 없으면 pin이나 후보 키로 대체하지 않는다. 프로젝트 manifest의 release·채널·deploy identity도 서명 태그 요청과 일치해야 한다. working manifest·origin·bundle receipt·후보의 publisher 파일은 host pin을 대신하지 못한다. validate_release_tag_authenticity는 독립 CI/bundle에서도 쓰는 서명 원시 검사이며 host pin을 설치하거나 조회하지 않는다.

    root 설치 launcher는 checkout 코드를 import하기 전에 고정 host root/KRL과 publisher pin을 독립해서 검증한다. v3 선언이나 pin만 남아도 인증을 요구하며, pin 누락·다른 project/deploy·v2 downgrade를 tracked 변경 stash보다 먼저 거부한다. checkout 파일이나 환경 입력은 설치된 launcher의 host pin 경로를 바꾸지 못한다. source 시험용 경로 치환은 설치된 경로에서 사용할 수 없다.

    publisher 인증을 포함한 현재 supervisor 계약은 3이다. v3 exporter는 기존 OTA 계약의 min_supervisor_contract: 3을 파생하며 v2의 최소 계약 2·epoch·config schema·control protocol은 바꾸지 않는다. P2 시기의 실행 차단용 v3 후보처럼 최소 계약이 2인 산출물은 runtime integrity에서 거부한다. 기존 설치 launcher 2는 v3 OTA를 준비·적용할 수 없다. 신규 v3 설치는 계약 3을 포함한 signed release로 시작한다. 기존 v2/구형 설치에서 project로의 전환은 exact release별 검증 전까지 bootstrap이 거부한다.

    v3도 기존 marker·설정 snapshot·package 종료 확인·activation·health 확정과 이전 정상판 복구를 사용한다. trust 파일은 rollback 대상에 넣지 않는다. 이 source 회귀는 실제 host 설치·재부팅이나 구형 fleet 전환·image·차량 검증을 대신하지 않는다.

    프로젝트 bundle 전달¶

    P2-6의 프로젝트 ./furive bundle은 성공한 signed release의 로컬 전달물을 만든다. 생성된 bootstrap.sh는 기존 설치 소유자에 연결한다. PC 선택·host 준비 전에 bundle publisher와 조직 SSH host key, 이미 설치된 root/pin/KRL의 충돌을 검사하고 서명된 exact commit의 publisher를 checkout import 전에 대조한다. host KRL은 bundle KRL이 생략되어도 적용한다. 기존 source에서 만드는 v2/v3/v4 bundle의 설치·PC 배정은 유지한다.

    ./furive bundle office-1 --release-pin v2026.10.21.1 \
  --release-root-public-key /trusted/team-root.pub \
  --deploy-known-hosts /trusted/deploy-known-hosts --output-dir /path/to/delivery

    조직에서 독립적으로 신뢰를 확인한 root를 명시하며, 프로젝트가 고정한 exact common·source· package·플랫폼의 clean checkout에서 실행한다. 현재 프로젝트 HEAD와 원격 source tag가 release의 source revision과 같아야 한다. 이 단위는 변경된 source에서 이전 release를 추정해 재사용하지 않는다. 출력 기본 경로는 기존 dist/credential-bundles이며 프로젝트에서 dist/를 ignore해야 한다.

    발행 대상·registry·차량 배정은 기존 프로젝트 선언과 원격 source Git 객체에서 읽는다. bundle에는 플랫폼·package·Autoware revision·설치 정책 변경 옵션을 제공하지 않는다. --release-pin과 root, 출력·KRL·기존 credential·registry 전달 인자를 사용한다. --deploy-known-hosts는 조직에서 독립적으로 확인한 deploy host의 ed25519 known_hosts 한 행을 전달한다. GitHub 고정 키로 다른 서버를 인증할 수 없어 필요한 입력이며, 자동 keyscan·새 host 상태 파일은 추가하지 않는다. 기존 installer가 FURIVE_OS_DEPLOY_KNOWN_HOSTS_FILE을 받아 기존 /etc/furive-os/known_hosts에 설치하고 repair에서 같은 publisher의 키를 유지한다. bootstrap은 FURIVE_OS_RELEASE_PUBLISHER_SCOPE_FILE을 같은 installer에 전달한다. 독립 root 인증과 signed tag의 채널 ancestry를 확인한 뒤 P2-5의 source/common 승인 reader와 offline artifact·lock·image digest· 공급망·필수 검사 validator를 다시 실행한다. package 코드나 후보 Python은 실행하지 않는다. signed report의 invocation label은 새 CI 인증이나 서명 권한으로 사용하지 않는다.

    scripts/release/project_bundle.py가 검증·전달을 소유한다. 기존 node identity 발급·peer pin 규약은 scripts/credential-bundle/node-identity.bash 한 곳을 기존 생성기와 함께 사용한다. 새 service· daemon·host 상태·project config는 없다. 전달물은 기존 bundle env v4와 manifest v3를 사용하고, release-trust/publisher.json에는 위에서 정의한 scope만 넣는다. root fingerprint를 scope에 중복 저장하지 않는다. manifest의 publisher, runtime_enabled: true, bootstrap.tag_object는 전달 범위·검증 결과를 기록하는 영수증이며 runtime 설정이나 host pin이 아니다.

    root/KRL·publisher와 signed release의 원본 검사 자료, PC·package 배정 영수증을 전달한다. 새 read-only deploy 공개키는 조직의 기존 접근권한 절차로 등록해야 하며 자동 등록하지 않는다. --reuse-git-credentials-from은 동일 차량·project/deploy scope의 프로젝트 bundle에서 deploy key만 재사용하고 node identity는 새로 만든다. --registry-env-file은 기존 FURIVE_OS_REGISTRY·username· password 세 필드를 data로 읽고 signed registry host를 대조한 뒤 shell quote해 전달한다. 사내 GitHub/Harbor·credential 환경 기본값을 읽지 않는다. Autoware source 접근·지도·image seed 추가 전달, 실제 credential 취득과 host 설치·구형 전환·복구는 이 로컬 결과의 완료 증거가 아니다.

    완성된 ZIP의 CRC·실제 파일 bytes를 확인하고 기존 출력을 덮지 않는 link로 게시한다. --keep-dir은 검토할 압축 해제본도 남긴다. 실패·취소 시 임시 credential과 이번 출력만 정리하고 기존 출력·원본은 보존한다. 마지막 source 입력·원격 source/deploy tag 이동도 대조한다. 이후 원격 서버가 바뀔 수 있으므로 실제 설치에서는 P3의 독립 host pin·signature·exact commit 인증이 다시 필요하다.

    supply-chain reader¶

    기존 source/v2의 index v1은 유지한다. v3는 index v2에서 기존 필드에 정규화한 composition_sha256·publication_sha256을 추가해야 한다. 공급망 증거는 생략할 수 없다. deploy validator는 다음을 실제 파일과 JSON 결과로 대조한다.

    • manifest→index→SBOM/provenance의 기존 파일 hash와 immutable image subject 집합.
    • 실제 package-lock 파일의 SHA-256과 조합이 참조한 hash.
    • index의 조합·발행 hash, SLSA build definition의 externalParameters.compositionSha256와 publicationSha256.
    • provenance의 project source subject: name: git+<정규 repository>와 digest.gitCommit.
    • resolvedDependencies의 project/common/platform 세 record. 각각 uri: git+<정규 repository>와 digest.gitCommit을 갖고, platform만 digest.gitTree·annotations.path를 추가한다. 순서는 무관하나 누락·추가·중복 수 차이는 실패한다.

    project SHA가 같아도 common·플랫폼·배포 repository·registry가 바뀌면 이전 증거를 재사용할 수 없다. index를 다시 해시해도 잘못된 dependency·다른 project repository·누락된 publication hash는 실패한다. manifest의 두 새 필드를 지워도 남은 project index를 v2 증거로 읽지 않는다.

    P2-4 generator는 아래 envelope와 별도로 전달한 필수 검사 목록이 일치할 때만 로컬 v3 후보 증적을 생성한다. 입력 오류는 기존 출력을 쓰기 전에 거부하고 쓰기 오류는 기존 후보 파일을 복구하며 실패한다. 이 reader는 실행자 인증·보호된 CI 승인·source tag 이동 검증이나 source evidence cache의 project 결박을 대신하지 않는다. 기존 v2 공식 signer와 source evidence cache는 project publisher에 재사용하지 않는다. 독립 승인 common의 보호된 project 서명·게시·전달 인증은 아래 계약을 따른다.

    외부 검사 envelope와 고정 subject¶

    형식과 검증의 소유자는 core/ota/validation_evidence.py다. 조직 CI가 기존 검사 결과와 필요한 검사 목록을 제공하고 기존 supply-chain generator/validator가 같은 함수를 사용한다. 새 service·daemon· 영구 상태·조직 release lock은 없다. 공통 runner가 지원하지 않는 언어의 빌드 도구를 설치하거나 report에 적힌 명령·경로의 프로그램을 실행하지 않는다.

    CI adapter는 필수 검사 목록을 report와 별도 입력으로 generator에 전달한다. 내부 --validation-requirements 인자는 이 목록의 JSON 경로이며 공개 사용자 명령을 추가하지 않는다. 원본은 조직이 검토한 CI/revision이다. 후보 안의 목록이나 origin 일치를 승인으로 사용하지 않는다. 파일 형식은 {"checks": [...]}이며 각 항목은 다음 다섯 필드만 갖는다.

    {
  "id": "sample-tests",
  "kind": "package-test",
  "package": "package/plugin/sample",
  "verifier": "organization-ci",
  "invocation": "reviewed-workflow-revision/run-123/attempt-1"
}

    id는 중복 없이 검사 하나를 식별한다. kind는 contract, package-test, rc-semantic, device다. 전체 공통 계약 검사(contract, 빈 package)와 package-lock의 모든 package에 대한 package-test가 최소 요구다. 추가 RC·장치 lane과 실행 identity는 조직의 검토된 목록이 결정하며 다른 lane의 PASS로 대체할 수 없다. package가 있으면 lock에 있는 정확한 path여야 한다. verifier와 invocation은 비어 있지 않은 문자열이며 각각 실행자와 exact 실행/attempt를 표현한다.

    release/validation/envelope.json은 version: 1, subject, checks만 갖는다. 각 check는 위 다섯 필드에 format, path, sha256을 추가한다. 필수 목록과 항목 수·종류·package·실행자가 정확히 일치해야 하며 report bytes의 SHA-256을 대조한다. 지원 format은 다음과 같다.

    format 검사하는 관측
    junit UTF-8 JUnit의 실제 testcase 수와 testsuite 선언 수가 일치하고 1건 이상. failure/error/skipped 없음. DTD/entity 금지.
    package-json 기존 native runner schema v2의 전체 lock inventory, 시작·종료 clean exact HEAD와 동일 source 상태, package/suite 성공 및 Python JUnit·Node TAP 건수. 부분/빈/실패/timeout report 거부.
    typed 외부 언어 CI의 아래 명시적 검사·assertion 수와 결과. RC·장치 검사는 probe 관측도 요구.

    native shell suite는 exit status만 기록하므로 그 report만으로 assertion 증거로 승격하지 않는다. 해당 조직 CI가 JUnit 또는 typed 결과로 실제 assertion 관측을 함께 제공해야 한다. 기존 shell runner의 개발/공식 v2 경로는 변경하지 않는다. JUnit만으로 RC·장치 probe를 대체하지 않는다.

    {
  "version": 1, "status": "passed", "tests": 2, "assertions": 3,
  "failures": 0, "errors": 0, "skipped": 0, "timed_out": false
}

    typed 수는 bool이 아닌 정수다. tests/assertions는 양수이고 실패·오류·skip은 0이어야 한다. RC·장치 typed report는 추가 probes 배열을 요구하며 각 항목은 중복 없는 id, status: passed, 비어 있지 않은 문자열 observed를 갖는다. tests/assertions가 probe 수보다 적으면 실패한다. probe의 기능적 정확성과 실행 사실은 조직의 검사와 이후 인증이 소유하며 report reader가 보증하지 않는다.

    subject는 최종 manifest hash를 포함하지 않는다. 아래 값을 먼저 고정하고 검사한 뒤 envelope에 넣는다.

    • version: 1, 정규화한 composition_sha256, publication_sha256.
    • locks: 실제 package-lock.yaml, image-digests.yaml bytes의 SHA-256.
    • payload_sha256: 아래 effective inventory를 {"files": inventory}로 감싼 기존 canonical hash.

    기존 release/deploy-assets.yaml의 새 effective_payload는 파일 path·mode·SHA-256, 디렉터리 path·mode, 내부 symlink의 path·mode·target을 담는다. 모든 생성 deploy 파일을 대상으로 하므로 플랫폼·Autoware lock·config·실행 파일·신규 파일·삭제와 권한 변경도 결박한다. 원본 밖·깨진·순환 symlink와 증적 파일을 실행 payload에 연결하는 symlink는 거부한다. inventory 계산에서 제외하는 것은 루트 Git metadata와 정해진 SBOM/provenance/index, release/validation/의 검사 파일뿐이다. manifest는 supply_chain, supply_chain_sha256만 제외한 canonical object를, deploy-assets는 effective_payload만 제외한 canonical object를 hash한다. 다른 manifest 변경은 재검사가 필요하다.

    generator가 inventory와 report descriptor를 기존 index v2의 validation에 결박하고 최종 manifest가 index를 hash한다. validator는 inventory 저장 여부와 현재 파일을 다시 대조한다. 증적 준비 중 subject가 움직여도 실패한다. 이 순서로 재생성 결과가 같고 최종 manifest와 report의 순환 hash가 생기지 않는다.

    상한은 report/JSON 파일별 8 MiB, envelope와 고유 report 총 16 MiB, checks 128개, 검사 건수 및 assertion 각 1,000,000개, payload entry 100,000개다. report 경로는 release/validation/ 바로 아래의 영문·숫자·_·- 이름과 .json/.xml만 허용한다. envelope 포함 고유 파일 수도 128개까지다. symlink·경로 탈출·미등록 report·하위 디렉터리·중복 JSON key와 중복 check는 거부한다. payload 파일은 전체를 메모리에 적재하지 않고 나누어 hash한다.

    validate_index에 외부에서 검토한 필수 목록을 전달하면 index가 자체 목록·invocation을 바꾸어 재해시해도 거부한다. offline 기본 reader가 후보 안의 목록과 label을 대조하는 것은 전달 인증이 아니다. P2-5의 보호된 경로는 승인 repository/revision과 허용 CI 실행에서 그 목록과 report가 왔는지 독립 확인한다. 로컬 구조 검증 PASS를 신뢰된 build·실제 image·서명·설치 PASS로 사용하지 않는다. 프로젝트의 직접 로컬 서명·게시 차단은 유지한다. 공개 --run은 아래 조직 CI 요청만 수행한다. v2/index v1은 기존 경로를 사용한다. P2-1의 검사 증적 없는 index v2 fixture는 이제 발행 후보 검증을 통과하지 못한다.

    호환과 다음 경계¶

    이번 reader는 기존 OTA epoch·config schema·control protocol과 v2 catalog/route 의미를 바꾸지 않는다. 기존 정상판에서 v3로 전환할 때는 해당 release의 installer/supervisor reader와 복구 경계를 확인해야 한다. 이 source 시험을 구형 실배포판→v3 OTA 가능 증거로 사용하지 않는다.

    P2-3은 아래 조직 입력·계획 조회와 로컬 export 후보를, P2-4는 후보 증적 생성을 지원한다. P2-5의 내부 CI 경로는 아래 보호된 서명·게시 계약을 사용한다. P2-6은 로컬 bundle 전달, P3-1은 host pin 소유자와 updater 인증을, P3-2는 bootstrap/launcher와 v3 activation의 source 경계를 연결한다. 실제 운영 검증과 exact 구형 release별 전환은 남는다.

    조직 입력과 발행 계획¶

    프로젝트의 기존 furive-project.yaml에 선택 publication을 선언한다. 프로그램 연결·실행에는 필수가 아니며, 프로젝트 발행 계획에는 필요하다. 플랫폼 제공자의 config가 조직의 발행 대상을 결정하지 않도록 프로젝트 descriptor가 원본을 소유한다.

    version: 1
common: toolchain/furive-os
publication:
  version: 1
  source_repository: https://git.example/team/project
  deploy_repository: git@git.example:team/deploy.git
  registry_namespace: registry.example/team

    publication은 위 네 필드만 받는다. repository와 registry는 앞 절의 정규화·자격증명 금지 규칙을 그대로 사용하며 누락·잘못된 버전·알 수 없는 필드·중복 YAML key는 실패한다. descriptor의 기존 일반 파일·64 KiB 제한도 유지한다. publication 없는 version 1 프로젝트는 기존 개발 경로를 유지한다. 새 필드를 사용하는 프로젝트에는 P2-3 이상 common이 필요하다. 이전 common으로 복귀할 때는 그 reader가 지원하는 프로젝트 revision을 함께 선택하며, 알 수 없는 필드를 무시해 실행하지 않는다.

    프로젝트 루트에서 기존 명령으로 계획을 조회한다.

    ./furive release normal --date 2026-10-21 --number 1
./furive release normal --date 2026-10-21 --number 1 --json
./furive release test office-1 --date 2026-10-21 --number 2 --json

    test는 기존 fleet에서 test 업데이트를 배정한 차량만 허용한다. 플랫폼·Autoware 선택·architecture와 normal 승인 세대는 기존 플랫폼·차량·deploy-targets 원본에서 파생한다. test의 플랫폼은 해당 차량의 배정이며 main의 기본 플랫폼으로 바꾸지 않는다. architecture는 CI의 기존 resolver와 같은 core/ota/targets.py를 사용한다. normal 계획은 기존 플랫폼 승인 정책도 검사한다.

    계획은 exporter의 exact Git·gitlink·원격·추적 bytes·경로 검사를 쓰되 snapshot을 만들지 않는다. project origin은 publication.source_repository와 같아야 한다. package 명령·Git 원격 조회·OCI·CI 호출 없이 읽으며 원본·index·overlay·이전 출력은 수정하지 않는다. 필요한 선언·checkout·built asset이 없거나 dirty이면 대상 경로·원인과 다음 행동을 stderr/nonzero로 반환한다. 계획에 필요한 명시적 ignored built asset도 준비해야 하지만 그 존재가 신뢰된 build 증명은 아니다.

    JSON은 source commit, composition_inputs, publication, package source, architecture, Autoware 선택, tag 대상과 publication_enabled: false(로컬 직접 게시 미지원)를 반환한다. composition_inputs는 아직 package-lock hash가 없는 export 입력이며 최종 v3 manifest·검증 PASS·서명 승인으로 사용할 수 없다. --json은 기존 CLI의 기계 조회 표현을 release 계획에도 제공하며 새 실행 정책이나 상태를 만들지 않는다.

    ./furive release ... --run은 아래 조직 CI 요청을 수행한다. 내부 publisher의 execute/push/publish-tags는 같은 요청 소유자로 전달하며 세 인자를 함께 사용해야 한다. 프로젝트를 내부 도구로 직접 호출해도 공식 발행 경로로 fallback하지 않는다. 계획에는 사내 주소·remote·runner fallback이 없으며, 명시 remote/workflow override로 다른 대상을 선택할 수 없다.

    runner·CI 작업 그래프·승인·접근권한은 조직 CI가 소유한다. 공통 project 파일에는 runner label이나 임의 명령을 추가하지 않는다. 조직 CI 예시는 선택한 exact 입력을 준비한 조직 runner에서 같은 공개 CLI를 실행한다. report는 source 밖 runner 임시 경로에 저장하고 실패하면 이전 report와 부분 출력을 제거한다. 이 예시의 실행 절은 합성 Git fixture로 검증하며 실제 외부 CI 실행·발행 증거는 아니다. 다른 CI도 같은 JSON/nonzero를 사용할 수 있으며 공통 해석기에 GitHub API·Harbor API가 필요하지 않다.

    기존 공식 v2 workflow와 signer는 구형 fleet 전환을 위해 유지한다. project 전용 workflow는 독립 승인 common의 publisher를 사용한다. source origin 일치만으로 보호된 승인과 후보 결박을 대신하지 않는다. 각 경계와 필요한 조직 입력은 보호된 프로젝트 서명과 게시를 따른다.

    프로젝트 export 후보¶

    내부 exporter는 기존 scripts/release/export-deploy-repo.sh다. 공개 프로젝트 ./furive release는 계획을 조회하고 --run으로 조직 CI에 요청한다. 로컬에서 직접 서명하거나 게시하지 않는다. 내부 호출의 --project-root는 본체 root만 알던 exporter에 프로젝트 선택을 전달하고, publication이 있으면 deploy 주소·registry·architecture는 위 원본에서 파생한다. 기존 명시 인자는 정규화 후 원본과 같아야 하며 다른 host·namespace·architecture는 실패한다. shell의 사내 기본값· registry/branch/architecture 환경값으로 프로젝트를 변경하지 않는다. publication 없는 P2-2 후보는 기존처럼 --deploy-repository와 명시적 --registry·--project가 모두 필요하며 계획 조회는 지원하지 않는다. 이 호환 경로는 P2-2 로컬 자동화에 한정한다. 후보에 입력한 주소는 인증된 발행 권한의 증거가 아니며, export는 네트워크 발행·서명·설치를 하지 않는다.

    core/ota/project_export.py는 P1의 project/common·inventory·플랫폼 해석 결과로 임시 snapshot을 만든다. 기존 exporter가 이 snapshot에서 같은 deploy 배치·package lock·이미지 선택·assets·Autoware lock을 생성한다. 공통 checkout의 package 전체와 조직 설정을 자동 수집하지 않는다. core는 기존 동일 슬롯 symlink 승인을 유지하고 plugin은 승격하지 않는다. common base image identity 계산도 그대로 쓴다.

    입력은 clean한 프로젝트 자체 Git 저장소와 프로젝트에 추적된 tree 또는 exact gitlink다. 독립 checkout은 부모 commit의 gitlink SHA·.gitmodules URL과 실제 HEAD·origin을 대조한다. 프로젝트 origin은 입력 식별이며 승인된 원격임을 인증하는 것은 아니다. 미등록·미준비 checkout, dirty·이동한 SHA·다른 source ref, 외부 fleet/package 환경 입력을 거부한다. 파일 bytes·실행 mode와 Git blob도 대조해 assume-unchanged로 가린 변경을 거부한다. LFS materialized bytes는 추적 pointer의 SHA-256·size와 비교한다.

    플랫폼 identity는 프로젝트 config/가 선택한 실제 repository subtree의 commit·path·tree다. 개별 config 파일은 이 subtree 안에 있어야 한다. P1 개발 조회에서 허용하는 여러 원본의 개별 파일 링크를 한 platform identity로 표시하지 않으며, export에는 하나의 subtree로 준비해야 한다. 프로젝트의 기존 deploy-targets가 필요하며 Autoware 미선택은 빈 inventory로 파생한다. 개발 overlay·로그·validation receipt를 배포하지 않는다. main은 normal에 등록된 차량의 기존 Autoware selector를 사용하고 해당 차량이 없으면 명시된 기본 플랫폼을 사용한다. test는 등록된 해당 차량의 selector를 사용한다. 선택한 대상의 lock은 필수이며 선언된 모든 lock은 검증한다. Autoware build 검증은 계속 not_performed이며 source lock만 내보낸다.

    추적된 내부 링크는 선택한 원본 경계 안에서 해석해 일반 파일로 복사한다. 원본 밖·패키지 사이 탈출과 순환 링크는 실패한다. 무시된 파일은 자동 수집하지 않으며 deploy.built_assets가 명시한 무시된 빌드 결과만 추가한다. 이 생성 bytes는 후보 입력이다. P2-4가 검사 대상을 결박하고 P2-5가 전달을 인증하기 전 신뢰된 build 증명으로 사용하지 않는다. 공유 ROS runtime도 기존 명시적 release-built 입력과 architecture/source marker를 사용한다. 최종 deploy의 inventory와 source lock을 선택 입력과 대조하고 설치 위치 밖 symlink를 거부한다.

    프로젝트 출력은 원본 밖의 새 경로에만 생성하며 기존 경로·다른 작업의 출력은 지우지 않는다. 실패하면 자신이 생성한 부분 출력과 임시 snapshot만 정리한다. 원본·index·overlay는 수정하지 않는다. v3 후보의 composition은 실제 package-lock hash를 참조한다. 기존 digest pinning도 source identity와 registry를 먼저 확인한 뒤 lock hash를 함께 갱신하며, 증적 작성 뒤 재고정은 거부한다. 증적 generator는 P2-4 envelope와 별도 필수 목록을 요구한다. runtime은 host publisher 인증과 supervisor 계약 3·기존 activation의 검사를 별도로 요구한다. 따라서 후보 export 성공은 release 검증·독립 발행·구형 설치본의 v3 전환·실차 PASS를 뜻하지 않는다.

    보호된 프로젝트 서명과 게시¶

    P2-5의 CI 요청·서명·게시 구현은 scripts/release/project_publication.py가 소유한다. 일반 사용자는 기존 ./furive release로 계획을 확인하고 --run으로 조직 CI에 요청한다. 기존 공식 signer·source evidence cache를 프로젝트에 재사용하지 않는다. 조직 CI는 runner·작업 그래프·승인·접근권한을 소유하고, 공통 도구는 승인된 Git 입력·검사·서명·게시 결과를 판정한다. 이 구현의 로컬 시험은 실제 외부 CI의 Environment 보호나 조직 권한 구성을 완료했다는 증거가 아니다.

    보호된 job은 후보와 별도로 승인 source repository·exact commit·release tag와 common commit, 허용 run/attempt/artifact ID를 고정한다. 독립적으로 설치한 clean common 도구를 python3 -I -B로 실행하며 프로젝트의 common gitlink·추적 URL과 실제 validator revision/bytes를 대조한다. 후보에서 validator·Git config·hook·replace ref·credential helper를 가져오지 않는다. 서명용 CA certificate·private key와 deploy write agent는 build job에 제공하지 않는다. 보호된 runner의 SSH agent는 필요한 repository에만 권한을 갖고 known_hosts를 사전 고정한다. host key 오류를 우회하지 않는다.

    필수 검사는 승인 프로젝트의 release/validation-policy.json 한 곳이 소유한다. P2-4의 CI 인자만으로는 report가 자기 요구 조건을 바꿔 재해시하는 경우를 signer가 독립 확인할 수 없어 이 검토 원본이 필요하다. 새 project 필드·runtime 상태·daemon은 추가하지 않는다. 조직 CI 담당자는 다음 작은 형식만 배운다.

    {
  "version": 1,
  "workflow": ".github/workflows/build.yml",
  "event": "workflow_dispatch",
  "checks": [
    {"id": "contract", "kind": "contract", "package": ""},
    {"id": "sample", "kind": "package-test", "package": "package/plugin/sample"}
  ]
}

    checks는 1~128개이고 선택 package 전체를 포함한다. kind·package·assertion의 P2-4 규칙을 그대로 사용한다. 임의 명령은 받지 않는다. workflow는 승인 revision에 존재하는 .github/workflows/*.yml, event는 push 또는 workflow_dispatch다. verifier는 canonical source URL에 /workflow-path@source-SHA를 붙인 문자열, invocation은 run_id/attempt로 파생한다. build job은 이 값으로 P2-4 envelope와 별도 필수 목록을 생성한다. 별도 CI에서 수행한 장치 시험은 이 승인 workflow가 전달·검증 책임을 맡아야 하며, 서로 다른 label만 나열한 report를 인증된 결과로 승격하지 않는다.

    GitHub adapter는 TLS API에서 repository/head repository·exact workflow/revision·event·성공한 run/attempt와 artifact의 run·source·repository ID·생성 시각·만료·SHA-256을 확인한다. artifact 이름은 furive-project-<run_id>-<attempt>이고 ID는 보호된 job이 선택한다. download redirect에는 API token을 전달하지 않는다. GitHub artifact API와 workflow run API의 응답을 사용하며, report 안의 JSON receipt·성공 label을 인증으로 받지 않는다. 다른 CI는 조직이 승인한 인증 adapter에서 받은 bytes를 같은 공통 unpack/validation/publication 함수에 전달한다. 현재 제공 CLI adapter는 GitHub용이다.

    build job은 export→digest 고정 뒤 최종 Git 표현과 같은 파일 0644/0755·디렉터리 0755에서 검사하고 증적을 생성한 다음 deploy를 commit한다. 이후 mode·파일·설정을 바꾸면 재검사한다. Git이 보존하지 않는 group-write bit나 빈 디렉터리를 증적에 포함하면 handoff 검사는 실패한다. prepare는 이를 정상화해 PASS로 바꾸지 않는다. 내부 CI의 prepare --deploy-dir <committed-deploy> --output <new.zip>은 관측한 deploy branch HEAD와 exact commit을 handoff.json에 넣고 refs/heads/candidate 하나의 deploy.bundle과 묶는다. build job은 결과 ZIP을 풀고 두 파일을 artifact 루트로 업로드한다 (ZIP 자체를 파일로 업로드하면 중첩 archive가 되어 signer가 거부한다). 기존 출력은 덮지 않으며 실패 시 자신이 만든 부분 출력만 제거한다. build의 credential은 source/deploy read·registry build 범위다.

    보호된 publish는 source tag를 별도 원격에서 가져와 commit을 확인하고 descriptor·policy·package와 platform pin을 Git blob/tree로 읽는다. 외부 입력은 .gitmodules의 exact gitlink만 따라가며 checkout이나 package 실행을 하지 않는다. 후보 ZIP은 위 두 일반 파일만 허용한다. bundle 512 MiB, payload 2 GiB· 10만 파일, JSON policy/descriptor 64 KiB, source 경로 추적 32단계·128 repository와 기존 report 상한을 적용한다. 임시 data projection은 relative symlink·gitlink도 거부하며 script를 실행하지 않는다. 공통 offline metadata/profile/migration·image digest·supply-chain reader와 독립 필수 목록을 실행한다. 실제 image/장치 기능은 해당 필수 report의 책임이며 signer가 image를 시작하지 않는다.

    서명은 기존 Ed25519 CA·channel principal·archival certificate·KRL reader를 사용한다. source tag의 object와 commit을 게시 직전 다시 확인한다. normal은 기존 플랫폼 generation 정책을 읽고 기존 release target의 서명·normal ancestry·지원 플랫폼을 확인한다. generation replay와 immutable release tag 충돌은 거부한다. test는 등록된 차량의 preview branch와 test principal만 사용한다. 정확한 branch lease와 새 tag 부재 lease를 한 git push --atomic에 넣고 원격 ref를 재확인한 후에만 status: published를 반환한다. atomic 미지원·경쟁 writer·통신 실패는 nonzero다. 응답이 유실되어도 자동 재전송하지 않고 관측한 원격 상태와 다음 확인 행동을 남긴다. source/deploy 두 저장소를 한 transaction으로 묶지 못하므로 source 최종 확인과 deploy push 사이의 이동 가능성은 남는다.

    내부 publish 입력은 --source-repository, --source-commit, --release, --common-commit, --run-id, --attempt, 선택 --artifact-id, --signing-certificate, --root-public-key, --revocation-krl이다. artifact ID를 생략하면 인증된 API의 해당 run artifact 목록(최대 100개)에서 exact run/attempt 이름의 유일한 ID를 선택한다. 누락·중복·부분 목록은 거부하며 선택 뒤에도 기존 run/attempt/hash 인증을 모두 수행한다. 인증 token은 보호된 job의 GH_TOKEN, Git/서명 agent와 신뢰 파일은 독립 CI 준비물이다. 내부 인자는 source/common과 검토 revision·실행을 분리해 표현하기 위한 것이며 일반 사용자 명령이나 두 번째 publication 설정 원본이 아니다. 실제 조직의 권한·runner 준비·외부 immutable test release·bundle/host pin· v3 설치/OTA·구형 release별 복구·실제 image/host/장치/차량 확인은 별도 완료 증거가 필요하다.

    공개 요청과 조직 CI 연결¶

    프로젝트에서 계획을 확인하고 조직 CI에 요청한다. 먼저 exact 프로젝트 commit과 등록된 dependency를 조직의 원격에 올려야 한다. 이 명령은 작업 중인 source commit이나 dependency를 대신 push하지 않는다.

    ./furive release normal --date 2026-10-21 --number 1
./furive release normal --date 2026-10-21 --number 1 --run
./furive release test office-1 --date 2026-10-21 --number 2 --run

    첫 요청 adapter는 GitHub source와 표준 Git/OCI 배포 대상을 지원한다. 기존 policy의 workflow와 event를 읽고 package 전체의 필수 검사를 같은 evidence 소유자로 사전 검사한다. policy·workflow의 dirty·숨긴 bytes 변경·누락, 미지원 source host, 잘못된 event를 원격 쓰기 전에 거부한다. workflow_dispatch는 GH_TOKEN의 source Actions write 권한과 default branch에 등록된 active workflow가 필요하다. 선택 revision의 workflow도 policy event를 선언해야 한다. API token은 SSH/Git credential이 아니며 Git transport는 scoped SSH agent와 사전 고정한 known_hosts를 사용한다.

    원격 source의 exact commit을 private bare 저장소로 fetch한다. source/deploy의 같은 immutable tag, 같은 이름의 source branch, 이전에 실제 deploy에 게시한 release 이후 deploy 영향 없는 변경을 거부한다. 과거 tag cache를 믿지 않고 원격 tag와 기존 deploy 영향 소유자를 사용한다. 빈 ref lease와 atomic push로 source tag 하나만 만들고 다시 조회한다. 요청별 nonce를 annotated tag 메시지에 넣어 동일 commit의 동시 요청도 서로 다른 tag object로 경쟁하게 한다. 같은 object의 push가 no-op이 되어 빈 lease를 우회하는 경우를 막기 위한 것이며 새 runtime 상태나 config가 아니다. source commit identity는 유지한다. 로컬 checkout·index·tag·branch·원격 설정은 바꾸지 않는다.

    workflow_dispatch는 해당 tag를 ref로 API 요청한다. 응답 204를 받은 경우 status: requested이며, push policy는 tag 관측만 확인한 status: source_tagged다. 둘 다 publication_complete: false와 source SHA·release·workflow·CI 주소를 반환한다. 종료 코드 0은 해당 요청 단계 성공이며 게시 완료가 아니다. 빌드 실패·서명 승인 대기·서명 실패·최종 게시 결과는 해당 CI 실행에서 확인한다. 보호된 signer만 서명·원격 ref 확인 후 status: published를 반환한다.

    push/dispatch 실패는 stderr/nonzero다. source tag가 만들어진 뒤 실패하거나 응답이 유실되면 tag를 삭제하거나 자동 재전송하지 않는다. 오류에 남긴 CI 주소와 원격 ref를 확인한 뒤 조직 CI에서 수동 dispatch 여부를 결정한다. 같은 source tag로 --run을 반복하면 거부한다. 조직 workflow는 policy와 같은 event 하나로 release 빌드를 시작하도록 구성해 tag push와 dispatch의 이중 실행을 피한다.

    공식 project 전용 연결은 build workflow와 protected publish workflow다. 호환되는 복사본은 build 예시와 publish 예시다. 프로젝트 root의 정책은 조직이 검토한 build workflow 경로를 가리켜야 한다. 이 저장소의 일반 source root는 project root와 독립 승인 common gitlink가 준비되기 전까지 발행 구성이 아니다. build는 서명·deploy write 권한이 없는 별도 runner에서 실행한다. 내부 build-inputs는 exact source tag·SHA와 정책에서 release·deploy branch·common SHA·필수 목록을 파생하며 실제 run/attempt를 verifier/invocation에 넣는다. 출력과 report는 runner 임시 경로에 둔다. 예시의 ci/build-validated-deploy.sh는 조직이 제공할 실제 빌드·시험 구현이며 공통 Furive가 실행하는 새 설정 언어나 제공되는 sample PASS script가 아니다. 인자는 inputs JSON·requirements JSON·deploy 출력 경로다. 조직 구현은 기존 exporter→digest pinning→ 최종 Git 표현의 실제 시험→P2-4 증적→deploy commit을 완료해야 한다. 없거나 실패하면 업로드하지 않는다.

    빌드 성공 뒤 별도 workflow_run job이 독립 runner와 보호된 project-release-signing Environment에서 실행된다. 같은 run 안에서 signer를 실행하지 않는다. artifact 인증은 완료된 성공 build run을 요구한다. signer는 source checkout·candidate cache를 사용하지 않고 독립 common 도구와 API artifact reader를 쓴다. Environment의 FURIVE_APPROVED_SOURCE_REPOSITORY, FURIVE_APPROVED_SOURCE_COMMIT, FURIVE_APPROVED_RELEASE, FURIVE_APPROVED_COMMON_COMMIT은 빌드 출력과 별도로 검토한 기존 publish 인자의 승인 값이다. publication 주소·필수 검사 원본을 복사한 새 config가 아니다. FURIVE_TRUSTED_COMMON_ROOT와 signer certificate/root/KRL 경로는 조직이 독립 공급한 runner 준비물이다. native 검증 runner에도 독립 검토한 같은 FURIVE_APPROVED_COMMON_COMMIT을 제공한다. native 단계는 공급 checkout의 HEAD를 승인 값으로 삼지 않고 실행 전 승인 SHA와 clean 상태를 확인한다. 보호된 signer는 이 값을 source gitlink와 별도로 다시 대조한다. 두 runner의 격리·필수 리뷰·scoped agent와 read/write 권한은 조직이 준비·검증해야 한다. YAML 예시를 복사한 사실이나 로컬 API 대역 시험이 이 운영 조건을 증명하지 않는다.

    GitHub의 dispatch API와 workflow_run event 계약을 사용한다. 이 CI 연결은 host trust를 설치하지 않는다. 설치·runtime 인증은 위 host publisher 계약이 소유한다.
