    PC 시간 동기화¶

    Furive 설치는 chrony를 호스트 시간 보정의 단일 소유자로 준비한다. 새 사용자 명령이나 시간 서버 주소 설정을 추가하지 않는다. 확인은 기존 furive system status와 furive status를 사용한다. 구현은 core/time_sync.py, 설치는 core/installer/10-host-foundation.bash가 소유한다.

    인터넷 연결에 따른 동작¶

    1PC에서는 같은 호스트의 시계를 함께 사용한다. 외부 NTP를 사용할 수 있으면 chrony가 그 기준으로 보정하고, 사용할 수 없으면 로컬 시간·마지막 보정 추정을 유지한다. 아래 상대 PC를 통한 표본 전달은 PC가 여러 대인 분산 구성에 적용된다.

    연결 상태 시간 기준
    양쪽 PC가 외부 시간 서버 사용 가능 각 PC의 기존 chrony NTP 설정을 우선 사용
    A-ECU만 외부 시간 동기화됨 인증된 PC 연결로 HMI-ECU에 시간 표본 전달
    HMI-ECU만 외부 시간 동기화됨 HMI-ECU의 외부 시간 표본으로 A-ECU도 보정
    둘 다 외부 시간 서버 사용 불가 설치가 지정한 main 역할의 로컬 시각을 차량 내부 기준으로 사용
    PC 연결도 끊김 chrony가 마지막 주파수 추정으로 진행. 상대 시간은 미확인으로 표시

    PC 역할과 실제 장비 이름은 기존 설치 배정을 따른다. 새 역할 선출이나 PC 두 대 고정을 추가하지 않는다. 여러 부가 PC가 외부 기준을 제공하면 먼저 선택한 유효 공급자를 유지하고 15초간 표본이 없을 때 다른 공급자를 선택한다. main은 자체 외부 기준을 가진 부가 PC의 표본만 받는다. 부가 PC는 main만 따르므로 서로의 보정 결과를 계속 되먹이는 순환을 만들지 않는다.

    연결이 반복해서 끊겼다 돌아와도 시간 서비스를 재시작하거나 시각을 즉시 바꾸지 않는다. 짧은 단절 동안은 chrony의 마지막 보정과 주파수 추정을 유지한다. 외부 서버 재조회와 기준 선택은 chrony가 계속 담당하며, 복구 시 유효한 표본을 확보한 뒤 아래의 속도 제한으로 보정한다. 인터넷 연결 직후 동기화가 완료되는 것은 아니다. Furive는 매 관측의 기준·보정 상태를 평가하므로 한 번 오프라인 기준을 사용했다고 그 기준에 고정되지 않는다.

    외부 기준, 차량 내부 기준, 보정 중, 미확인은 구분한다. source는 직접 외부 기준·상대 PC·로컬 기준을, scope는 관측한 시간 기준의 출처를 나타낸다. 인터넷 접속 여부 자체를 나타내는 필드는 아니며, 짧은 단절 중에도 chrony가 마지막 외부 기준을 유지할 수 있다. 상대 PC 관측이 오래되면 그 표본의 출처는 미확인으로 표시한다. 인터넷이 없는 차량 내부 동기화는 정확한 UTC를 보장하지 않는다.

    기존 통신과 자원 사용¶

    별도 NTP 서버 포트를 열지 않는다. 기존 mTLS node heartbeat에 네 개의 시각과 한 개의 교환 ID를 추가하고, 인증 완료된 연결에서만 사용한다. PC 탐색·유선/Wi-Fi 선택·같은 IP 재연결은 기존 node control이 계속 소유한다. 새 credential을 배포하거나 package에 host key를 주지 않는다.

    왕복 지연과 서버 처리 시간을 분리해 상대 시각 차이를 계산한다. 왕복 전송 지연 100 ms 초과, 15초 초과 표본, 측정 중 시각 점프, 비정상 숫자, 60초 초과 차이, 일치하지 않는 교환 ID는 보정에 쓰지 않는다. 연결마다 미완료 교환 한 개와 완료 표본 한 개만 유지하며 재연결 때 폐기한다. 관측 거부와 chrony 전달 실패는 상태에 남긴다. 차량 명령은 이 경로에서 호출하거나 재전송하지 않는다.

    chrony의 공식 SOCK 입력(/run/chrony/furive.sock)으로 표본만 전달한다. node 프로세스에는 시각 설정 권한이나 chrony 관리 명령 권한을 주지 않는다. 기존 heartbeat 주기(기본 5초)를 사용하고, chrony 조회는 PC별 15초 간격·0.5초 timeout, SOCK 전송은 0.1초 timeout이다. 새 스레드·상태 파일·전체 ROS graph 주기 조회는 없다. 통신량은 heartbeat별 작은 JSON 객체 하나이며 로깅이나 업로드를 A-ECU로 옮기지 않는다. 실차 CPU·메모리 영향 측정은 별도 검증이다.

    시각 점프 방지와 설치¶

    chronyd -R로 최초 실행·재시작 때의 startup step을 억제하고 보정 속도를 최대 1000 ppm (시계 진행 속도의 0.1%)으로 제한한다. chronyc makestep, date -s 등 즉시 변경 명령을 호출하지 않는다. 예를 들어 1.8초 차이는 이 상한에서도 약 30분 이상 걸릴 수 있다. 차이가 250 ms 이상이거나 보정 불확실성이 크면 정상으로 숨기지 않는다. 시간 오류로 Autoware, 로깅 등 다른 패키지를 재시작하거나 health 재시작 횟수를 소모하지 않는다.

    기존 /etc/chrony/chrony.conf의 시간 서버·운용 설정을 보존한다. Furive는 /etc/chrony/conf.d/furive.conf와 /etc/systemd/system/chrony.service.d/furive.conf만 생성한다. 표준 Ubuntu chrony include가 없거나 무제한 step·상한 초과 slew 정책이 있으면 충돌을 보고하고 설치를 실패시킨다. chrony 신규 설치는 임시 runtime mask로 패키지의 조기 시작을 막고, 구성 뒤 자신이 만든 mask만 해제한다. chrony 서비스 실패는 systemd의 5초 재시도로 복구한다.

    서비스 시작 후 표본 socket만 실행 그룹 소유·0660으로 설정한다. /run/chrony의 그룹과 탐색 권한을 맞추며 기존 chrony command socket의 소유권·쓰기 권한은 유지한다. Docker 패키지에 표본 socket을 mount하지 않는다. chrony의 기본 AppArmor 경로 안에서 동작한다. 서비스 활성화 성공과 실제 동기화 성공은 별개다. 설치·설정·서비스 실패는 설치 호출자에게 전달한다.

    신규 설치와 기존 furive setup --repair가 호스트 구성을 적용한다. 기존 PC에 소스나 OTA만 갱신해도 chrony가 자동 설치되었다고 간주하지 않는다. 준비되지 않은 PC는 미확인으로 표시되며, 호스트 준비는 정비 시 설치 경로에서 수행한다. 일반 제거는 기존 공유 호스트 패키지 보존 규약에 따라 chrony와 시간 설정을 남긴다. 차량 배포에는 새 signed release와 그 release의 설치 묶음이 필요하다.

    검증 범위¶

    • tests/core/test_time_sync.py: 계산·지연·시각 점프·교환 재사용 거부, 인터넷 연결 조합, 같은 실행 인스턴스에서 반복하는 기준 변경·PC 관측 단절과 복구, 실제 임시 Unix socket 메시지, 관측 실패·노후화. chrony 관측을 대체하는 source 회귀이며 실제 외부 NTP 단절 시험은 아니다.
    • tests/release/test_time_sync_installation.py: 실제 설치 함수의 설정 보존·재실행·정책 충돌·실패 전달.
    • tests/integration/verify_time_sync.py: 추출한 Ubuntu chrony 4.2를 -x로 실행해 호스트 시각 권한 없이 양쪽 역할이 SOCK 표본을 선택하는지 확인한다. 실제 시계 보정 속도·실차 타이밍 검증은 아니다.
    • 기존 node 통신 회귀와 ./furive check: 연결·운용 요청과 전체 source 계약.

    참고: chrony 설정과 SOCK 입력, chronyd 실행 옵션, SOCK 표본 형식.
