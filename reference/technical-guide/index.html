    Furive OS 기술 구조¶

    이 문서는 Furive OS 내부를 수정하거나 장애 원인을 추적하는 개발자를 위한 지도다. 처음 사용하는 사람은 루트 README에서 시작하고, 실제 작업은 문서 안내에서 해당 가이드 하나를 선택한다.

    이 문서의 앞부분만 읽어도 다음 질문에 답할 수 있어야 한다.

    • Furive OS와 각 기능 패키지가 각각 무엇을 맡는가?
    • main과 edge는 무엇이 다른가?
    • 패키지는 누가 발견하고 실행하며 상태를 확인하는가?
    • 패키지 메시지, ROS2 데이터, 업데이트는 각각 어느 경로로 흐르는가?
    • 기능을 바꾸려면 어느 파일부터 확인해야 하는가?

    코드와 설정에는 호환을 위해 master, agent, capability_profile이 남아 있다. 사람이 쓰는 명령과 일반 설명에서는 각각 main, edge, 플랫폼이라고 한다. 내부 이름은 해당 데이터 형식이나 파일을 설명할 때만 표시한다.

    1. 한 장으로 보는 구조¶

    아래 main/edge는 공통 코드의 운영 역할이다. 일반 설치와 장비 표시는 플랫폼이 정한 A-ECU/HMI-ECU 등의 이름을 사용한다. 단일 묶음의 최초 PC 선택, 기존 배정 유지와 자율주행 연산 보호 기준은 ECU 설치 설계에 정리한다. 기존 통신·인증 역할 이름은 유지한다.

    공개 개념은 네 묶음이다¶

    개념 뜻
    main / edge 설치할 때 한 번 정하는 PC 역할. main은 차량 전체 상태와 업데이트 순서를 조정하고, edge는 차량 기능 패키지를 실행한다.
    패키지 독립 프로그램을 Furive가 찾고 실행하고 상태와 로그를 확인할 수 있게 연결한 단위다.
    플랫폼 차량 모델, 센서 모델과 그 차량에서 사용할 패키지의 조합이다.
    normal / test 여러 차량이 쓰는 공용판과 차량 한 대에서 먼저 확인하는 시험판이다.

    Autoware package나 ROS package는 여기서 말하는 패키지와 다르다. Autoware 소스는 별도 저장소와 작업 공간에서 개발한다. Furive OS는 검증된 소스 버전 선택과 Autoware 시작·종료만 맡는다.

    각 PC에는 프로그램 실행 관리자(PackageManager)가 하나씩 있다. 이 관리자는 선택된 패키지와 먼저 필요한 패키지를 찾아 시작·중지·상태 확인·재시작을 맡는다. 각 기능의 상태와 규칙은 해당 패키지가 맡는다.

    통신 경로는 목적별로 분리한다.

    • main/edge 제어 연결은 PC 등록, 상태 요약과 업데이트 조정에만 쓴다.
    • integration-gateway는 같은 PC의 패키지 사이 요청·응답·이벤트만 전달한다.
    • zenoh-bridge는 main과 edge 사이 ROS2 데이터를 전달한다.

    현재 integration-gateway끼리 main과 edge를 연결하는 기능은 구현되어 있지 않다. 패키지 이름이나 양쪽 역할에서 실행 가능하다는 설명 파일만 보고 PC 사이 전달이 된다고 가정하면 안 된다.

    각 상태를 한 곳에서만 담당하기¶

    상태·규칙·실행 흐름 담당 프로그램 담당하지 않는 곳
    패키지 시작·중지·상태 확인·재시작 각 PC의 PackageManager 패키지별 자체 재시작, Dashboard
    main/edge 등록과 호스트 상태 요약 main/edge 실행기 기능 패키지, integration-gateway
    패키지 사이 전달과 요청 ID 연결 integration-gateway main/edge 실행기, Dashboard
    구버전 HMI용 임시 상태 변환 hmi_dls_legacy.py 원본 상태, 녹화·전송 규칙
    녹화·세션·NAS 전송 상태와 규칙 data-logging-system 메시지 통로, main/edge 실행기, 운영 화면
    Autoware 시작·중지와 실행 선택 furive-launcher Dashboard, PackageManager
    ROS2 데이터 전달 zenoh-bridge main/edge 제어 연결, gateway
    업데이트 정책·목표·준비·적용·복구 하나의 OTA 흐름 개별 패키지, Dashboard
    표시와 사용자 입력 전달 운영 화면 패키지·OTA·Autoware의 실제 기능 상태
    설치한 PC 역할 setup이 만든 설치 상태 일반 명령의 반복 인자

    integration-gateway는 수신자와 요청 번호를 보고 메시지만 전달합니다. 예외적으로 hmi_dls_legacy.py가 구버전 HMI에 맞게 녹화 상태를 잠시 변환하지만, 원본 상태와 전송 규칙은 계속 data-logging-system이 담당합니다. 현재 HMI가 새 형식을 직접 쓰게 되면 이 변환 코드는 삭제합니다.

    원격 업데이트도 하나의 흐름입니다. 허용 규칙, 목표 선택과 별도 폴더 준비, 폴더 교환·확정·복구, 운영 화면 연결로 코드만 나뉘며 서로 다른 업데이트 방식은 아닙니다.

    무엇을 바꿀 때 어디서 시작하는가¶

    공통 소스 안내에서 기능별 시작 파일, 연결 파일, 설정과 읽는 순서를 찾는다. 폴더 전체 배치는 루트 지도, 책임 경계는 개발 계약의 수정 위치를 기준으로 한다. 화면과 프로그램 자체 기능은 해당 package/ 저장소가 담당한다.

    새 보조 코드, 서비스, 설정 항목을 만들기 전에 기존 담당 코드가 처리할 수 있는지 확인한다. 같은 값이나 시작·종료 상태를 두 곳에 저장하지 않는다.

    2. 처음부터 실행까지¶

    공개 작업 경로¶

    차량 PC의 정상 진입점은 전달받은 설치 묶음이다.

    ./bootstrap.sh

    설치가 끝나면 main/edge 서비스는 부팅 때 자동으로 시작되고 main 운영 화면은 로그인 뒤 자동으로 열린다. 평상시에는 별도 시작 명령을 호출하지 않는다.

    소스 코드 작업 폴더를 직접 수정하는 개발자는 저장소 최상위 폴더에서 현재 코드를 실행한다.

    ./furive dev main

./furive check

    edge 전용 코드를 다룰 때만 main을 edge로 바꾼다. 영구 설치를 마친 개발 PC에서는 저장된 역할을 자동으로 사용하므로 furive dev만 실행할 수 있다. 독립 프로그램을 연결하는 단계에서는 다음 흐름을 사용한다.

    furive package add <repository-url>
furive package run <name>
furive package check

    설치된 차량에서 터미널은 문제가 있을 때만 사용한다.

    furive status
furive service logs

    닫은 main 운영 화면을 다시 열 때만 furive dashboard를 사용한다.

    시작 내부 흐름¶

    공개 명령 아래에서는 다음 순서로 동작한다.

    1. 설치 상태에서 main 또는 edge 역할을 읽는다.
    2. pending update가 있으면 적용 가능 여부를 확인한다.
    3. runtime asset과 역할별 설정을 준비한다.
    4. 해당 node runtime을 시작한다.
    5. PackageManager가 manifest를 발견하고 플랫폼이 선택한 package 목록을 읽는다.
    6. dependency closure를 계산해 의존 패키지부터 시작한다.
    7. PackageManager와 공통 watchdog가 health를 확인하고 필요한 재시작을 수행한다.
    8. main/edge node는 호스트와 package 상태의 제한된 요약만 교환한다.

    내부 호환 이름 때문에 구현 파일은 nodes/master.py, nodes/agent.py, 설정은 config/master.default.yaml, config/agent.default.yaml이다. 이 파일 이름을 새 사용자 명령이나 일반 문서의 역할명으로 확장하지 않는다. run.sh, install.sh, scripts/*도 공개 진입점이 아니라 CLI, runtime, CI가 사용하는 내부 구현이다.

    개발 실행과 설치 서비스¶

    furive dev는 개발 세션 동안 OTA hold와 backend lifecycle을 소유한다. 종료하면 이전 hold와 설치 서비스 상태를 복원한다. main에서는 backend와 Electron 표시 계층을 분리해 실행한다. 브라우저가 필요할 때만 furive dev --browser, 화면이 필요 없을 때는 furive dev --no-ui를 사용한다.

    설치 후 main backend는 furive-os-master.service, edge backend는 furive-os-agent.service라는 내부 systemd unit이 소유한다. Electron autostart는 기존 backend에 연결하는 표시 계층일 뿐 backend lifecycle을 소유하지 않는다.

    Docker package는 기본적으로 restart=no로 실행한다. container와 process의 health·restart는 모두 PackageManager가 맡는다. script·colcon·binary package의 stdout/stderr는 logs/<package>.log에 기록된다. package 자체에 restart loop나 다른 package 제어를 넣지 않는다.

    3. 패키지 모델¶

    독립 저장소의 프로그램은 이름·버전과 run.sh만 알려주면 Furive가 시작·중지·상태·로그를 관리한다. 이 운용 단위를 패키지라고 한다.

    name: example
version: 0.1.0

    flowchart LR
  Develop["🧑‍💻 독립 저장소에서 개발·단독 검증"] --> Contract["📄 package.yaml + 실행 진입점"]
  Contract --> Add["🔗 furive package add"]
  Add --> Run["▶️ furive package run"]
  Run --> Check["✅ furive package check"]
  Check --> Platform["🧩 플랫폼에 package 선택"]
  Platform --> Release["🏷️ test 후 normal"]

    PackageManager는 등록된 저장소에서 패키지를 찾고 현재 PC 역할과 플랫폼이 선택한 것만 실행한다. Docker·장치·의존성·특수 상태 확인처럼 기본과 다른 요구만 package.yaml에 추가한다. 프로그램의 언어·빌드·기능 상태는 해당 저장소가, 공통 실행 순서와 재시작은 PackageManager가 한 번만 소유한다.

    실제 연결 순서는 프로그램 연결 가이드, 모든 필드·발견·실행·권한 규칙은 프로그램 연결 설정이 소유한다. 배포 산출물 경계는 CI/CD 기준을 따른다.

    4. 세 가지 통신 경로¶

    main/edge node 제어 연결¶

    main과 edge는 PC 등록, heartbeat, package·host 상태 요약과 업데이트 조정 정보를 교환한다. 기능 package의 세션이나 업무 상태를 node가 복제하지 않으며 application request를 중계하지 않는다.

    Autoware 실행 상태는 launcher가 소유한다. main은 heartbeat 응답에 launcher의 runtime 조회 결과만 담고, edge는 기존 공유 상태 파일에 수신 시각과 함께 전달한다. edge의 로컬 Dashboard는 이 결과가 heartbeat 유효 시간 안에 있을 때만 실행 상태 API로 제공한다. 원격 Dashboard HTTP는 loopback 전용이므로 이 전달이 필요하며, 새 포트·설정·사용자 명령은 없다. 조회 실패나 연결 단절로 오래된 실행 상태를 정상으로 표시하지 않는다.

    표준 2PC에서 main의 TCP 15001은 차량망에 bind하고 TLS 1.3 상호 인증으로 차량·역할·node 신원을 확인한다. edge가 광고한 protocol 범위에서 직전 또는 현재 protocol만 협상한다. 오래된 config에 identity나 bind 항목이 없더라도 외부 비인증 연결로 낮추지 않는다. 인증 계약이 없는 pre-epoch 장비는 정차된 유지보수에서 역할별 credential bundle로 edge, main 순서로 등록한다.

    각 역할 bundle에는 자기 private key와 상대 leaf pin만 둔다. /etc/furive-os/control.env의 token은 같은 host의 loopback Dashboard·OTA 제어에만 사용하며 PC 사이에 공유하지 않는다. PackageManager는 기본적으로 이 credential을 package 환경에서 제거한다. manifest에 control.credentials: true를 선언한 Dashboard, OTA owner, launcher 같은 trust duty만 받을 수 있다.

    같은 PC의 integration-gateway¶

    현재 gateway는 각 PC의 127.0.0.1:15003에서만 요청·응답·이벤트를 전달한다. 필요한 package의 dependency로 자동 시작되므로 사용자용 설치 선택, CLI, endpoint config가 없다. HMI, DLS와 Autonomy Studio 연계 package가 이 경로를 사용한다.

    HMI/DLS legacy adapter는 기존 JSON 이름과 응답 형식을 현재 전달 계약으로 변환합니다. 이 과정에서 구형 HMI 응답을 만들기 위한 녹화·upload의 작은 휘발성 projection과 DLS 명령 분류를 소유합니다. 지속 상태, 재시도와 업무 정책은 소유하지 않으며 gateway 재시작 뒤 DLS에서 다시 동기화합니다. 이 N-1 예외는 adapters/hmi_dls_legacy.py 한 파일에만 두고 HMI/DLS의 v1 전환 뒤 삭제합니다.

    현재 제한은 다음과 같다.

    • main gateway와 edge gateway 사이 routing은 미구현이다.
    • loopback은 차량 밖 접근을 막지만 같은 PC process identity를 인증하지는 않는다.
    • gateway는 message durability, 업무 retry, schema registry나 domain state store가 아니다.
    • legacy adapter 밖의 새 domain projection이나 command 해석은 허용하지 않는다.

    PC 사이 package 메시지가 필요해져도 현재 node control 연결이나 Zenoh ROS2 경로에 임의로 섞어서는 안 된다. 그것은 현재 기능이 아니라 별도 보안·routing 계약이 필요한 후속 변경이다.

    ROS2의 zenoh-bridge¶

    ROS2 데이터는 zenoh-bridge가 전달한다. 표준 2PC에서 main은 QUIC/UDP 7447을 listen하고 edge가 연결한다. TLS 1.3 mTLS와 peer-CN 기반 default-deny ACL을 사용한다.

    main의 Autoware domain과 Zenoh 쪽 shadow domain은 ros2-domain-bridge가 분리한다. 232는 Furive 내부 shadow domain 예약값이며 일반 ROS2 app의 ROS_DOMAIN_ID로 사용하지 않는다. ROS domain을 바꾸면 두 bridge의 endpoint와 재시작 상태를 함께 확인한다.

    Dashboard 경계¶

    Dashboard는 상태를 표시하고 사용자 입력을 소유자에게 전달하는 adapter다. package, OTA, Autoware lifecycle을 직접 소유하지 않는다. HTTP는 localhost 18082에 bind하며 control token을 요구한다.

    package dashboard는 main Dashboard와 같은 권한으로 실행하지 않는다. package frame은 allow-same-origin 없는 opaque-origin sandbox에서 열고, package별 capability에 허용된 method/path/query만 proxy한다. package HTML을 top-level 문서로 직접 열어 이 경계를 우회하지 않는다. 로컬 HDMI capture viewer는 media API 때문에 control API가 없는 별도 loopback origin을 사용한다.

    Furive OS 전체 데이터 교환 정책¶

    이 계약은 ROS 토픽뿐 아니라 패키지 메시지, 운용 명령, 화면·영상, 기록 파일과 업데이트에도 적용한다. Furive OS는 누가 어떤 목적으로 어느 경계를 넘어 어떤 동작을 할 수 있는가를 제한한다. 데이터의 의미와 기능 상태는 계속 해당 독립 패키지가 소유한다. 모든 통신을 새 gateway 하나로 모으거나, 중앙 서비스가 패키지의 녹화·보존·재시도 상태를 다시 관리하는 구조로 바꾸지 않는다.

    독립 개발과 한 번의 연결 설정¶

    서비스의 독립성과 수동 설정의 분산은 다르다. 패키지는 자기 구현·인터페이스·업무 상태를 소유하고, Furive OS는 그 패키지들을 연결하는 정의를 한 곳에서 해석해 설치·실행에 적용한다. 새 데이터를 연결할 때마다 소비 패키지, 두 bridge, 설치 스크립트와 bundle을 각각 수정해야 한다면 통합 계약이 완성되지 않은 것이다. 설정 화면 하나가 여러 원본 설정 파일을 대신 편집하는 방식도 해결로 보지 않는다.

    변경하려는 것 사람이 바꾸는 원본 Furive OS가 파생·적용할 것
    기존 허용 범위 안에서 녹화할 토픽 추가 DLS의 녹화 선택 한 곳 목록·타입 확인, 필요한 수신 경로 요청과 bridge 설정 적용
    패키지가 기존 인터페이스를 새로 소비 해당 패키지의 소비 요구 한 곳 플랫폼 허용 범위 대조, 필요한 연결과 설정 생성, 수신 가능 여부 표시
    차량에서 허용할 데이터·명령 범위 변경 플랫폼 연결 계약 한 곳 방향별 전송 필터와 허용 결과 생성; 각 bridge의 수동 allowlist 수정 제거
    새로운 데이터 타입·기능 인터페이스 제공 생산 패키지의 인터페이스 계약 한 곳 호환성 확인과 필요한 타입 지원 배포; 소비자별 동일 타입 정의 복사 제거
    패키지 조합·배치 변경 기존 플랫폼의 패키지 구성 한 곳 기존 설치·PackageManager가 의존성과 실행 위치 반영

    이 표는 후속 구현의 사용자 경험과 소유권 기준이다. 현재 공통 인터페이스·연결 선언 schema가 이미 있다는 뜻은 아니다. 기존 package.yaml과 플랫폼 선택 계약을 확장할 때 연결 정의를 그 계약에서 해석하고, 별도의 수동 토픽 목록을 각 패키지에 계속 유지하지 않는다. producer의 타입·의미, consumer의 사용 목적, 플랫폼의 허용 범위는 서로 다른 사실이며 동일 값을 중복 선언하는 이유가 되어서는 안 된다.

    flowchart LR
  Interface["생산 패키지의 인터페이스"] --> Resolve["Furive OS 연결 정의 검증·설정 생성"]
  Demand["소비 패키지의 데이터 선택"] --> Resolve
  Platform["설치된 플랫폼의 허용 범위"] --> Resolve
  Resolve --> Settings["기존 전송 경로에 적용할 설정"]
  Settings --> Transport["bridge · 로컬 API · 기존 adapter"]
  Producer["생산 패키지"] --> Transport --> Consumer["소비 패키지"]

    공통화하는 대상은 연결 정의의 검증과 설정 생성이다. 실제 데이터는 기존 경로로 흐르고 패키지의 업무 로직은 독립적으로 실행된다. 통합 설정 생성기의 단일 구현 위치와 입력 schema는 구현 단계에서 기존 package 발견·플랫폼 해석 계약에 결합해 정하며, 패키지별 생성기를 복사하지 않는다.

    이미 설치된 타입과 허용 범위 안의 데이터 선택에는 소스 수정·이미지 재빌드·release·bundle 재생성을 요구하지 않는 것이 완료 조건이다. 새 메시지 타입의 실행 지원이나 화면의 새 기능이 필요한 경우에는 해당 패키지 변경이 필요할 수 있다. 그때도 나머지 bridge와 installer를 사람이 함께 고치지 않도록 한다.

    현재는 zenoh-bridge/entrypoint.sh의 수신 allowlist와 ros2-domain-bridge/config/config.default.yaml의 auto_topics.include가 같은 정방향 범위를 각자 보유한다. 먼저 이 중복을 단일 연결 정의의 파생 설정으로 바꾸고, 기존 기본 동작이 유지되는지 검증해야 한다. 이후 데이터 목록 조회·소비 요구의 자동 적용을 연결한다. 단순히 allowlist를 전부 여는 것은 이 중복 소유 문제를 해결하지 않는다.

    아래 표는 기존 경로를 분류한 설계 기준이다. 통합된 권한 선언 형식과 동적 경로 적용은 아직 구현되지 않았다. 각 경로의 현재 구현과 제한은 앞 절을 따르며, 이 문서가 런타임 권한을 추가하지 않는다.

    데이터와 동작 경계·기존 경로 허용 기준과 단일 소유자
    등록·heartbeat·패키지 및 host 상태 요약 main ↔ edge node 제어 연결 설치된 차량·node 신원과 협상된 protocol에 맞는 메시지만 허용한다. node가 연결 상태를 소유하고 원본 기능 상태는 패키지가 소유한다.
    패키지 실행·Autoware 실행·OTA 적용 명령 인증된 로컬 제어 API와 정의된 node 운용 protocol 조회와 변경을 구분하고 실행 대상과 명령을 제한한다. PackageManager·launcher·OTA가 각각 자기 lifecycle만 실행한다. 임의 shell이나 패키지 업무 RPC를 node 연결로 전달하지 않는다.
    토픽·기능 목록과 타입 정보 각 데이터 소유자의 조회 경로 목록 조회는 실제 데이터 구독·기록·명령 권한을 만들지 않는다. 아직 브릿지되지 않은 차량 토픽을 edge에서 조회하는 통합 경로는 미구현이다.
    센서·차량·Autoware 상태의 실시간 데이터 ROS Domain Bridge → Zenoh → 수신 PC의 ROS 영역 플랫폼이 허용하는 출발지·목적지·이름·타입·방향 안에서 필요한 경로만 구성한다. ROS 경로 설정은 bridge가 적용하고 소비 목적과 처리 방식은 패키지가 소유한다.
    목표속도·경로·운행 모드 등 차량 명령과 응답 명시적으로 허용된 ROS topic·service·action 및 차량 adapter 표시용 구독과 별개로 명령별 송신·호출 권한을 정한다. 응답을 받는 권한이 반대 방향의 새 명령 권한이 되지 않는다. 실제 상태 전환 가능 여부는 차량·Autoware의 해당 기능 소유자가 판단한다.
    같은 PC의 업무 요청·응답·이벤트 integration-gateway 크기가 제한된 envelope와 지정 수신자만 전달한다. schema·중복 처리·업무 성공 여부는 수신 패키지가 판단한다. PC 사이 forwarding은 현재 미구현이다.
    화면 표시·캡처 영상·원격 입력 package surface·MGMT IPC·영상 경로·원격제어 패키지 화면 보기와 키보드·마우스 입력 허용을 구분한다. 화면 adapter에 포괄적인 ROS publish·host 제어 권한을 주지 않는다. 원격 입력 허용은 해당 원격제어 소유자가 적용한다.
    로컬 기록·재생·삭제 DLS → 로컬 dataset 및 재생 ROS 영역 녹화 선택·세션·보존·삭제는 DLS가 소유한다. 재생은 새로운 데이터 발행이므로 수신·녹화 권한만으로 live 차량 명령 경로에 주입하도록 허용하지 않는다.
    기록 파일·운영 자료의 외부 전송 DLS → 설정된 NAS 등 해당 기능의 전송 경로 로컬 수신·기록과 외부 전송은 별도 허용이다. DLS의 NAS 비활성화는 화면과 실제 업로드 실행에 모두 적용해야 하며, 허용 목적지·전송 대상·보존 결과는 DLS가 소유한다.
    소스·실행 이미지·지도·설치 파일의 반입 release·OTA·bundle·외부 workspace 경로 등록된 플랫폼과 고정된 revision·digest·서명을 검증한다. OTA가 적용 정책을, bundle이 승인된 전달물 포장을 소유한다. 데이터 구독 요청이 새 실행 코드 설치를 허용하지 않는다.
    비밀키·token·접속 비밀번호 설치 및 해당 credential 소유자 필요한 실행 주체에만 제공하고, topic·gateway 이벤트·heartbeat·일반 로그·화면 데이터로 전달하지 않는다. 공개 신원 정보와 비밀 credential을 구분한다.

    권한을 판단하는 공통 규칙¶

    연결 인증은 상대 PC의 신원을 확인하는 단계다. 연결 성공이나 같은 차량이라는 이유만으로 모든 데이터와 명령을 허용하지 않는다. 경계를 넘는 경로의 최종 허용 범위는 다음 조건의 교집합이다.

    • 설치된 차량·플랫폼·역할이 허용하는 범위
    • 활성 패키지가 자기 기능을 수행하기 위해 요청한 범위
    • 출발지·목적지의 검증된 신원과 실제로 강제할 수 있는 격리 범위
    • 데이터 이름·타입·동작·방향과 전송량·유효 시간 조건

    발견/조회, 구독, 발행, 명령 호출, 로컬 기록, 재생, 삭제, 외부 전송을 구분한다. 로컬에서 접근 가능한 데이터에 대한 기록 제한까지 네트워크 allowlist가 강제한다고 주장하지 않는다. 토픽 이름만으로 조회 데이터인지 차량 명령인지 결정하지 않으며, 같은 토픽이라도 방향과 사용 목적을 함께 본다. 상태에는 관측 시각과 유효성을 붙여 미수신·오래된 값과 실제 0·false를 구분한다.

    허용 범위 밖의 요청, 타입 충돌, 지원하지 않는 protocol은 이유와 함께 거부한다. 실패 시 전체 wildcard 허용, 다른 차량 선택, 비인증 연결 또는 포괄적인 송신 권한으로 자동 대체하지 않는다. 고대역폭 센서·영상 전송은 경로별 자원 조건을 확인하고, 기록 편의를 위해 차량 제어·운용 연결을 막지 않도록 한다. 임의의 샘플링·누락을 정상적인 완전 녹화로 표시하지 않는다.

    정책과 업무 상태의 소유권¶

    플랫폼 연결 계약은 설치된 차량에서 허용 가능한 통신 범위를 소유한다. 패키지의 기능 설정은 그 안에서 필요한 데이터를 선택한다. 예를 들어 DLS의 녹화 토픽 선택이 업무 요구의 원본이며, 사람이 같은 목록을 Zenoh와 ROS Domain Bridge 설정에 반복 입력하게 만들지 않는다.

    통합 선언과 자동 적용을 구현할 때는 허용 범위와 요청을 한 번 대조한 결과에서 각 경로의 설정을 생성한다. bridge의 allowlist는 그 결과를 적용하는 설정이며 독립적으로 편집하는 두 번째 정책이 되어서는 안 된다. ROS 경로의 적용·해제는 기존 bridge가, 패키지의 실행·재시작은 PackageManager가, 기록·재생·NAS 정책은 DLS가 계속 맡는다. Dashboard와 MGMT는 요청과 결과만 표시한다.

    새 데이터 요구는 목적·생산자·소비자·이름/타입·동작/방향·필요 자원·보관/외부 전송 여부를 설명할 수 있어야 한다. 이 항목들은 설계 검토 기준이며 현재 package.yaml에 존재하는 새 필드가 아니다. 공통 선언 schema와 경계별 검증 API는 기존 package·플랫폼 계약의 후속 구현으로 정의해야 한다. 이를 위해 별도 정책 daemon, 업무 상태 복제본, 패키지별 bridge 재시작 loop를 추가하지 않는다.

    동적 데이터 요청의 적용 계약 — 후속 구현¶

    DLS뿐 아니라 HMI, MGMT, 분석·센서 패키지가 새 데이터를 필요로 할 때 공통으로 사용할 계약이다. 현재 릴리즈에는 아래 자동 경로 변경이 구현되어 있지 않다.

    1. 소비자는 허용된 목록에서 데이터와 타입·출처·관측 시각을 조회한다. 목록 조회는 payload 전송을 시작하지 않으며, 오래된 목록이나 현재 미발행 상태를 별도로 표시한다.
    2. 소비 패키지가 기존 기능 설정에 선택을 저장하고 수신 경로를 요청한다. 정책 소유자는 설치된 허용 범위와 신원·방향·타입·자원을 검증한다. 요청자가 보낸 package 이름만으로 권한을 인정하지 않는다.
    3. 경로 소유자가 검증 결과를 적용한다. 요청 저장, 경로 적용, publisher 발견, 첫 데이터 수신은 서로 다른 상태다. 전부 완료되기 전에 UI에 수신·녹화 성공으로 표시하지 않는다.
    4. bridge 재시작이 필요한 구현에서는 진행 중인 제어·녹화에 미치는 영향을 먼저 처리하고 적용 결과를 확인한다. 한쪽만 적용된 경우 성공으로 처리하지 않으며, 실패 복구는 현재의 다른 소비자 경로를 보존한다.
    5. 선택 해제·패키지 중지·신원 폐기·정책 변경 시 해당 요청의 효력을 회수한다. 같은 데이터를 사용하는 다른 소비자가 있으면 그 경로는 유지한다. 재연결 시 기존 기능 설정에서 요구를 다시 검증하고 적용한다.
    6. 화면에는 미발견·정책 거부·타입/QoS 불일치·자원 부족·연결 단절을 구분해서 표시한다. 진단에는 요청 주체·대상·적용한 정책 버전·결과를 남기되 원본 payload와 credential은 남기지 않는다.

    DLS의 사용 흐름은 이 계약 아래에서 토픽 선택 → 수신 가능 여부 확인 → 녹화로 줄인다. 사용자 선택은 플랫폼이 사전에 허용한 수신 범위를 구체화하며, 허용 범위 자체의 확장은 플랫폼 연결 계약 변경으로 처리한다. 녹화 선택으로 차량 제어 송신이나 NAS 업로드 권한이 함께 확장되지 않는다. 토픽 목록 자동 재조회는 이미 구현됐지만, 차량 전체 목록 조회와 선택에 따른 경로 자동 적용은 아직 별개 구현 과제다.

    현재 강제할 수 있는 경계와 남은 검증¶

    현재 mTLS node/peer 인증, ROS bridge 필터, Dashboard surface 제한과 로컬 제어 인증은 각각 존재한다. 그러나 인증된 node와 인증된 개별 package는 같은 경계가 아니다. 같은 ROS domain을 공유하는 프로세스는 같은 데이터를 볼 수 있으며, gateway의 loopback bind도 로컬 process 신원 인증이 아니다. 따라서 현재 구성을 package별 완전한 데이터 격리나 모든 외부 전송을 통제하는 장치라고 설명하지 않는다.

    동적 경로 자동화에 앞서 통합 정책의 실행 소유자·선언 schema, 요청 package 신원 확인, PC 사이의 타입이 정해진 경로 요청 protocol, 적용 결과 회신과 회수 절차를 구현·검증해야 한다. 기존 node control에 임의 업무 메시지를 섞거나 gateway가 이미 PC 사이를 연결한다고 가정해서는 안 된다. 패키지별 접근 격리가 필요한 경로는 ROS domain·process·network 경계를 실제로 분리할 수 있는지도 확인한다.

    검증은 한 경로에서 목록 조회만으로 데이터가 전송되지 않는지, 수신 요청이 송신·재생·외부 전송 권한을 늘리지 않는지, 다른 차량·위조 package·허용 범위 밖 요청을 거부하는지 확인한다. 추가로 부분 적용 실패, 재연결, 선택 해제, 여러 소비자 공유, QoS 충돌과 대용량 데이터 부하를 확인한다. 실행하지 않은 경계는 구현 완료로 표시하지 않는다. 이 절의 변경은 설계 문서 변경이며 실행·설치 산출물이나 통신 허용 범위를 바꾸지 않으므로 그 자체로 release·bundle을 새로 만들지 않는다.

    5. 업데이트와 복구¶

    사용자가 보는 정책¶

    운용자는 normal과 test만 선택한다.

    공개 이름 용도 내부 배포 표현
    normal 여러 차량이 쓰는 공용판 main channel
    test 지정한 차량 한 대의 임시 시험판 preview/<vehicle_id>

    차량별 목표 version은 fleet assignment 한 곳이 소유한다. 운용자가 Git branch, 내부 호환판이나 구버전 설정 변환을 직접 고르지 않는다.

    내부 적용 흐름¶

    1. ota-updater가 현재 channel의 최신 canonical tag 또는 차량의 exact version을 최종 목표로 선택한다.
    2. 현재판에서 목표판으로 직접 갈 수 없으면 release manifest에 결박된 bounded compatibility route를 검증한다.
    3. 현재 실행본을 유지한 채 /data/safe_staging/<checkout-key>/work에 source와 image를 준비한다.
    4. source commit, release manifest, architecture별 image digest와 설치 산출물을 검증한다.
    5. 후보를 finalized로 만든 뒤 다음 시작에서 ReleaseActivation이 switching journal을 먼저 쓰고 active와 candidate를 원자적으로 교환한다.
    6. 호환판에 구버전 설정 변환이 있으면 패키지 시작 전에 실행한다. 설정 준비와 필수 package health가 성공하면 그 단계를 확정하고 최종 목표를 다시 계산한다.
    7. 실패하면 직전 정상판과 이번 설정 준비가 바꾼 값만 복구한다. 동시에 사람이 바꾼 값은 CAS conflict로 보존한다.

    staging 실패는 현재 실행본을 바꾸지 않는다. 교체 상태가 모호하거나 manifest·commit·digest가 일치하지 않으면 실행하지 않고 fail closed한다. 파일명 marker나 process exit code 하나만으로 release 성공을 판단하지 않는다.

    1PC에서는 main이 OTA를 관리하고 edge OTA가 비활성화될 수 있다. 2PC에서는 main이 exact 목표를 고정하고 edge를 먼저 준비한다. edge의 fresh signed heartbeat가 목표 protocol, release tag, 전체 commit과 확정 상태를 보고한 뒤에만 main이 자기 후보를 준비한다. updater가 임의로 다른 PC를 재시작하거나 edge의 영구 channel/version 설정을 덮어쓰지 않는다.

    호환판 선택, 설정 journal과 rollback의 전체 불변식은 업데이트 호환 정책과 이전 정상 버전 기준이 소유한다. release와 bundle 중 무엇이 필요한지는 CI/CD 릴리즈 판단을 따른다.

    6. 저장소와 런타임 위치¶

    소스 폴더 배치는 루트 지도에 모아 둔다. 공통 소스 안내에서 구현·설정 파일을, 스크립트 안내에서 검사·배포 내부 도구를 찾는다. deploy-repo-template/은 차량용 생성 저장소의 템플릿이며 source 구현과 구분한다.

    차량의 지속 runtime asset은 /data/furive-os 아래에 둔다. package별 config와 data는 가능하면 /data/furive-os/<package> 아래에서 그 package가 소유한다. source repo와 runtime data를 같은 상태 저장소처럼 사용하지 않는다.

    찾으려는 정보 위치
    현재 역할과 node package 목록 내부 config/master.yaml, config/agent.yaml
    플랫폼별 package 조합 config/capability-profiles.yaml
    Autoware OS/GPU/CUDA/driver/image 호환 config/autoware-compatibility.yaml
    차량별 플랫폼·channel·version config/fleet-vehicles.yaml
    실제 발견된 package 목록 logs/effective-packages-*.json
    package lifecycle 로그 logs/<package>.log, logs/<package>.build.log
    차량 runtime asset과 data /data/furive-os/
    OTA staging /data/safe_staging/

    7. 현재 패키지 보기¶

    패키지 목록을 문서에 복사하면 저장소가 추가·삭제될 때 바로 오래된 정보가 된다. 현재 checkout에서 Furive가 실제로 발견한 목록은 다음 명령이 한 번만 계산한다.

    ./furive package list

    차량에서 실행할 목록은 플랫폼과 PC 역할이 선택한다. 주요 운영 패키지의 역할은 실행 구성요소, 모든 package.yaml 필드는 프로그램 연결 설정을 기준으로 한다.

    8. 차량 네트워크와 주요 포트¶

    flowchart LR
  Main["🖥️ main PC<br/>Autoware"] <-->|"node control<br/>TCP 15001 mTLS"| Edge["🖥️ edge PC<br/>차량 package"]
  Main <-->|"ROS2<br/>QUIC/UDP 7447 mTLS"| Edge
  Sensors["📡 LiDAR · camera"] --> Edge
  Edge --> CAN["🚘 CAN"]
  Edge --> External["☁️ NAS · 외부 서비스"]
    경로 현재 값 범위
    main/edge node control TCP 15001 main의 차량망 interface; mTLS
    node discovery UDP 15002 차량망
    package integration gateway TCP 127.0.0.1:15003 각 PC의 loopback
    Dashboard HTTP 127.0.0.1:18082 loopback
    Zenoh ROS2 bridge QUIC/UDP 7447 차량망; mTLS와 ACL
    RS80 LiDAR UDP 6699/7788, multicast 239.192.1.2 sensor network
    FLIR camera UDP 50000, multicast 239.192.1.1 sensor network
    NAS upload HTTPS 443 외부 연결

    표준 2PC 주소는 main 192.168.1.102, edge 192.168.1.103이다. 내부 config의 local_ip은 NIC 주소를 직접 바꾸지 않고 자동 탐색의 우선값으로만 사용한다. discovery가 실제 main 주소를 찾으면 edge node 연결과 Zenoh endpoint를 동기화한다. 시작·재연결 시 main 후보가 여러 개면 운영체제의 실제 송신 경로가 이더넷인 주소를 Wi-Fi 주소보다 먼저 선택한다. 이더넷으로 탐색된 후보가 없으면 Wi-Fi를 사용하며, 같은 경로 종류 안에서는 기존 선호 대역·저장된 주소 우선순위를 유지한다. 이 선택은 호스트의 라우팅 테이블을 변경하지 않는다.

    Gateway 연결 주소는 현재 127.0.0.1:15003 하나다. 이전 package별 endpoint와 tcp_port 설정은 구버전 설정 변환 대상이며 현재 사용자가 선택하는 항목이 아니다. 저장소의 과거 HMI bundle에는 N-1 release 전환 검사용 5000 listener가 남을 수 있지만 현재 Unity source와 관리 실행의 통신 구조로 설명하거나 재사용하지 않는다.

    실차에서 ROS2나 sensor가 보이지 않으면 application 재시작 전에 다음을 함께 확인한다.

    • main/edge의 차량 ID, platform, ROS domain과 node identity
    • NIC 주소, subnet, multicast routing, IGMP, MTU와 ring buffer
    • zenoh-bridge와 ros2-domain-bridge의 endpoint와 health
    • package가 mount한 CycloneDDS config와 shared message ABI
    • sensor IP, serial, UDP port와 실제 link speed

    9. 유지보수와 검증¶

    장애를 좁히는 순서¶

    1. furive status에서 node와 package health를 확인한다.
    2. furive service logs에서 Furive lifecycle 오류를 확인한다.
    3. 문제 package의 logs/<package>.log와 build log를 확인한다.
    4. Docker package이면 container 상태와 해당 package 로그를 확인한다.
    5. 통신 문제는 node control, integration gateway, Zenoh 중 어느 경로인지 먼저 구분한다.
    6. ROS2 문제는 domain, CycloneDDS config, shared message ABI를 확인한다.
    7. 장치 문제는 process restart보다 NIC, sensor, CAN, mount와 권한을 먼저 확인한다.
    8. 업데이트 문제는 target identity, staging, activation journal과 직전 정상판 상태를 확인한다.

    로그에 ERROR라는 문자열이 있다는 이유만으로 package를 unhealthy로 판단하지 않는다. process 또는 container 생존 여부 밖의 판정이 필요하면 package manifest가 health pattern과 startup grace를 소유한다. pending 상태는 준비 중이라는 뜻이며 restart 실패 횟수를 소비하지 않는다.

    변경 단계에 맞는 검증¶

    단계 필요한 검증
    일상 개발 변경 범위의 작은 test, 관련 package test
    차량 한 대 시험 furive check, 한 차량 test, 변경 기능의 실행과 복구
    고객용 normal 전체 검증, 운영 증적, 실제 권한·데이터·외부 전송 변경에 필요한 별도 검토

    작은 test를 먼저 실행하고 마지막에 다음 공통 검사를 실행한다.

    furive check

    systemd, Docker, GUI, 장치나 실차를 실제로 실행하지 않았다면 검증 결과에 그 사실을 남긴다. 미래 인증 로드맵이나 변경과 무관한 운영 자동화를 일상 개발의 완료 조건으로 추가하지 않는다.
