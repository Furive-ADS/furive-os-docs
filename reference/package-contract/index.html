    프로그램 연결 설정 (package.yaml)¶

    이 문서는 프로그램을 Furive에 연결할 때 쓰는 package.yaml의 상세 설정입니다. 일반 프로그램은 먼저 프로그램 연결 가이드의 name, version, run.sh만 사용합니다.

    기본값으로 동작한다면 필드를 더 쓰지 않습니다. 새 필드를 추가할 때는 “기본값으로 불가능한 이유”와 “이 값을 담당하는 한 곳”을 설명할 수 있어야 합니다.

    flowchart LR
  Program["🧑‍💻 독립 프로그램"] --> File["📄 package.yaml"]
  File --> Discover["🔍 Furive가 발견"]
  Discover --> Run["▶️ 실행 · 상태 확인 · 중지"]
    필요한 기능 찾아볼 절
    최소 설정 최소 필드와 기본값
    로그와 상태 확인 로그와 정상 상태 기준
    장치·권한 책임·권한 경계
    개발 중 소스 실행 승인된 소스 실행(Source Unlock)
    시작·종료·재시작 시작·중지 규칙, 다시 시작 조건
    패키지 자체 테스트 패키지가 담당하는 테스트

    아래부터는 코드와 설정에서 쓰는 내부 필드 이름을 그대로 설명합니다.

    개발 경계¶

    Furive 패키지는 독립 저장소에서 이미 개발된 프로그램을 Furive의 발견·실행·상태 확인·로그·업데이트에 연결하는 운용 단위다. Autoware package나 ROS package와 다른 개념이며 furive package 명령은 프로그램 소스, Dockerfile 또는 Autoware 작업 공간을 생성하지 않는다.

    프로그램 내부의 언어, 프레임워크, 빌드 및 테스트 방식은 독립 저장소가 담당한다. Furive OS는 package.yaml과 실행·중지·정상 상태 확인만 담당한다. Autoware 소스는 별도 작업 공간과 저장소에서 개발하고, Furive OS에서는 검증된 소스 버전과 Autoware 시작·종료 방식만 연결한다.

    패키지 발견 기준¶

    프로그램 실행 관리자와 검사 도구는 기본적으로 다음 package.yaml을 찾는다.

    package/core/*/package.yaml
package/plugin/*/package.yaml

    공식 패키지는 최상위 저장소가 추적하거나 .gitmodules에 등록한 연결 저장소입니다. 승인된 소스 실행 표시가 있는 작업 폴더도 포함합니다. 등록되지 않은 중첩 Git 저장소는 제외해 예전 작업 폴더나 백업이 검사와 차량 실행에 섞이지 않게 합니다.

    외부 패키지를 실험할 때만 FURIVE_OS_EXTERNAL_PACKAGE_DIRS에 별도 Git 저장소 경로를 지정합니다.

    최소 필드와 기본값¶

    일반 script 패키지의 필수 필드는 name과 version뿐이다.

    필드 기준
    name Furive OS가 인식하는 패키지명. 플랫폼 설정에는 이 이름을 쓴다.
    version 사람이 확인할 수 있는 패키지 버전.
    type 생략 시 script. 필요한 경우 docker, colcon, binary를 명시한다.
    nodes 생략 시 edge를 뜻하는 내부 값 [agent]. 설정 파일에서만 master, agent를 사용한다.
    run.script 생략 시 run.sh. 다른 이름을 사용할 때만 명시한다. 
    name: hello-sensor
version: 0.1.0

    Docker 패키지는 type: docker와 run.script가 필요합니다. Docker 이미지 이름을 생략하면 패키지 이름을 사용합니다. 빌드가 필요하면 build.script 또는 Dockerfile을 두고, 실행 파일 패키지는 binary.path를 지정합니다.

    실행 프로그램 없이 운영 화면 파일만 제공하는 패키지는 dashboard.yaml과 dashboard/index.html을 함께 둡니다. run.sh나 상태 검사를 억지로 추가하지 않습니다.

    docker 형식은 컨테이너로, 나머지는 일반 프로그램으로 실행 관리자가 직접 감시합니다. run.sh는 준비를 끝낸 뒤 실제 프로그램을 exec해야 합니다. 자체 재시작이나 pkill을 넣지 않습니다.

    호스트의 로그인 X 세션을 실제로 사용하는 패키지만 아래 필드를 선언한다. edge/main 백엔드는 GUI를 기다리지 않고 먼저 시작하며, PackageManager는 사용자 systemd 세션이 게시한 정확한 DISPLAY와 XAUTHORITY, X 소켓 접근을 확인한 뒤 해당 패키지만 시작한다. 기다리는 동안 재시작 실패 횟수를 소비하지 않는다. 컨테이너 안에서 자체 X 서버만 사용하는 패키지에는 선언하지 않는다.

    runtime:
  requires_graphical_session: true

    공식 release에서 GUI를 host process로 실행해야 하지만 package source 접근 권한을 배포하면 안 되는 Docker package는 준비된 runtime을 같은 release image 안에 넣고 다음처럼 선언한다.

    runtime:
  requires_graphical_session: true
  host_from_image:
    source: /app
    entrypoint: run.sh
    startup_probe_seconds: 2

    PackageManager는 release manifest가 선택한 architecture별 로컬 image를 사용하고 없을 때만 pull한다. 임시 network-disabled container에서 지정 payload만 사용자 전용 임시 디렉터리로 materialize한 뒤 로그인 세션 환경으로 실행한다. 상태·중지·재시작·health는 기존 PackageManager process lifecycle이 그대로 소유한다. 별도 user service나 autostart owner를 만들지 않는다. 이 필드는 Git key를 설치하거나 source checkout을 허용하지 않으며 source_unlock의 접근제어 의미를 바꾸지 않는다. Image 안의 backend는 필요하면 같은 digest image를 headless sidecar로 실행할 수 있다.

    차량 플랫폼이 선택하는 Docker package의 release image는 원본 구현 source를 실행 파일처럼 그대로 싣지 않는다. 해당 Dockerfile은 build stage와 runtime final stage를 분리하고, final stage에는 native binary, bundle/minified JavaScript, bytecode, ROS install tree처럼 실행에 필요한 결과와 config만 복사한다. 최종 image에는 다음 내부 metadata를 둔다.

    LABEL io.furive.runtime.source-confidential="1"

    Package manifest 검사는 이 label과 final stage의 직접적인 source copy를 정적으로 확인하고, release workflow는 실제로 빌드한 local image의 label을 Harbor push 전에 다시 확인한다. 이 계약은 docker run, docker save로 원본 프로젝트 source를 그대로 열람하는 경로를 막기 위한 것이다. 실행 결과는 역공학될 수 있으므로 암호화나 DRM, 완전한 비밀성을 뜻하지 않는다. 실행에 필요한 공개 OSS dependency, 생성 code, ROS/Python runtime helper와 config도 image에 남을 수 있다.

    Source Unlock은 이 경계의 예외가 아니라 별도의 의도적인 source 제공 경로다. 운영자가 package를 명시적으로 승인하면 Git checkout을 전달하며, 그 checkout과 Autoware source workspace에는 위 image 은닉 계약을 적용하지 않는다.

    로그와 health 경계¶

    패키지는 stdout/stderr에 로그를 쓰고 메시지 내용과 내부 logger 이름을 소유한다. Furive는 서로 다른 언어와 framework의 출력 본문을 다시 해석하거나 재작성하지 않는다. 대신 Docker runtime을 파일과 Dashboard에서 읽을 때 Docker의 RFC3339 timestamp를 붙이고, PackageManager가 생성하는 build·start lifecycle 행은 다음 공통 형식을 사용한다.

    2026-08-10T16:30:00+0900 [INFO] [example] 빌드 완료

    로그에 ERROR, failed, traceback 같은 문자열이 있다는 이유만으로 package health를 실패로 판정하지 않는다. 프로세스·컨테이너 생존 여부 외에 로그 기반 판정이 필요하면 그 package의 health_check.healthy_log_patterns, health_check.pending_log_patterns 또는 health_check.unhealthy_log_patterns에 명시한다. pending_log_patterns는 장치 연결을 기다리는 살아 있는 runtime처럼 재시작하면 안 되는 미준비 상태에만 사용한다. 이 규칙으로 Chromium/D-Bus 진단처럼 무해할 수 있는 stderr와 실제 lifecycle 실패의 소유자가 섞이지 않는다.

    health_check.startup_grace_seconds 동안 살아 있는 runtime은 healthy가 아니라 pending이다. OTA candidate gate는 이 시간이 끝나기 전에 package를 확정하면 안 된다. health_check.max_failures는 누적 실패 횟수가 아니라 연속된 확정 unhealthy sample의 threshold이며 healthy sample이 나오면 counter를 초기화한다. observer 자체 오류나 indeterminate 결과는 runtime crash로 간주하지 않는다. pending도 연속 실패 횟수와 재시작 횟수를 소비하지 않으며 다른 독립 package의 lifecycle에 영향을 주지 않는다. 다만 준비되지 않은 장치를 healthy로 표시하지는 않는다.

    update.rollback_on_failure의 기본값은 true다. 장치가 빠진 정비·개발 환경에서도 나머지 기능이 계속 동작해야 하는 하드웨어 package만 이를 false로 둔다. 이 package도 평소처럼 시작·health 표시·재시작 감독을 받지만, 장치 미연결이 OTA 후보 전체의 rollback 사유가 되지는 않는다. 특정 차량 시험에서 그 장치를 반드시 확인해야 하면 node의 self_update.candidate_required_packages에 명시해 해당 시험에서만 release gate로 승격한다. ota-updater는 복구 경로를 준비하는 core package이므로 실행 대상으로 선택된 node에서는 이 예외를 적용하지 않으며 항상 후보 release gate에 포함된다.

    책임·권한 경계¶

    dependencies는 문서용 메타데이터가 아니라 실행 순서 계약이다. PackageManager는 의존 패키지를 먼저 시작하고, 재시작·종료 때는 역순으로 정리하며 OTA 후보 검증에도 같은 dependency closure를 사용한다. 없는 의존성이나 순환 의존성은 시작 실패이며, 실행 중인 dependent가 있으면 개별 dependency 중지를 거부한다. 따라서 로컬 메시지가 필요한 기능 패키지가 integration-gateway를 의존하면 사용자가 gateway를 패키지 목록에 다시 선택하거나 새 설정을 배울 필요가 없다.

    제어 토큰은 기본적으로 package의 build/run 환경과 Docker container에 전달하지 않는다. Master 제어면을 호출해야 하는 신뢰 package만 다음처럼 명시적으로 opt-in한다.

    control:
  credentials: true

    이 설정은 전역 관리자 권한이 필요한 core package에만 허용한다. 일반 plugin은 자체 로컬 서비스나 제한된 Master command를 사용하고 reusable token을 보유하지 않는다.

    Docker package는 privileged: true와 pid: host를 기본 수단으로 쓰지 않는다. 필요한 Linux capability와 장치를 최소 단위로 선언한다. 선택 장치는 host에 없을 때 생략할 수 있다.

    docker:
  cap_drop: [ALL]
  cap_add: [NET_ADMIN, NET_RAW]
  security_opt: [no-new-privileges:true]
  devices:
    - path: /dev/bus/usb
      optional: true

    기능마다 지속 상태와 lifecycle의 소유자는 하나뿐이다.

    책임 단일 소유자
    패키지 실행·중지·health PackageManager
    main/edge 등록·호스트 상태 main/edge 노드
    각 PC 안의 패키지 사이 요청·응답·이벤트 전달 integration-gateway
    녹화·재생·세션·NAS 전송 data-logging-system
    Autoware 시작·종료 furive-launcher
    ROS2 데이터 전달 zenoh-bridge
    OTA 정책·목표·준비·적용·복구 하나의 OTA 흐름; 구현 분리는 기술 구조 참조
    표시와 사용자 입력 Dashboard; 다른 항목의 상태는 소유하지 않음

    integration-gateway의 일반 v1 경로는 크기가 제한된 메시지를 지정된 수신자에게 전달할 뿐 업무 상태를 소유하지 않는다. 현재 hmi_dls_legacy.py만 N-1 응답 호환을 위해 DLS 명령을 분류하고 작은 휘발성 상태 projection을 둔다. 지속 녹화·재생·세션·NAS 상태와 정책은 계속 data-logging-system이 소유하고, gateway 재시작 뒤 다시 동기화한다. 새 호환 상태를 gateway에 추가하지 않으며 HMI/DLS가 v1 envelope를 직접 쓰면 이 adapter를 삭제한다.

    패키지의 데이터 요구와 플랫폼의 허용 범위, 조회·수신·명령·기록·외부 전송의 구분은 Furive OS 전체 데이터 교환 정책을 따른다. 통합 선언 schema와 동적 경로 적용은 후속 구현이며, 현재 manifest에 임의의 권한 필드를 추가해 허용된 것으로 취급하지 않는다.

    Source Unlock 실행 모드¶

    Docker package는 기본적으로 deploy repo에서 Harbor image로 실행된다. Source unlock으로 실제 package repo가 package/core/<name> 또는 package/plugin/<name>에 checkout되더라도, 명시 설정이 없으면 PackageManager는 기존 Docker 실행 방식을 유지한다.

    Source checkout에서 host run.sh를 직접 실행해야 하는 Docker package는 다음처럼 opt-in한다.

    source_unlock:
  run_mode: source
  build_script: scripts/prebuild-source.sh
  startup_probe_seconds: 2

    이 설정이 있고 source unlock checkout이 감지되면 PackageManager는 source_unlock.build_script(생략 시 build.script)를 완료한 뒤 run.sh를 subprocess로 실행한다. 사전 빌드를 수행한 경우 실행 환경에 FURIVE_OS_BUILD_PREPARED=1이 전달되므로 package는 같은 빌드를 반복하지 않을 수 있다. startup_probe_seconds를 지정하면 그 시간 안에 프로세스가 종료되는 경우 시작 성공으로 보고하지 않는다. 상태 조회, 중지, health check도 process 기준으로 처리한다. Docker image 실행과 source 직접 실행을 모두 지원하는 GUI package, 예를 들면 lotte-ohmio-mgmt, 에서 사용한다.

    Deploy source unlock 중 active config의 self_update.package_updates.<package-name>: false인 package만 실제 Git checkout을 /data/furive-os/dev-sources/package/<core|plugin>/<name>에 영구 보관하고, release tree의 원래 package 경로에는 symlink로 노출한다. 따라서 whole-release atomic swap이 일어나도 개발 workspace의 tracked/untracked 파일과 Git HEAD는 바뀌지 않는다. Source Unlock key는 updater의 clone/fetch에만 사용하고 repo-local SSH 명령으로 고정하지 않는다. 기존 package 경로에서 commit/push할 때는 쓰기 권한이 있는 사용자의 호스트 GitHub 인증 또는 SSH key가 그대로 적용된다. 기존 workspace에는 updater가 fetch만 수행하며 stash/reset, release ref checkout 또는 submodule update를 수행하지 않는다. detached HEAD에는 같은 commit의 로컬 작업 branch만 연결할 수 있다. FURIVE_OS_DEV_SOURCE_ROOT로 경로를 바꿀 수 있지만 updater와 launcher를 포함한 모든 실행 환경에 같은 값을 제공해야 한다.

    기본 managed checkout을 독립 개발 저장소로 전환하려면 package 경로에서 .git을 제거하고 git init한다. 다음 source sync는 원래 Source Unlock remote가 없는 새 Git 저장소를 사용자 takeover로 판정하고 기존 self_update.package_updates.<name>: false 정책을 기록한 뒤 영구 workspace로 옮긴다. deploy 루트의 git status에서는 installer-owned overlay를 숨기지만, package 경로의 git status에는 개발자의 tracked/untracked 변경이 그대로 보인다.

    Deploy image package의 source checkout은 소스 저장소의 package.yaml을 포함하지만, runtime 정책은 release가 생성한 release/package-manifests.yaml 사본을 사용한다. 따라서 source-unlock이 package 경로를 checkout 또는 symlink로 바꿔도 Harbor digest, architecture별 image와 distribution lock은 바뀌지 않는다. launcher는 source sync 전후에 artifact integrity를 각각 검사하며, sync 뒤 release manifest와 package lock이 어긋나면 package를 시작하지 않는다.

    설정이 없거나 true이면 package OTA가 기본 동작이다. false에서 true로 되돌리면 외부 workspace를 원래 package 경로로 이동하고, Source Unlock key가 있으면 dirty 파일을 stash한 뒤 manifest의 release ref로 정렬한다.

    next_restart OTA는 현재 release를 실행한 채 후보 checkout에서 source package를 사전 빌드한다. 기본적으로 non-Docker build.script와 source mode의 source_unlock.build_script가 대상이다. 사전 빌드가 외부 장치나 실행 중 서비스에 영향을 줄 수 있는 package는 다음처럼 제외한다.

    OTA가 중단된 영구 source-unlock workspace는 개발자가 소유한 작업트리이므로 release image pull과 후보 사전 빌드에서 자동 제외한다. 후보 활성화 후 PackageManager가 기존 symlink를 통해 현재 개발 source를 실행하고 health gate는 그대로 적용한다.

    update:
  prebuild: false

    사전 빌드 script는 FURIVE_OS_PREPARE_ONLY=1, FURIVE_OS_CANDIDATE_ROOT=<staging-root> 환경을 받을 수 있으며 실행 프로세스를 띄우지 않고 후보 artifact만 완성해야 한다. 성공하면 updater가 release HEAD와 build script가 기록된 일회성 marker를 남긴다. 후보의 첫 PackageManager 시작은 marker를 소비하고 동일 build를 건너뛰며, 이후 일반 package 재시작은 기존 build/hash 정책을 다시 따른다. prebuild: false인 host build package는 후보 시작 직전에 이전 정상 release의 build 자산을 승계할 수 있다. PackageManager는 실행 전에 package의 build script를 호출하므로 .build_hash가 현재 source와 다르면 재빌드하고, 같을 때만 기존 결과를 사용한다.

    Release CI에서 만든 결과를 차량이 다시 빌드하면 안 되는 source package는 deploy.built_assets에 상대 경로를 선언한다. deploy exporter는 전역적으로 제외하는 dist/, build hash 같은 생성물 중 선언된 항목만 포함하고 deploy용 .gitignore 예외를 만든다. release 검증은 각 항목이 실제 deploy commit에 추적되는지도 확인하며, 누락되면 release를 실패시킨다. 따라서 차량 OTA는 검증된 결과를 그대로 사용하고 npm 같은 개발 의존성을 내려받지 않는다.

    build:
  script: build.sh
deploy:
  built_assets:
    - web/dist
    - .build_hash

    시작·중지 규칙 (lifecycle)¶

    lifecycle은 PackageManager가 stop/restart를 어떻게 다룰지 정하는 운영 정책이다.

    lifecycle:
  stop_timeout_seconds: 30
  restart_on_autoware_stop: true
    필드 의미
    stop_timeout_seconds Docker stop, subprocess SIGTERM 대기, lifecycle command timeout의 기본값.
    pre_stop 패키지 stop 전에 실행할 argv 또는 argv 목록. 문자열 호환 입력도 shell 없이 argv로만 해석한다.
    post_stop 패키지 stop 후 실행할 argv 또는 argv 목록. pipeline·redirect·substitution 같은 shell 문법은 실행하지 않는다.
    restart_on_autoware_stop Autoware 종료 후 잔여 ROS2 graph/cache 정리를 위해 재시작할지 여부. 미지정 기본값은 false. 자동 재시작이 필요한 패키지만 true로 명시한다.
    restart_on lifecycle event별 재시작 정책을 mapping/list/string으로 표현할 때 사용.

    Autoware 종료는 독립 furive-launcher가 감지해 master에 autoware_stopped lifecycle event를 보낸다. master는 로컬 PackageManager와 연결된 agent에 lifecycle_event: autoware_stop을 generation과 함께 전파하고 마지막 generation을 저장한다. 끊겼다가 재접속한 agent는 최신 generation을 한 번만 적용한다. PackageManager는 실행 중인 패키지 중 lifecycle.restart_on_autoware_stop: true를 명시한 패키지만 재시작하며, 이 값이 없거나 false이면 재시작하지 않는다. dashboard는 이 lifecycle 경로에 관여하지 않는다.

    다시 시작 조건 (restart_triggers)¶

    restart_on top-level 필드는 설정 변경에 반응하는 재시작 조건이다.

    restart_on:
  - ros_domain_id

    예를 들어 ROS domain 변경 시 ros_domain_id를 선언한 패키지 또는 manifest 안에 ROS_DOMAIN_ID를 명시적으로 참조하는 구형 패키지는 재시작 대상이 된다.

    패키지가 소유하는 테스트¶

    root pytest는 의도적으로 package/를 수집하지 않는다. 대신 CI 내부의 run-package-tests가 runtime과 같은 discovery로 package/core/*, package/plugin/*를 inventory하고 각 package의 test를 그 package cwd에서 실행한다. 독립 서비스 gitlink는 해당 package 저장소 revision을, root가 직접 소유하는 얇은 통합 package는 root revision을 증거로 사용한다. 개발 검사는 보이는 direct package도 실행하지만 release 검사는 root 전체가 clean하고 package가 추적된 상태여야 통과한다. FURIVE_OS_EXTERNAL_PACKAGE_DIRS로 명시한 독립 저장소도 manifest 검증과 같은 경로로 test한다.

    현재 runner가 발견하는 형식은 다음과 같다.

    • package root의 test_*.py, *_test.py, test/·tests/의 Python test
    • src/<ros-package>/test·tests의 Python test
    • package.json에 선언된 scripts.test
    • test/·tests/·scripts/ 아래 test-*.sh

    official package에는 이 중 적어도 하나의 실행 가능한 suite가 있어야 한다. 발견된 test가 없거나 manifest를 읽을 수 없거나 suite가 실패·timeout되면 root/PR gate 전체가 실패한다. ROS나 장치가 없는 사무실 CI에서도 판정해야 하는 logic은 module shim, fixture와 fake adapter로 실제 분기를 실행한다. 장치가 필수인 test는 조용히 skip해 이 lane을 통과시키지 않고 별도 bench/HIL lane에서 필수 증거로 관리한다.

    현재 runner는 no-tests·timeout을 fail-closed 처리하고 source 종류, 기대 revision, 실제 HEAD, 시작·종료 dirty status, 실행 worktree hash, 명령과 stdout/stderr가 포함된 JSON report를 만든다. 개발 PC에서는 아직 commit하지 않은 수정도 그대로 시험하되 그 사실을 report에 표시한다. trusted CI/release에서는 actual HEAD가 기대 revision과 다르거나 test 전후 source repository가 clean하지 않으면 실패한다. Python suite는 JUnit을 생성하며 skip 수가 하나라도 있으면 성공 코드를 실패로 승격한다. TAP Node suite도 test/pass/fail과 skip/todo/cancelled를 파싱해 exit 0 안의 필수 case 누락을 실패시킨다. trusted CI는 package JSON/JUnit과 root pytest JUnit을 함께 보존한다.

    각 package는 위험에 맞는 세 경계를 소유한다. 계산·파싱·상태 전이는 production 함수를 직접 호출하는 unit test로, process/signal/filesystem/ROS adapter는 실제 entrypoint와 격리된 fake dependency를 잇는 integration test로 검사한다. 사용자가 보는 핵심 결과는 release image/entrypoint를 기동해 API, ROS message, 파일 또는 화면으로 확인하는 semantic E2E를 둔다. 장치가 필요한 E2E는 source test의 mock 통과로 대체하지 않고 bench/HIL lane으로 분리한다.

    Native test는 기능 분기를 실제로 호출해 입력과 관측 결과를 assert해야 한다. 다음은 단독으로 의미 동작의 증거가 아니다.

    • 파일·함수명·source 문자열이 존재한다는 검사
    • PID, port 또는 Docker container가 살아 있다는 검사
    • 아무 일도 하지 않는 run.sh, sleeper, 항상 성공하는 health
    • mock 호출만 확인하고 외부에 보이는 payload·파일·ROS message를 확인하지 않는 검사

    Release 증거에는 root SHA, 독립 package gitlink SHA, JUnit과 전체 log를 묶는다. RC/시험 배포까지 승격할 때는 같은 묶음에 exact artifact/image digest, 플랫폼/Autoware SHA와 ROS/API/파일 probe도 추가한다. Source test 통과는 RC semantic smoke나 차량 OTA/HIL 통과를 대신하지 않는다.

    package/shared/msgs는 package가 아니라 공용 ROS interface source다. Release base image는 그 저장소의 prebuilt install을 ABI 증거로 신뢰하지 않고 target architecture에서 source를 clean build한다. Release export는 architecture별 install-<arch>를 같은 /data/furive-os/msgs/install target의 상호 배타적인 runtime asset으로 기록한다. 차량 시작과 OTA activation은 해당 asset을 refresh하고 architecture/source digest가 일치하지 않으면 package를 시작하지 않는다. 개발 PC 설치도 architecture와 source digest가 모두 맞는 install만 재사용하며 먼저 build를 확인한 뒤 /data로 동기화한다.

    검증¶

    Furive 연결 검증에는 다음을 실행한다.

    ./furive package check

    이 명령과 release/CI는 중복 package name도 실패 처리한다. 내부 validator를 직접 호출할 필요는 없다.

    ./furive package list

    발견된 package는 위 명령으로 빠르게 보고, 상세 런타임 discovery 결과는 다음 파일에서 확인한다.

    logs/effective-packages-master.json
logs/effective-packages-agent.json

    로그 디렉터리를 만들 수 없는 비정상 환경에서는 PackageManager가 /tmp/furive-os/logs로 fallback하고 실행을 계속한다.
