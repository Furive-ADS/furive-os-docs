    이전 정상 버전 복구 기준¶

    이 문서는 준비된 새 버전을 언제 적용하고, 실패했을 때 어떤 상태로 돌아가는지 설명하는 내부 자료입니다. 운용자는 차량 업데이트의 화면 안내를 따릅니다.

    버전 사이의 호환성과 중간 버전 선택은 업데이트 호환 정책에서 설명합니다.

    이 문서에서 찾을 것¶

    질문 담당 코드
    어떤 배포 버전을 받을지, 언제 준비할지 core/self_updater.py
    새 버전을 적용·확정하거나 직전 상태로 복구하기 core/release_activation.py
    전환 중에도 멈추지 않는 시작 프로그램 최상위 run.sh와 설치된 서비스
    상태 표시와 사용자 입력 운영 화면과 furive status

    각 패키지는 자신의 시작 방법과 정상 상태만 알려줍니다. 패키지마다 별도 업데이트·복구 프로그램을 만들지 않습니다. 아래 파일명과 설정명은 코드를 찾을 때만 쓰는 내부 이름입니다.

    Furive는 새 버전을 발견해도 실행 중인 버전을 바로 덮어쓰지 않습니다. 새 버전을 별도 위치에 준비한 뒤 운영자가 차량의 안전 상태를 확인하고 재시작할 때 전환합니다. updater가 운행 안전 여부를 대신 판단하지는 않습니다.

    한눈에 보는 동작 순서¶

    현재 배포 버전 실행
  → 현재 Git 폴더를 별도 후보 폴더로 복사
  → 후보 폴더만 새 Git tag·commit에 맞춤
  → 연결 저장소·대용량 파일·Docker 이미지·빌드 준비
  → 현재 버전은 계속 실행
  → 다음 재시작에서 현재 폴더와 후보 폴더를 한 번에 교환
  → 모든 패키지를 시작하고 정상 상태 확인
  → 성공: 새 버전 유지, 직전 상태 1개 보관
  → 실패: 직전 코드·설정·Docker 이미지로 복구

    Git 내려받기, Docker 이미지 받기, 소스 빌드 중 하나라도 실패하면 후보 폴더만 버립니다. 현재 버전과 실행 중인 패키지는 멈추지 않습니다.

    ota-updater 하나만 새 버전 확인과 준비를 맡습니다. 운영 화면은 상태를 보여주고 사용자의 명령만 전달합니다.

    재시작 때 전환하고 실패하면 복구하기¶

    run.sh는 완성된 후보가 있으면 Linux의 디렉터리 교환 기능으로 현재 폴더와 후보 폴더를 한 번에 바꿉니다. 교환 직전에 서명, 목표 commit, Git 파일과 배포 정보를 다시 확인합니다. 두 폴더는 같은 디스크에 있어야 하므로 시스템이 설치 위치에 맞는 준비 폴더를 자동 선택합니다. 다른 개발 작업 폴더와 업데이트 상태를 공유하지 않습니다. 교환 뒤 새 코드가 모든 패키지를 시작합니다.

    furive setup --repair는 기존 업데이트 기록이 현재 설치 폴더의 것인지 확인한 뒤에만 이어 씁니다. 경로가 남아 있다는 이유만으로 다른 설치의 기록을 사용하지 않습니다.

    모든 패키지가 정해진 시간 동안 계속 정상이어야 새 버전을 확정합니다. 제한 시간 안에 하나라도 정상화되지 않으면 새 패키지를 먼저 종료하고 이전 버전으로 돌아갑니다. CAN 패키지는 프로그램 실행 여부뿐 아니라 두 CAN 장치가 실제로 준비됐는지도 확인합니다.

    새 버전이 확정되기 전에 프로그램이 죽거나 다시 시작돼도 다음 시작에서 이전 버전으로 돌아갑니다. 실패한 같은 commit은 반복 적용하지 않으며, 더 새 버전이 올라오면 다시 준비합니다. 운영자가 직접 고정한 이전 버전은 자동으로 해제하지 않습니다.

    정상 확인 뒤에도 업데이트 직전 상태를 바로 지우지 않는다. 대시보드의 이전 정상 또는 updater의 previous 복귀를 선택하면 해당 시도 직전에 보존한 release tree, mutable Docker tag, /data/furive-os 아래 실행 설정을 함께 복구한다. 설정 snapshot은 이름이 config인 디렉터리와 루트 설정 파일만 포함하며 logs, datasets, binaries, version state는 포함하지 않는다. 따라서 주행 기록은 롤백 때문에 과거 상태로 되감기지 않는다. 새 후보를 준비할 때 복구 슬롯은 그 시점의 실제 현재 상태로 교체된다. 그 사이 Furive OS 업데이트가 여러 번 있었더라도 release에 미리 적힌 과거 버전을 찾지 않으며, 항상 이번 업데이트 시도 직전 상태 하나를 기준으로 한다. 대시보드는 이 즉시 복귀 항목과 현재 channel에 보존된 과거 signed release 전체를 함께 보여준다. preview/<vehicle_id>는 그 차량의 test tag만, main은 suffix 없는 normal tag만 목록에 포함한다. 이전 정상은 이미 보존한 전체 상태를 즉시 복구하고, 그보다 오래된 버전은 일반 업데이트와 같은 별도 준비·호환성 검증·다음 재시작 절차를 거친다. 목록 포함은 적용 가능 판정이 아니다. 후자는 같은 identity가 같고 설정 변환이 필요 없는 controlled return만 허용하며 검증에 실패하면 현재 release를 유지한다.

    후보 staging이 완료되면 updater는 candidate marker, host supervisor, active/finalized 동일 filesystem, 현재 release에 결박된 Docker image snapshot을 읽기 전용으로 다시 검증한다. 이 복구 사전 확인 결과는 rollback_readiness로 상태에 포함되며, apply_update는 ready가 아니면 재시작 예약을 거부한다. Persistent config snapshot은 실제 값의 변경 경쟁을 줄이기 위해 release 전환 직전에 만들고 검증한 뒤, 성공한 경우에만 원자 교환한다.

    Credential bundle은 과거 ZIP을 장기 rollback artifact로 삼지 않는다. 기존 설치에 bundle을 적용하는 경로도 candidate activation을 사용해 설치 직전 release를 retained previous로 남긴다. 완전히 새 PC에는 pre-install release가 없지만, 원격에 보존된 호환 과거 signed release는 일반 controlled return으로 준비할 수 있다. 오프라인 전달이 필요하면 fleet assignment의 정확한 version을 선택해 현재 credential로 bundle을 다시 만든다. Bundle이 release history나 rollback 정책을 별도로 소유하지 않는다.

    상태 파일과 보존 디렉터리는 다음과 같다.

    경로 의미
    <staging>/finalized 다음 재시작에 적용할 완성 후보
    <staging>/old_furive-os 다음 정상판을 준비하기 전까지 보존하는 이전 정상 release
    <staging>/failed-furive-os 자동 복구 후 보존하는 실패 후보
    <staging>/persistent-config-snapshot 직전 정상판의 실행 설정 복구본
    <staging>/.release-image-snapshot.json mutable Docker tag의 이전 image ID
    <staging>/.release-activation.json idle, 교환·롤백 journal, guarded candidate, good, rolled_back, error 상태와 commit/health 기록
    <repo>/.rollback_pin 같은 실패 후보 재적용 또는 수동 rollback 자동 업데이트 방지

    설정¶

    self_update:
  auto_apply_on_detect: false
  candidate_health_timeout_seconds: 180
  candidate_stable_seconds: 5
  # 생략/true는 일반 OTA. false인 Source Unlock package만 작업공간을 보호한다.
  package_updates:
    lotte-ohmio-mgmt: false
  # 생략하면 config의 packages 전체를 검사한다.
  # candidate_required_packages: [dashboard, lotte-ohmio-can-ros2]

    기본값 auto_apply_on_detect: false에서는 업데이트 탐지만 주기적으로 수행하고, Dashboard에서 적용을 선택할 때 후보를 준비한다. 따라서 평상시 service 장애 재시작이 아직 승인하지 않은 일반 OTA를 우연히 활성화하지 않는다. true는 탐지 시 후보 준비까지 자동화해야 하는 통제된 환경에서만 사용한다. fleet의 exact target 수렴은 이 일반 채널 기본값과 별도 정책이며, OTA apply와 rollback은 모두 같은 staged ReleaseActivation 경로를 사용한다. run.sh의 시작 전 인플레이스 git sync도 기본적으로 꺼져 있으며, 유지보수 목적으로 꼭 필요할 때만 FURIVE_OS_ALLOW_INPLACE_SYNC=1을 명시한다.

    후보 release에서 ota-updater가 실행 대상으로 선택됐다면 이 package는 candidate_required_packages나 update.rollback_on_failure로 후보 검증에서 제외할 수 없다. 후보의 프로세스 생존뿐 아니라 OTA 제어 응답과 polling thread를 확인한 뒤에만 정상 release로 확정한다. 응답하지 않거나 polling이 중단된 후보는 정상판이 되지 않으며, 후보 코드가 아닌 안정된 host launcher가 이전 release로 되돌린다. 단순 상태 관찰 timeout은 기존 복구 담당 프로세스를 즉시 종료하는 근거로 쓰지 않아, 오래 걸리는 검증 중 updater를 스스로 끊지 않는다.

    상태는 다음 명령으로 확인한다.

    furive status
furive status --json

    CI와 test 배포 검증기는 내부적으로 strict OTA 검사까지 수행한다. 사용자는 해당 구현 script를 직접 호출하지 않고 위 공개 상태 명령과 Dashboard를 사용한다.

    업데이트할 프로그램 준비¶

    • 일반 시작은 설치된 소스와 로컬 이미지를 사용하며 원격 소스 동기화나 이미지 일괄 pull을 기다리지 않는다. 이미지 배포 package의 기본 pull 정책은 missing이다. 필요한 이미지가 없는 package만 다운로드가 필요하다.
    • Docker image 배포 package는 release/package-images.tsv의 선택 package 및 공용 base image를 staging 중에 준비한다. 정확한 digest의 이미지가 이미 있으면 재사용한다. 변경 가능한 태그는 staging에서 pull에 성공해야 하며, 통신 실패 시 이전 태그 캐시를 새 후보로 간주하지 않는다. 다운로드·사전 빌드가 실패하거나 지연되어도 현재 release를 교체하지 않고, 준비가 완료된 후보만 다음 재시작에 적용한다.
    • script, colcon, binary source package의 build.script는 staging checkout에서 실행한다.
    • source_unlock.run_mode: source package는 source_unlock.build_script를 staging에서 실행한다. 성공한 후보에는 release HEAD가 묶인 일회성 prebuild marker를 남겨 첫 PackageManager 시작이 같은 script를 다시 실행하지 않는다. MGMT는 build hash와 last-known-good runtime cache도 사용해 변경 없는 telemetry/UI 빌드를 건너뛴다.
    • 차량에서 self_update.package_updates.<name>: false로 OTA를 중단한 source unlock 개발 package만 실제 Git checkout을 /data/furive-os/dev-sources에 영구 보관한다. OTA는 이 workspace를 stash/reset/checkout하거나 사전 빌드하지 않고 후보 release의 원래 package 경로에 symlink만 재연결한다. 해당 경로에서 개발자가 수행한 commit/push와 dirty 작업은 whole-release atomic swap 뒤에도 유지된다.
    • master에 존재하는 외부 furive_autoware_main Git checkout은 release/external-workspaces.yaml에서 active capability_profile에 고정된 40자리 commit SHA도 release 구성요소로 취급한다. 이 선택은 Furive OS branch/tag와 독립적이므로 동일 release에서도 lotte-ohmio, ipg-g80, furive-niro가 서로 다른 Autoware SHA를 적용할 수 있다. staging에서는 target SHA를 fetch만 하고 atomic swap callback에서 checkout한다. 적용 직전에 루트/하위 repo의 실제 HEAD와 branch, tracked 변경 및 build/install을 한 묶음으로 캡처한다. candidate 또는 수동 release rollback은 release에 적힌 임의의 이전 commit이 아니라 바로 그 업데이트 시도 직전 상태를 재빌드 없이 복구한다. branch 값은 fetch/audit metadata이고 실제 적용 identity는 commit SHA이다. 정상 확인 뒤에도 이 복구 묶음 하나는 유지하고, 다음 Autoware OTA가 시작될 때 당시의 실제 상태로 교체한다. 각 snapshot은 이를 만든 Furive 후보 HEAD와 결합되어 다른 Furive-only update의 rollback에는 사용되지 않는다. repos_manifest 하위 repository는 release에 기록된 개별 40자리 SHA를 사용한다. 일반 release는 플랫폼별 빌드 fingerprint나 receipt를 요구하지 않고 exact root·하위 SHA만 고정하며 artifact에 build_validation: not_performed를 기록한다. 실제 적용 build와 rollback은 외부 Autoware 업데이트를 명시적으로 켠 차량의 다음 경로가 소유한다.
    • 외부 Autoware OTA on/off는 default-first/local-override 방식의 self_update.external_updates.furive-autoware-main으로 결정한다. 현재 default는 false이며 local true를 명시한 차량만 업데이트한다. false이면 fetch와 checkout을 모두 생략해 source 작업공간을 hold한다. 이 경로는 Docker image pull/build를 포함하지 않고, 최초 설치의 Autoware image 준비와 분리한다.
    • 외부 Autoware checkout 적용 직후에는 commit diff를 package.xml에 매핑한 선택 colcon build를 실행하고 매핑할 package가 없으면 전체 build한다. 로그와 상태는 각각 logs/furive_autoware_build.log, logs/furive_autoware_build.status.json에 보존한다. build 실패 시 candidate와 외부 source/build/install을 업데이트 시도 직전 상태로 함께 rollback한다. external update hold이면 snapshot, checkout, build, rollback을 모두 실행하지 않는다.
    • staging 중 apt/colcon처럼 host를 오래 점유하는 package는 update.prebuild: false를 사용한다. RS80은 이전 정상 release의 build/install/hash를 후보 시작 직전에 승계한 뒤, PackageManager가 현재 source hash를 다시 검사한다. source가 같으면 즉시 재사용하고 다르면 실행 전에 재빌드한다.
    • 후보 준비 시 사전 빌드하면 안 되는 package는 update.prebuild: false를 명시한다.
    • health_check는 단순 프로세스 존재보다 실제 사용 가능 조건을 표현해야 한다. 하드웨어가 필요한 package는 interface/device/topic 준비 상태를 검증해야 한다.

    보장 범위¶

    이 구조는 소프트웨어 update/build 실패 때문에 현재 정상 release가 사라지지 않도록 하고, 직전 정상판 한 개로 코드·이미지·실행 설정을 함께 복구한다. 과거 차량별 업데이트 경로의 1회 전환판은 이전 설정을 먼저 보존한 뒤 후보 기능 시작 직전에 설정을 보정하고, 보정 완료와 health가 모두 확인될 때만 확정한다. 어느 쪽이든 실패하면 과거 경로까지 복구한다. 기존 구버전 설정 변환 완료 이력도 전환판에 이어받아 끝난 작업을 불필요하게 다시 실행하지 않는다.

    자동 legacy 인계의 최저 기준은 v2026.06.17 차량별 배포판이다. active tree의 구형 평문 marker만 신뢰하지 않고 marker의 이전/후보 commit, 실제 retained checkout, Git ancestry와 변경 수, 전환판의 deploy metadata·branch·tag·deferred migration을 함께 검증한다. 기존 candidate state가 있는 v2026.07.07 이후 배포판은 snapshot schema를 현재 journal로 보수적으로 승격한다. 첫 bridge가 확정된 뒤 host launcher에 supervisor contract가 없거나 후보가 요구하는 최소 contract보다 낮고, unit/token 연결도 구 계약이면 다음 staging은 furive setup --repair 완료까지 fail-closed한다. launcher byte hash 차이만으로는 막지 않는다. repair는 candidate/switching 상태에서는 시작하지 않고, 누락 unit을 다시 쓰며, 기존에 실행 중이던 service를 끝에서 재시작해 영구 token을 현재 updater에도 적용한다. 이보다 오래된 설치 또는 marker·backup 증거가 모호한 상태는 setup --repair 대상이 아니다. 최신 credential bundle의 bootstrap.sh --mode <main|edge> --target-dir <현재 설치 경로>로 known-good 배포를 복구한다.

    후보 전환 순간에는 package 재시작에 필요한 짧은 중단이 있다. CAN 장치 자체 고장, 전원 단절, 디스크 손상처럼 이전 release에서도 해결할 수 없는 하드웨어 장애는 복구할 수 없다. logs/datasets/database 자체는 자동 snapshot하지 않으므로 이를 변경하는 migration은 반드시 이전판도 읽을 수 있는 방식으로 작성해야 한다. 파괴적 데이터 변환이 필요한 release는 이 일반 OTA 경로에 넣지 말고 별도 백업·복구 절차를 먼저 설계한다.
