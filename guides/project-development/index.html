    별도 프로젝트로 개발하기¶

    다른 조직이 자기 차량과 프로그램을 연결할 때는 별도 Git 프로젝트 안에서 승인된 Furive OS 공통 버전을 선택합니다. 플랫폼·패키지·발행 대상은 프로젝트가 소유하고 공통 코드는 재사용합니다. 이 경로는 새 프로젝트를 위한 것이며 기존 니로·오미오·EV9 설치나 기존 source 개발을 이전하지 않습니다.

    flowchart LR
  Project["조직 프로젝트<br/>플랫폼·선택 패키지·발행 입력"] --> Common["선택한 common revision<br/>공통 검사·실행·업데이트"]
  Project --> CI["조직의 CI·서명·배포 인프라"]
  CI --> Vehicle["검증된 지원 차량"]

    1. 공통 코드 선택하기¶

    Linux 개발 PC에 Git, Python 3.10 이상, PyYAML·pytest와 선택한 패키지의 개발 도구가 필요합니다. 공통 native 구성에는 Rust 1.85.1 cargo와 rustc, C 컴파일러 cc가 필요합니다. 공통 Python 가상 환경을 준비하려면 개발 환경 준비를 참고합니다. 먼저 조직에서 접근을 확인한 common 저장소 URL과 사용할 정확한 revision을 준비합니다. 아래 <...>는 실제 값으로 바꾸는 예시입니다.

    mkdir my-vehicle
cd my-vehicle
git init
mkdir -p toolchain
git submodule add <common-repository-url> toolchain/furive-os
git -C toolchain/furive-os checkout <approved-common-revision>
git add .gitmodules toolchain/furive-os
ln -s toolchain/furive-os/furive furive

    git submodule add는 프로젝트의 Git 등록을 변경합니다. git status로 결과를 확인하고 프로젝트에서 commit합니다. common을 자동으로 받거나 모든 private submodule을 재귀 clone하지 않습니다. 선택한 core 패키지 등 별도 checkout이 필요하면 그 저장소의 접근 권한과 revision을 확인해 필요한 경로만 준비합니다.

    프로젝트 루트에 일반 파일 furive-project.yaml을 만듭니다.

    version: 1
common: toolchain/furive-os

    ./furive symlink와 common이 같은 checkout을 가리켜야 합니다. git add furive furive-project.yaml로 두 파일도 프로젝트에 등록하고 선택한 common gitlink와 함께 commit합니다. 명령은 이후 프로젝트 루트에서 실행합니다. common을 직접 수정하는 작업은 공통 개발 시작을 따릅니다.

    2. 프로그램과 플랫폼 연결하기¶

    자체 프로그램의 저장소와 접근 권한을 확인한 뒤 연결합니다. 아래 이름은 해당 패키지 manifest의 이름으로 바꿉니다.

    ./furive package add <package-repository-url>
./furive package list

    add는 프로젝트의 package/plugin/ 아래 Git submodule을 등록합니다. 목록에 선택한 패키지가 나타나는지 확인하고 git status에서 등록 내용을 검토한 뒤 commit합니다. common에 있는 패키지가 모두 자동 선택되지는 않습니다. 공통 core 패키지는 common의 package/core/와 같은 디렉터리 이름으로 프로젝트에 symlink를 둡니다. 디렉터리 이름과 manifest의 패키지 이름은 다를 수 있습니다. 정확한 연결 경로는 패키지 계약을 따릅니다.

    차량·센서와 PC 역할을 쓰려면 프로젝트 config/에 플랫폼 설정을 준비합니다. 프로젝트 안의 별도 플랫폼 저장소를 연결할 수도 있습니다. 패키지 배정과 장치·Autoware 모델은 차량 플랫폼 만들기, 정확한 설정·검사 범위는 플랫폼 원본 검사를 따릅니다. 필요한 차량·Autoware 대상과 revision을 명시하고 선택하지 않은 common 설정이 대신 적용된다고 가정하지 않습니다.

    3. 검사하고 개발 실행하기¶

    ./furive check
./furive package run <package-name>

    프로젝트의 ./furive check는 선택한 프로젝트 패키지와 플랫폼 설정을 확인하고 각 패키지의 테스트를 실행합니다. 성공 출력의 scope=project와 패키지 목록을 확인합니다. 프로젝트의 ./furive package check도 같은 검사를 실행합니다. 전경 실행은 프로그램이 만드는 파일이나 API 결과와 프로젝트 logs/의 로그를 확인한 뒤 Ctrl+C로 종료합니다. 실패하면 출력된 패키지·단계와 로그를 확인하고 수정 후 다시 실행합니다.

    프로젝트 플랫폼에 PC별 배정을 준비했다면 미설치 개발 PC의 첫 node 실행에 역할을 지정합니다.

    ./furive dev edge --no-ui

    필요한 패키지가 선택된 역할에서 시작되는지 로그와 실제 기능으로 확인합니다. 종료는 Ctrl+C입니다. 다른 PC 역할이나 화면이 필요하면 ./furive dev --help를 확인합니다. 프로젝트 검사·개발 실행은 common 전체 회귀, Autoware 실제 빌드, 설치 또는 차량 시험을 대신하지 않습니다. 자세한 실행·실패 경계는 패키지 계약을 봅니다.

    4. 배포가 필요할 때¶

    조직의 source·deploy 저장소와 registry를 프로젝트에 선언하고 정확한 Git 입력 및 조직 CI 검증을 준비한 뒤 발행 계획을 확인합니다.

    ./furive release normal --date 2026-10-21 --number 1 --json

    --run은 조직 CI에 발행을 요청하며 서명·게시 완료를 의미하지 않습니다. 현재 요청 adapter는 GitHub source와 조직이 구성한 workflow를 사용합니다. CI runner, 실제 build·검사 및 보호된 서명 승인은 조직이 준비합니다. 입력 형식, test 차량 선택과 결과 확인은 독립 발행 계약을 따릅니다.

    서명된 release와 별도 확인한 신뢰 입력이 준비되면 ./furive bundle로 설치 전달물을 만들 수 있습니다. 필수 인자와 검증은 프로젝트 bundle 전달을 봅니다. 기존 설치·구형 차량의 전환, 실제 image·차량 동작과 복구는 별도 검증이 필요하며 프로젝트 source 검사만으로 완료되지 않습니다.
