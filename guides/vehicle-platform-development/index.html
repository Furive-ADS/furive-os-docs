    차량 플랫폼 만들기¶

    새 차량·센서 구성을 Furive에 연결할 때 이 문서를 사용합니다. 플랫폼은 여러 차량이 공유할 차량·센서 구성, 정확히 고정한 Autoware 소스 버전과 PC별 패키지 조합입니다. Furive가 임의의 모든 차량을 자동 지원한다는 뜻은 아닙니다. 설치, 프로세스 감독, 로그, 대시보드, OTA는 공통 Furive 기능이므로 플랫폼마다 복사하지 않습니다.

    플랫폼명과 Autoware 모델명은 다릅니다¶

    두 이름은 서로 다른 대상을 가리키며 같을 필요가 없습니다.

    이름 예 소유하는 것
    Furive 플랫폼 lotte-ohmio 패키지 구성, 화면·지도 기본값, Autoware 버전 선택
    Autoware 모델 이름 lotte_bus <이름>_vehicle과 <이름>_sensor_kit의 공통 앞부분

    예를 들어 lotte-ohmio 플랫폼이 선택한 Autoware 작업 공간 안에 lotte_bus_vehicle과 lotte_bus_sensor_kit이 있어도 정상입니다. vehicle 모델과 sensor-kit 모델은 서로 같은 이름 앞부분으로 한 쌍을 이루지만, 이를 Furive 플랫폼명과 맞추는 규칙은 없습니다.

    실제 선택 흐름은 다음과 같습니다.

    차량 ID
  → Furive 플랫폼
  → 한 PC에 함께 배정하거나 A-ECU·HMI-ECU로 분산
  → 플랫폼에 고정된 Autoware 소스 버전
  → 그 작업 공간의 Autoware 차량/센서 모델 선택
  → Autoware 실행 프로그램이 시작·중지

    변경을 담당하는 곳 찾기¶

    바꾸려는 것 담당하는 곳 기준 위치
    차량별 플랫폼·업데이트·버전 차량 배정 정보 core/fleet_assignment.py, config/fleet-vehicles.yaml
    플랫폼의 패키지·화면·지도 조합 플랫폼 구성 config/capability-profiles.yaml
    플랫폼이 받을 Autoware 소스 버전 소스 버전 고정 설정 config/external-workspaces.yaml
    Autoware 차량 모델·보정 Autoware 저장소 <prefix>_vehicle 계열
    Autoware 센서 배치·보정 Autoware 저장소 <prefix>_sensor_kit 계열
    CAN·장치 연결 기능 해당 차량 패키지 독립 패키지 저장소, 공통 연결 코드는 core/vehicle_control.py
    Autoware 탐색·시작·중지 Autoware 실행 프로그램 package/core/furive-launcher, core/launcher_control.py

    HMI, 로깅, 장치 driver처럼 다른 차량도 독립적으로 사용할 수 있는 기능은 Autoware 모델에 넣지 않고 별도 패키지로 둡니다. 새 프로그램 연결은 프로그램 연결을 먼저 완료합니다.

    1. 구현을 실제 소유 저장소에 두기¶

    Autoware 실행·설정과 차량·센서 모델은 별도 Autoware 작업 공간에서 개발하고 테스트합니다. 독립 기능은 그 기능의 패키지 저장소에서 개발합니다. Furive OS에는 이 소스 코드를 복사하지 않고 선택 정보만 둡니다.

    차량 구동·센서 배치는 Autoware 모델, CAN 장치·독립 서비스는 해당 패키지, 기능 사용 여부는 플랫폼 구성이 담당합니다. 설치·로그·상태 확인·업데이트는 Furive 공통 코드에서 수정합니다.

    2. 플랫폼 구성을 연결하기¶

    config/capability-profiles.yaml에 플랫폼 이름 하나를 만들고 필요한 main/edge 패키지와 기본 화면, 설치 묶음에 포함할 승인 지도만 연결합니다. 내부 YAML에는 master/agent가 남아 있고 source 개발에서는 main/edge 역할을 사용합니다. 일반 설치·운용 안내에서는 플랫폼의 장비 이름을 씁니다.

    PC 한 대에서 함께 쓸 기능은 기존 node_configs.master.packages에 명시적으로 배정합니다. 분산 배정은 A-ECU의 자율주행과 HMI-ECU의 로깅·부가 기능으로 나눕니다. 1PC에서도 공통 runtime을 복사하거나 두 역할의 설치를 중복 실행하지 않습니다. 장치·ROS domain·의존성·화면·포트와 동시 부하, 현재 중앙 토픽 CLI의 제약은 ECU 설치 설계를 따릅니다.

    그 플랫폼 이름을 config/external-workspaces.yaml의 targets.capability_profiles에도 사용해 Autoware 최상위 저장소와 관리 대상 하위 저장소를 정확한 commit으로 고정합니다. Git branch의 최신값을 차량에서 다시 해석하게 두지 않습니다.

    두 파일의 역할은 겹치지 않습니다.

    • capability-profiles.yaml: 차량이 어떤 패키지 구성을 실행하는가
    • external-workspaces.yaml: 그 구성이 어떤 Autoware 소스 버전을 받는가

    차량 한 대는 furive vehicle set으로 이 플랫폼을 참조합니다. 차량별 설정 파일을 복사하거나 영구 차량 전용 branch를 만들지 않습니다. 소스 버전 고정의 상세 기준은 CI/CD 기준을 봅니다.

    3. 개발 PC에서 실제 흐름 확인하기¶

    새 패키지가 있다면 먼저 하나만 실행하고 검사합니다.

    ./furive package run <패키지>
./furive package check

    그다음 전체 구성을 실행합니다. 역할이 아직 없는 소스 코드 작업 폴더의 첫 실행만 main을 적습니다.

    ./furive dev main

    이미 설치 역할이 있는 PC에서는 furive dev만 사용합니다. main 화면에서 패키지 구성과 Autoware 실행 화면을 열고 다음을 확인합니다.

    • 고정한 Autoware 소스 버전이 준비됐는가
    • 실행 화면이 완전한 차량/센서 모델 쌍을 찾는가
    • 모델, 지도와 실행 방식을 선택해 Autoware를 시작·중지할 수 있는가
    • 새 패키지의 실제 출력과 logs/<이름>.log가 정상인가

    작업 공간에 모델 쌍이 하나면 자동 선택하고, 여러 쌍이면 화면에서 하나를 선택합니다. 탐색 경로와 내부 선택 파일을 조사할 때만 Autoware 플랫폼 탐색을 봅니다. 이 참고 문서의 내부 platform 표현은 Furive 플랫폼이 아니라 Autoware 모델 이름 앞부분을 뜻합니다.

    4. 검사한 뒤 차량 한 대에서 시험하기¶

    ./furive check

    Autoware 소스 버전이나 빌드 입력을 바꿨고 해당 작업 공간을 빌드할 수 있는 PC라면 선택 진단을 추가합니다.

    ./furive check --platform <Furive-플랫폼>

    이 검사는 고정한 소스 코드가 빌드되는지만 확인하며 실제 CAN·센서·차량 동작을 증명하지 않습니다. 마지막으로 차량 업데이트의 test 흐름에서 한 차량의 기능과 이전 정상 버전 복구를 확인한 뒤에만 normal로 승격합니다.

    완료하려면 패키지 구성과 Autoware 소스 버전을 담당하는 곳이 분리되어 있고, 차량 차이가 Autoware 모델이나 독립 패키지 한 곳에 있어야 합니다. 개발 검사와 한 차량 test·복구까지 확인합니다.
