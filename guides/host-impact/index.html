    설치가 PC에 미치는 영향¶

    이 문서는 Furive OS를 설치하기 전에 PC 전체에 남는 변경과 차량·네트워크에 영향을 줄 수 있는 선택 기능을 확인할 때 사용합니다. 일반 설치 전에는 이 요약까지만 읽으면 됩니다.

    필요한 만큼만 읽기¶

    읽는 사람 여기까지만 보면 됨
    처음 설치하는 사람 설치 전 요약과 빠른 판단
    패키지를 추가하는 개발자 요약을 본 뒤 세부 목록에서 패키지 이름 검색
    설치·권한·네트워크 문제를 조사하는 담당자 세부 목록에서 영향 태그와 실제 확인 명령 확인

    기본 설치가 PC에 남기는 변경은 install.sh, 특정 패키지의 추가 영향은 그 패키지 저장소가 담당합니다. 실행 중 포트와 프로그램 시작·종료는 공통 실행 관리자가 맡습니다.

    기본 설치만으로 모든 차량 패키지가 설치·실행되는 것은 아닙니다. 다음 영향은 해당 옵션이나 패키지를 선택하고 실제로 실행할 때만 생길 수 있습니다.

    선택 기능 가능한 영향 확인할 때
    Docker 패키지 포트·이름 충돌, X11 접근 패키지 추가 전
    멀티캐스트 네트워크 경로와 NIC 설정 변경 --customize 사용 전
    Autoware·CAN 패키지 CAN 연결 장치 설정, 직접 켠 경우 실제 송신 정차·벤치 시험 전
    카메라 패키지 NIC down/up 또는 MTU 변경 실제 장치 연결 전
    데이터 로깅 접근 정보, 방화벽, 저장·외부 전송 고객 데이터 사용 전
    원격 접속 서비스, 로그인 화면과 sudo 권한 변경 기능 활성화 전
    차량 test용 Git 쓰기 키 실제 시험 차량의 main/edge에만 설치 고객 전달 전과 normal 전환 전

    설치 전 빠른 판단¶

    • 다른 프로그램이 같은 포트, Docker 이름 또는 ROS domain을 쓰는지 확인합니다.
    • Docker 그룹에 들어간 사용자는 높은 권한을 가질 수 있으므로 설치 계정을 제한합니다.
    • CAN 송신, NIC 변경과 원격 접속은 기본 기능으로 간주하지 말고 별도 시험·승인을 거칩니다.
    • 실제 위치·영상·고객 데이터를 쓰면 보안·개인정보 기준을 추가로 확인합니다.

    여기까지 확인했으면 일반 설치 전 검토는 끝입니다. 아래 내용은 충돌을 조사하거나 특정 패키지의 정확한 파일·명령·환경변수를 찾을 때만 펼칩니다.

    세부 영향과 점검 명령 펼치기 일반 설치 전에는 [설치 전 요약](#설치-전-요약)까지만 확인하면 됩니다. 이후 내용은 `--customize`, 차량 장치 또는 특정 패키지가 PC에 미치는 영향을 조사할 때 사용하는 상세 자료입니다. > [!IMPORTANT] 범위 > 이 문서는 Furive OS 내부 파일이 아니라, 같은 PC의 다른 소프트웨어에 영향을 줄 수 있는 **host-wide 영향**만 본다. > > 단순한 repo checkout, package config, `/data/furive-os` 내부 파일, package 로그는 여기서 제외한다. > [!SUMMARY] 운영 원칙 > Furive OS는 기본적으로 host 영향을 최소화한다. 꼭 필요한 설치/실행 영향은 명시적으로 남기고, 차량/센서/원격접속/package별 host 설정은 선택 옵션이나 해당 package 설치/실행 조건 안에 가둔다. > > - 기본 설치/실행 경로에 넣는 host 변경은 core 실행에 필요한 경우로 제한한다. > - 네트워크, CAN, 원격접속, X11, firewall 같은 영향은 기본값 off, prompt, config, 또는 package 조건으로 분리한다. > - package 실행 방식인 Docker `privileged`, host network, mount는 host 설정 변경처럼 과대표시하지 않는다. > - host를 바꾸는 항목은 조건, 실제 명령, 확인 방법을 같이 남겨 문제 원인 추적이 가능해야 한다. > [!NOTE] 가장 중요한 전제 > Furive OS 설치/기동과 package 설치/기동은 분리해서 본다. > > - `./furive setup`은 역할·플랫폼의 기본 package 목록을 그대로 사용한다. `--customize`를 붙인 경우에만 package 선택 화면을 열고, 최종 선택된 package의 `setup.sh`/`build.sh`를 실행한다. > - 실행 시에는 선택한 역할의 PackageManager가 설정된 package 목록을 시작한다. > - `package/plugin/*` 영향은 해당 package가 config에 들어가 있거나 대시보드/API에서 시작된 경우에만 해당한다. > - Furive OS를 설치하거나 켰다고 모든 plugin package가 자동 설치/실행되는 것은 아니다. 보안 통제의 현재 판정과 잔여 위험은 [보안 보증 기준](../reference/security-assurance.md)이 canonical source다. 이 문서는 그중 host에 생기는 영향과 확인 방법만 설명한다. > [!TIP] 읽는 법 > 이 문서에서 **순정 Furive OS**는 plugin/선택 package를 추가로 선택하지 않고 Furive OS 본체와 core 실행 흐름만 설치/실행한 상태를 뜻한다. > > `./furive setup --customize` 선택 옵션, 해당 package 설치/실행, Autoware launch, CAN bridge, RustDesk 같은 항목은 순정 영향에 포함하지 않고 **추가 영향**으로 따로 본다. ## 영향 수준 | 수준 | 의미 | 예시 | | --- | --- | --- | | L1 | 실행 중에만 생기는 충돌 가능성 | TCP/UDP 포트 사용, 같은 `ROS_DOMAIN_ID`의 ROS2 통신 섞임, X11 접근 허용 | | L2 | 종료 후에도 남는 host 설정 변경 | apt package/source/key, Docker daemon DNS, docker group, systemd, autostart | | L3 | 네트워크/제어/원격접속 영향 | CAN 설정/TX, NIC MTU/route/firewall, RustDesk/GDM | ## 영향 태그 태그는 package 실행 방식이 아니라 **host 설정 변경** 또는 **다른 SW에 직접 충돌을 줄 수 있는 동작**이 드러나도록 붙인다.     ## 순정 Furive OS 영향 > [!SUMMARY] 이 절에서 보는 것 > plugin/선택 package를 추가 설치/실행하지 않았을 때의 Furive OS 본체와 core 실행 흐름 영향만 본다. > > `./furive setup --customize` 선택 옵션, package 설치/실행, Autoware launch, CAN bridge, RustDesk 등은 아래 **추가 영향** 절에서 따로 본다. ### L2 · `./furive setup` 기본 dependency / Docker / 자동 실행 **태그** #apt-install #apt-remove #apt-source-add #docker-install #docker-daemon-dns #systemd-unit-write #systemd-enable-start #desktop-autostart-add #credential-file **항상 발생?** 설치할 때만 발생한다. 이미 설치된 dependency는 건너뛸 수 있지만, Docker daemon DNS 확인은 설치 과정에서 수행된다. **영향** - `python3`, `python3-yaml`, Node.js, Docker 설치 가능. credential bundle의 모든 bootstrap은 `htop`이 없을 때 APT로 설치하며 기존 실행 파일과 `~/.config/htop` 사용자 설정은 변경하지 않는다. - Docker 설치 시 apt key/source 추가와 `docker` group 변경 가능 - 설치는 host에 존재하는 `video`/`render` 그룹을 runtime user에 추가하고, main/edge service에는 `docker`와 존재하는 `video`/`render`를 supplementary group으로 부여한다. Unity HMI, Electron, RViz처럼 로그인 세션과 systemd 실행에서 같은 DRM render node를 쓰는 GUI가 이 권한 경계를 공유한다. [Docker 공식 문서](https://docs.docker.com/engine/install/linux-postinstall/)가 경고하듯 `docker` group은 root-level privilege다. 따라서 이 user로 실행되는 core, package lifecycle 또는 OTA code가 침해되면 host root와 동등한 영향이 가능하며 `NoNewPrivileges`나 `ProtectSystem`만으로 이 경계를 격리했다고 보면 안 된다. 잔여 위험은 **HIGH**이고 rootless Docker 또는 root-owned 최소권한 broker/역할별 service account로 분리하기 전까지 runtime user를 privileged account로 관리한다. 같은 runtime group이 0640의 `node.key`와 `dls-credential.key`도 읽으므로 동일 UID/native package 침해는 node 사칭과 DLS/Autonomy credential·pending data 복호화로 이어진다. - apt 복구 과정에서 `v4l2loopback-dkms` 문제가 감지되면 `v4l2loopback-dkms`, `v4l2loopback-utils`를 purge/autoremove할 수 있음 - `/etc/docker/daemon.json`에 DNS를 병합/생성함. 설치기는 `docker ps`로 실행 중인 컨테이너가 없음을 확인한 경우에만 Docker daemon을 즉시 재시작함 - 실행 중인 컨테이너가 있으면 Docker daemon을 자동 재시작하지 않는다. NVIDIA runtime 설정처럼 즉시 적용이 필요한 단계는 차량 정차와 컨테이너 종료 후 같은 `bootstrap.sh`를 다시 실행하도록 중단함 - 새 Docker의 group 권한은 설치기가 `docker` group의 새 하위 세션으로 자동 전환해 같은 `bootstrap.sh` 실행 안에서 설치를 이어간다. Furive 서비스와 운영 화면은 즉시 사용할 수 있다. 이미 열려 있던 데스크톱 세션에서 사용자가 직접 `docker` CLI를 실행하려면 로그아웃·로그인 후 새 터미널을 사용한다. 설치 완료 화면도 이 차이를 명시한다. 재부팅해도 같은 group 권한이 적용된다. Docker 소켓 권한을 완화하지 않는다. - bootstrap은 host 변경 전에 설치·유지·건너뜀 항목, 정확한 Autoware image와 NVIDIA package, 재부팅 여부를 표시하고 대화형 실행에서 `y/N`을 한 번만 받는다. 설치 중에도 현재 작업과 이유를 진행률 옆에 표시한다. 승인 뒤 대상이 달라지면 다른 대상을 적용하지 않고 중단한다. - Furive가 NVIDIA driver를 실제 설치하는 경우 host package, NVIDIA Toolkit, credential, Autoware 사용자 도구와 systemd 등록을 먼저 끝낸다. driver를 재부팅 직전의 마지막 큰 변경으로 적용하므로 새 display driver를 설치한 뒤 Toolkit이나 Docker 설정을 계속하지 않는다. 10초 카운트다운 뒤 자동 재부팅하며 `Ctrl+C`로 취소할 수 있다. 다음 부팅의 `furive-autoware-finalize.service`는 root가 아니라 지정된 Furive 사용자와 `docker`/`video`/`render` supplementary group으로 GPU container 검증, Autoware source·image·data·build를 끝낸다. 성공 marker만 systemd의 `ExecStartPost=+`가 root 소유로 기록하며 이 unit이 성공하기 전에는 Furive 서비스를 시작하지 않는다. 로그인하면 최대화 터미널이 이 단일 서비스의 진행률과 로그만 표시한다. 로그인, sudo 재인증, sudoers·비밀번호 저장, 자동 로그인 변경은 필요하지 않다. - Furive가 driver를 설치하지 않았더라도 `/var/run/reboot-required`처럼 별도 kernel 반영이 필요한 상태는 자동 재부팅 범위에 넣지 않고 원인 package와 수동 재부팅·재실행을 안내한다. - `scripts/fix-docker-dns.sh`가 Docker daemon DNS 보정을 한 번 소유하며 일반 설치 흐름도 이 helper를 호출함 - `/usr/local/bin/furive`를 현재 checkout의 `furive` 명령으로 연결 - `/usr/local/bin/fui`를 같은 명령으로 연결해 `furive dashboard`의 짧은 별칭으로 사용 - main의 Autoware 설치를 선택하면 VS Code가 없는 경우 Ubuntu signed Snap의 `code` classic package를 설치하고 로그인 사용자에게 `ms-vscode-remote.remote-containers` extension을 설치한다. 같은 사용자의 `~/.bashrc`에는 Furive가 소유하는 단일 marker block으로 `fd`, `fcd`, `fw` alias를 추가하며 기존 marker block만 원자적으로 교체한다. Furive가 VS Code 자체를 새로 설치한 경우에만 기존 GNOME `favorite-apps` 순서를 보존한 채 `code_code.desktop`을 뒤에 한 번 추가한다. 기존 VS Code가 있으면 dock 설정을 바꾸지 않는다. - Autoware host 환경은 차량 ID가 있으면 플랫폼 검증값, 없으면 실제 Ubuntu·CPU architecture·NVIDIA driver CUDA 호환 상한으로 선택한다. NVIDIA driver가 없거나 선택 image의 최소값보다 낮으면 `ubuntu-drivers devices`는 GPU 지원 package 후보 조회에만 사용하고, 플랫폼 CUDA의 `minimum_driver`를 만족하면서 `recommended_driver`에 가장 가까운 Ubuntu package를 설치기가 명시적으로 선택·설치한다. 후보가 CUDA 최소값을 만족하지 않으면 `autoinstall`로 우회하지 않고 중단한다. 이미 최소 조건을 만족하는 driver는 바꾸지 않는다. 기존 driver package가 있고 교체가 필요하면 교체 이유, 기존 package와 exact 설치 package를 출력한 뒤 시작 시 받은 단일 승인 범위에서 계속한다. exact image는 pin된 Dockerfile과 실제 tracked Compose 순서로 정한다. AMD/Intel 내장 그래픽이나 매핑표 밖의 조합은 fail-closed이며 driver를 임의로 바꾸거나 amd64 CUDA image를 강제하지 않는다. GPU 이름·PCI ID·driver·선택 CUDA를 출력하고 image 준비 뒤 `docker run --runtime=nvidia --gpus all` smoke test를 통과해야 data 복사와 build를 시작한다. CUDA 12.4 amd64는 공식 최소 550.54.14와 별도로 현장 확인 권장값 595를 표시한다. 값의 단일 원본과 1차 매핑·2차 자동 판정·3차 차단의 상세 기준은 [Autoware 호환 기준](../reference/autoware-compatibility.md)을 따른다. 설치 뒤 현재 매칭 결과는 `furive status`에서 확인한다. - 기본 경로에 `Autoware` 폴더나 symlink가 하나라도 있으면 bootstrap과 설치기는 전체 경로를 자동으로 보존한다. Git 저장소인지, 비어 있는지, Furive가 아는 디렉터리 구조인지와 무관하다. `--skip-autoware-setup`과 같은 경계로 처리하므로 remote 표기 정규화, branch/revision 전환, `vcs import`, 소유권·권한 변경, image/data·bundle 지도 준비와 build를 수행하지 않고 나머지 Furive 설치만 계속한다. Autoware 준비는 해당 경로가 전혀 없는 PC의 최초 provisioning에서만 수행한다. - `test` credential bundle의 bootstrap에서만 Chrome stable, `ibus-hangul`, 나눔 글꼴, `language-pack-ko`와 고정 Codex CLI를 추가한다. IBus 선택은 로그인 사용자의 `~/.xinputrc`에 반영되고, Codex는 `~/.local/share/furive-os/codex-cli/`과 `~/.local/bin/codex`를 사용한다. Chrome 공식 `.deb`가 Google APT source를 등록할 수 있다. Chrome과 Codex는 없는 PC에만 설치하고 이후 Furive bootstrap/OTA가 버전을 올리지 않는다. Codex 최초 설치는 source에 기록된 호환 확인 버전을 사용한다. 기존 Fcitx package/config, GNOME 입력 소스와 dock, 기존 사용자 Codex 실행 파일은 삭제하거나 덮어쓰지 않으며 `normal` bootstrap도 이 도구들을 제거하지 않는다. - `/usr/local/lib/furive-os/furive-os-launcher.sh`를 root 소유의 stable launcher로 설치하고, `/etc/furive-os/control.env`를 `root:<설치 사용자 그룹> 0640`으로 유지 - credential bundle 설치는 `/etc/furive-os/release-trust/root.pub`과 optional `revoked.krl`을 root 소유 read-only file로 고정한다. 설치된 root fingerprint가 다른 bootstrap 입력으로 자동 교체되는 것을 거부한다. - credential bundle 설치는 역할 전용 `node.crt`, `node.key`, `trust.pem`을 `/etc/furive-os/node-identity/`에 설치한다. Private key는 `root:<설치 사용자 그룹> 0640`, certificate와 peer pin은 root 소유 0644다. Symlink, 안전하지 않은 parent/owner/mode, 만료 임박, key 불일치, vehicle/role/node SAN 불일치는 설치를 중단한다. - Fresh bundle은 main/edge마다 서로 다른 `furive_node_<32 lowercase hex>` opaque CN을 128-bit CSPRNG로 생성한다. 기존 사람이 읽을 수 있는 CN bundle은 Zenoh이 거절하므로 이 변경 전에 쌍으로 재발급해야 한다. - Main↔edge 제어 TCP는 이 identity로 TLS 1.3 mTLS를 수행하며 peer leaf certificate를 직접 pin한다. `/etc/furive-os/control.env` HMAC은 loopback local control에만 쓰고 원격 plaintext/HMAC downgrade에는 쓰지 않는다. - Zenoh은 같은 identity를 검증·private staging한 뒤 QUIC/UDP `7447` TLS 1.3 mTLS와 exact peer-CN default-deny ACL을 사용한다. 다만 client가 WebPKI public root도 load하므로 직접 leaf/SPKI pin은 아니다. Custom-root-only/SPKI pin과 UDP source allowlist 방화벽은 남은 보안 작업이다. - Installer는 GitHub 공식 Ed25519 host key를 `/etc/furive-os/known_hosts`에 root-owned 0644로 고정한다. Bundle·installer·deploy runtime/recovery·Source Unlock은 `/usr/bin/ssh -F /dev/null`과 `StrictHostKeyChecking=yes`만 쓰고 checkout의 mutable local SSH override를 신뢰하지 않는다. 공식 rotation을 검토해 code·bundle·차량 pin을 함께 바꾸기 전에는 연결 실패를 우회하지 않는다. - Autoware private repository는 저장소별 read-only deploy key를 SSH 별칭으로 선택한다. `vcstool`의 기본 host 검사는 installer의 고정 SSH config를 읽지 않으므로 installer가 처음부터 한 worker로 import한다. 이 구간의 점(`.`) 표시는 직렬 clone 진행 상태이며 fingerprint 입력을 기다리는 상태가 아니다. 실제 SSH 검증은 위 `/etc/furive-os/known_hosts` pin을 그대로 사용한다. - 실제 차량의 `test` main/edge credential bundle은 공용 개발 Git 쓰기 key를 `/etc/furive-os/development-git/id_ed25519`에 설치한다. Furive가 준비한 Autoware 저장소의 빈 repo-local `core.sshCommand`를 이 key에 연결한다. 이미 다른 repo-local SSH 인증이 있으면 그 설정을 유지한다. `normal` bundle 또는 test bundle의 명시적 제외를 적용하면 Furive marker가 있는 repo-local 설정과 설치된 key pair를 제거하며, read-only deploy key와 Harbor pull credential은 유지한다. symlink나 예상 밖 파일이 있으면 자동 쓰기·삭제를 거부한다. 로그인 사용자에게 기존 GitHub SSH identity가 없으면 `~/.ssh/config`에 Furive marker `Host github.com` block을 자동 설치해 일반 clone·push에도 적용한다. 기존 identity가 있으면 질문 없이 보존하며, normal 전환에서 Furive marker block만 제거한다. - 현재 node certificate는 397일짜리 self-signed Ed25519 leaf다. 자동 rotation·revocation이 없으므로 만료 전 새 역할 bundle을 발급하고 상대 장비의 `trust.pem` pin도 함께 바꿔야 한다. Main/edge 중 한쪽만 교체하면 원격 연결은 의도대로 fail-closed 된다. - main은 `/etc/systemd/system/furive-os-master.service`를 enable/restart하고, 기본 설치에서 `~/.config/autostart/furive-os-electron.desktop`도 등록한다. 따라서 backend는 부팅 때 시작되고 운영 화면은 데스크톱 로그인 뒤 자동으로 열린다. `desktop_surface`가 지정된 플랫폼은 같은 자동 시작에서 해당 전용 화면을 열며, 예를 들어 lotte-ohmio는 `furive-launcher` 화면을 연다. 명시적으로 `--no-gui-autostart`를 사용한 예외에만 등록하지 않는다. - generated deploy에는 개발용 `node_modules`를 복제하지 않는다. main 설치와 repair는 Dashboard `package.json`에 고정된 정확한 Electron 버전을 `~/.local/share/furive-os/electron-runtime/`에 한 번 설치하고 `current` 링크로 공유한다. 정상 런타임은 다음 deploy release와 repair에서 재사용하므로 릴리즈마다 npm 전체 의존성을 다시 설치하지 않는다. main 제거 시 이 Furive 소유 런타임도 함께 제거한다. - edge는 `/etc/systemd/system/furive-os-agent.service`를 enable/start - service unit은 stable launcher를 `ExecStart`로 사용하고 `/etc/furive-os/control.env`를 `EnvironmentFile`로 연결한다. `NoNewPrivileges`, read-only system 영역과 kernel/control-group 보호를 기본 적용한다. 차량 package와 host 상태 수집기가 GPU·CAN·카메라 같은 플랫폼 장치를 사용하므로 전체 device allowlist를 닫는 `ProtectClock`은 적용하지 않는다. service는 일반 사용자로 실행되어 별도의 시계 변경 권한을 갖지 않는다. OTA status/control은 UID와 checkout으로, launcher socket은 UID로 구분한 기존 host `/tmp` runtime 경로를 사용하며 `furive status` 같은 사용자 명령도 같은 경로를 읽어야 하므로 service의 `PrivateTmp`는 끈다. Control socket은 소유 사용자만 접근할 수 있는 mode로 생성한다. Root-installed launcher는 production 정상 시작 때 signed annotated tag=HEAD, tracked index/worktree와 recursive initialized submodule clean 상태를 activation 전·runtime 직전에 다시 확인한다. 다만 checkout과 service가 같은 UID인 동안 ignored/untracked module과 verify→exec TOCTOU는 남으므로 end-to-end runtime integrity 경계가 아니다. Checkout만 갱신해도 기존 root-owned launcher는 자동 교체되지 않으므로, 신규 bootstrap 또는 아래 지원되는 `furive setup --repair` 완료 전에는 이 보강이 설치됐다고 보지 않는다. 구버전 OTA 전환 뒤 `furive setup --repair`는 차량 설정을 다시 고르지 않고 이 host 소유 파일과 연결만 현재 계약으로 복구한다. 복구 전에는 다음 OTA가 fail-closed 된다. 후보 health가 아직 확정되지 않았으면 repair도 fail-closed하며, 누락 unit은 비활성 상태로 다시 만든다. 기존 service가 실행 중이었다면 repair 마지막에 한 번 재시작해 새 launcher와 영구 token을 현재 updater 프로세스에도 적용한다. 이후 OTA는 active checkout의 launcher와 byte hash를 비교하지 않고 root 소유 launcher가 선언한 supervisor contract를 비교한다. 따라서 호환 contract 안의 launcher 개선은 매 release마다 repair를 요구하지 않는다. - 구버전 marker와 retained checkout의 소유권을 증명할 수 없는 `legacy_repair_required`는 host 파일 repair로 해결하지 않는다. 최신 credential bundle의 `bootstrap.sh --mode --target-dir <현재 설치 경로>`로 known-good checkout과 host 경계를 함께 복구한다. **확인**
