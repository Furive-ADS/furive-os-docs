    🚘 Furive OS 기본 사용법¶

    이 문서는 설치 ZIP의 ./bootstrap.sh를 마친 뒤 차량 PC를 사용하는 데 필요한 내용만 설명합니다. 정상일 때 Furive OS는 자동으로 동작하므로 터미널 명령은 문제가 있거나 정비할 때만 사용합니다.

    🚘 평소 동작¶

    • A-ECU와 HMI-ECU 서비스는 PC 부팅 때 자동으로 시작됩니다.
    • A-ECU의 기본 화면은 보통 데스크톱 로그인 뒤 자동으로 열립니다. 내부 개발 PC는 필요할 때 fui로 엽니다.
    • HMI-ECU는 화면 없이 동작합니다.
    • OTA Update는 지정된 버전을 확인하고, 검증되지 않은 업데이트는 적용하지 않습니다.

    A-ECU의 기본 화면은 차량 플랫폼에 따라 달라질 수 있습니다. Lotte Ohmio에서는 Autoware 실행과 맵을 다루는 Launcher가 먼저 열립니다. 이 화면을 닫았다면 다음 명령으로 다시 엽니다.

    fui

    fui는 furive dashboard의 짧은 이름입니다. 서비스가 정상 실행 중일 때 이 명령으로 화면을 다시 엽니다. 서비스를 다시 시작하려면 아래의 furive service restart를 사용합니다.

    ⌨️ 터미널에서 운용하기¶

    화면을 닫아도 Furive 서비스가 실행 중이면 CLI를 사용할 수 있습니다. 설치한 장비 배정은 자동으로 사용합니다. 먼저 현재 PC에서 가능한 기능과 전체 운용 상태를 확인합니다.

    furive help
furive status

    활용 팁

    CLI 명령어 표에서 패키지·OTA·Autoware·시스템·토픽 작업을 기능별로 찾으세요. furive help는 설치 상태에 맞는 안내이고, furive --help는 이 버전의 전체 문법입니다. 시작이 필요한 패키지나 서비스도 도움말에 표시됩니다.

    flowchart LR
  Help["⌨️ furive help<br/>사용 가능한 기능"] --> Status["🔎 furive status<br/>전체 문제 확인"]
  Status --> Package["📦 package status · logs<br/>문제 패키지 조사"]
  Package --> Action["🛠️ 필요한 작업 실행"]
  Action --> Verify["✅ 상태와 결과 재확인"]

    DLS에서 A-ECU 토픽이 보이지 않을 때¶

    DLS는 Furive OS 없이도 독립 실행할 수 있습니다. 연결된 ROS 환경의 토픽을 선택해 녹화하며, Furive OS로 다른 ECU의 토픽을 전달받는 경우에만 아래 중앙 통신 설정을 사용합니다.

    1. DLS의 “토픽이 목록에 없나요?”에서 Furive OS 통신 토픽 관리를 엽니다.
    2. 발행 중인 토픽을 찾아 통신에 추가합니다. 실행·녹화 중이면 중앙 설정에 저장하고 적용 대기로 표시합니다.
    3. 정비 상태에서 Autoware와 녹화를 중지한 뒤 설정 다시 적용을 누릅니다. 이미 중지되어 있으면 추가 시 적용합니다.
    4. 수신 PC에서 조회 가능을 확인하고 기록 화면으로 돌아갑니다. DLS 목록이 갱신되면 기록할 토픽으로 선택합니다.

    터미널에서도 같은 흐름을 사용합니다.

    furive topic list
furive topic add /sensor/example
# 적용 대기로 안내된 경우, 정비 상태에서 실행
furive autoware stop
furive topic stop
furive topic apply
# 발행 프로그램을 다시 실행한 뒤 수신 확인
furive topic list
furive topic record /sensor/example
furive topic stop

    record는 기존 DLS 기록 선택에 토픽을 추가한 뒤 선택된 토픽들을 함께 녹화합니다. 중앙 통신 허용 범위는 바꾸지 않습니다. 불필요한 전달 경로는 furive topic remove /sensor/example로 제외합니다. 새 메시지 타입 지원이 양쪽 PC에 없으면 해당 패키지 업데이트가 필요합니다. 토픽 조회·녹화 시작 상태와 실제 파일 저장 결과는 다르므로 녹화 결과는 DLS 세션에서 확인합니다.

    ⚙️ 설정 바꾸기¶

    설치된 차량에서는 파일을 직접 고치지 않습니다. 지원하는 화면이나 CLI에서 설정을 저장하고, 차량 구성이나 배포 버전은 검증된 배포 버전(release) 또는 설치 묶음으로 바꿉니다.

    PC 시작 동작¶

    설치가 끝난 PC에서는 역할을 다시 쓰지 않습니다. 다음 네 명령으로 부팅 시 서비스 시작과 로그인 시 화면 열기를 각각 켜거나 끕니다.

    # PC 부팅 시 Furive 서비스
furive setup --autostart on
furive setup --autostart off

# main PC 로그인 시 운영 화면
furive setup --dashboard-autostart on
furive setup --dashboard-autostart off

    서비스 자동 시작 변경은 다음 부팅부터 적용되며 현재 실행 중인 서비스는 유지됩니다. 지금 바로 멈추거나 시작하려면 furive service stop 또는 furive service start를 사용합니다. 화면 자동 열기를 꺼도 이미 열린 창은 닫히지 않고, 켜도 다음 로그인 전에는 자동으로 뜨지 않습니다. 지금 열 때는 fui를 사용합니다. edge에는 로그인 화면 설정이 없습니다.

    내부 개발 PC도 같은 명령으로 화면 자동 열기를 다시 켤 수 있습니다.

    화면에서 바꾸는 운용 설정¶

    먼저 fui를 열고 아래 화면을 사용합니다. 저장 버튼이 있는 값은 설치 경로나 배포 파일을 직접 고치지 않아도 유지되도록 담당 프로그램이 저장합니다.

    바꾸려는 것 화면 적용 시점과 주의
    main·edge의 ROS Domain ID 시스템 매니저 → 시스템 설정 저장 즉시 연결된 edge에 전달하고 관련 ROS 패키지와 컨테이너를 재시작하므로 차량을 정비 상태로 만든 뒤 변경
    원격접속 허용·차단, 접속 ID 확인 시스템 매니저 → 선택 노드 상태 허용·차단은 즉시 적용되며 차단하면 진행 중인 원격 세션도 종료
    Autoware 실행 모드, 지도, 차량·센서 모델 런처 Autoware를 멈춘 뒤 선택하고 다시 시작; 선택값은 다음 실행에도 사용
    Furive 업데이트 잠금, 지금 확인·적용·이전 정상판 복구 OTA Update 잠금 중에는 새 업데이트와 수동 복구도 중지; 적용 전 복구 가능 상태를 화면이 확인
    Autoware 버전 업데이트 허용 OTA Update 다음 Furive 원격 업데이트부터 적용; 개발 작업은 먼저 커밋하거나 별도 백업
    수동·자동·상시 녹화, 파일 분할 시간과 최근 데이터 보관량 Data Logging System → 설정 저장 즉시 녹화 규칙에 반영될 수 있으므로 진행 중인 녹화 상태 확인
    녹화 시작 조건·ROS topic·추가 정보 Data Logging System → 설정 새 구독과 다음 기록에 반영; topic 이름을 실제 ROS 연결 상태와 대조
    NAS 주소·로그인·자동 전송·전송 후 삭제 Data Logging System → NAS 설정 연결 시험 뒤 저장; 자동 전송과 전송 후 삭제는 각각 별도로 켜며 실제 credential을 문서나 Git에 기록하지 않음

    화면에 값이 보이지 않거나 저장에 실패하면 먼저 furive status, 그다음 furive service logs와 해당 패키지 화면의 로그를 확인합니다. 파일을 먼저 고치면 화면 소유 상태와 서로 달라질 수 있습니다.

    차량 구성과 배포 설정¶

    바꾸려는 것 바꾸는 곳 반영 확인
    Autoware 실행 방식·지도·차량/센서 모델 main의 Autoware 실행 화면(Launcher) Autoware를 다시 시작한 뒤 화면 상태
    녹화·NAS 등 한 프로그램의 기능 해당 프로그램 화면 해당 화면과 프로그램 로그
    차량의 플랫폼·test/normal·버전 개발 저장소의 furive vehicle 배포 버전 적용 뒤 furive status
    main/edge에서 실행할 프로그램 조합 config/capability-profiles.yaml ./furive dev main, 이후 한 차량 test
    Autoware 소스 버전 config/external-workspaces.yaml ./furive check --platform <이름>, 이후 한 차량 test
    접근 정보·지도 같은 전달 파일 새 설치 묶음 ./bootstrap.sh 뒤 해당 기능 화면

    Autoware 실행 설정은 차량을 정비 상태로 만든 뒤 Autoware를 중지하고 바꿉니다. 화면에서 실행 방식, 지도와 차량/센서 모델을 저장한 다음 다시 시작하면 됩니다. 여기서 고르는 모델은 이번 Autoware 실행에 쓰는 모델이며, 차량에 설치할 전체 프로그램 조합인 Furive 플랫폼과는 다릅니다.

    차량의 플랫폼이나 배포 버전은 Furive OS source에서 현재값을 먼저 보고 필요한 값만 바꿉니다.

    ./furive vehicle show <vehicle-id>
./furive vehicle set <vehicle-id> --platform <platform>
./furive vehicle set <vehicle-id> --update test
./furive vehicle show <vehicle-id>

    이 명령은 배포할 설정만 바꾸며 차량에는 즉시 적용되지 않습니다. 실제 적용은 차량 업데이트의 test → 실차 확인 → normal 순서를 따릅니다.

    주요 패키지의 개발 설정¶

    아래 값은 일반 운용자가 설치 차량에서 직접 고치는 값이 아닙니다. 플랫폼·센서 통합 개발자가 개발 저장소에서 바꾸고 작은 실행 시험과 차량 test 업데이트로 전달합니다. config.yaml은 현재 통합값이고, 같은 폴더에 config.default.yaml이 있으면 지원하는 키와 기본 예시를 확인하는 기준입니다. 전체를 무조건 복사하지 말고 현재 장치에 필요한 값만 바꿉니다.

    패키지 주로 바꾸는 값 기준 위치 적용·확인
    hmi 창 자동 배치 config.default.yaml furive package run hmi 후 실제 display 확인
    lotte-ohmio-mgmt 창 자동 배치, 원격 모니터 초기 audio, 외부 명령 차단, CAN read-only config.yaml 차량 명령 송신 허용 여부를 분리해 확인
    data-logging-system 화면에서 제공하지 않는 진단·복구 기본값과 기본 topic 목록 config.default.yaml 먼저 화면 저장 경로 사용; 기본값 변경은 녹화·복구 시험 뒤 차량 test
    autonomy-studio-data-management 거리 조건, 목적, trigger·operation topic config.yaml DLS와 함께 pending record·재전송 확인
    flir-camera 카메라 serial·multicast 매핑; 지원하는 packet·pixel·노출·frame 키 config.default.yaml, 카메라별 예시 링크와 실제 image topic을 함께 확인
    rs80-lidar LiDAR 수, UDP port, 거리·각도, frame과 topic config.default.yaml port 충돌과 point cloud frame 확인
    ros2-sensor-dataset-recorder 저장 경로, LiDAR·camera topic, 동기화·timeout params.yaml 실제 두 센서 timestamp와 저장 파일 확인
    lotte-ohmio-can-ros2 CAN interface·bitrate, 자동 구성, USB reset, TX 허용 config.yaml 정비 상태에서 RX부터 확인하고 TX는 별도 승인·실차 시험
    ECU 간 ROS 전달 중앙 topic, 방향, type, QoS capability-profiles.yaml의 connections.ros2; 운용 중에는 furive topic 양쪽 전달 상태·제어·녹화 확인; bridge 지원 항목은 기본값 참고
    zenoh-bridge 일반 사용자가 직접 입력하지 않음 main/edge 설치 주소와 인증서가 자동 구성 주소를 package config에 중복 저장하지 말고 양쪽 연결 상태 확인

    설정 변경은 다음 순서로 확인합니다.

    furive package run <name>
furive package check
./furive check

    센서, CAN, ROS 전달 경로 또는 패키지 조합이 바뀌면 한 차량 test 업데이트에서 실행과 복구까지 확인합니다. 차량이 받는 설정이나 실행 결과물이 달라졌다면 새 배포 버전이 필요합니다. 접근 정보나 지도 전달물만 바뀐 경우에만 기존 배포 버전을 유지하고 설치 묶음을 다시 만듭니다.

    패키지별 전체 필드가 필요할 때는 각 저장소 README와 프로그램 연결 설정을 봅니다. 일반 운용 절차에 Docker 명령이나 package별 run.sh를 추가하지 않습니다.

    Furive PC의 소스 코드 개발 설정¶

    개발 PC 하나의 차이는 추적되지 않는 config/master.yaml 또는 config/agent.yaml에 바꿀 값만 적습니다. 예를 들어 main 개발 PC의 ROS domain, Dashboard 포트와 OTA 확인 주기만 바꾼다면 다음이면 충분합니다.

    ros_domain_id: 18
dashboard_port: 18083
self_update:
  check_interval: 600

    한 프로그램만 쓰는 설정은 그 저장소의 config/config.yaml에 바꿀 값만 적습니다. 팀 전체의 제품 기본값을 바꿀 때만 추적되는 *.default.yaml을 수정합니다. 목록 값은 일부 추가가 아니라 전체 교체되므로 필요한 항목을 모두 적어야 합니다.

    # Ctrl+C로 기존 개발 실행을 끝낸 뒤
./furive package run <name>  # 프로그램 하나 확인
./furive dev main            # 전체 흐름 확인

    설치 차량의 배포 폴더를 직접 고친 값은 다음 원격 업데이트나 재설치에서 사라집니다. 차량에 유지할 변경은 화면에서 저장하거나 검증된 배포 버전·설치 묶음으로 전달합니다.

    🔍 문제가 있을 때 확인 순서¶

    먼저 서비스, 설치 버전, OTA Update와 Autoware 실행 상태를 요약해서 봅니다.

    furive status

    status는 관리 중인 패키지·PC 연결·호스트 복구 요구를 집계합니다. 오래되거나 받지 못한 상태는 정상으로 표시하지 않고 확인 불가로 구분합니다. 특정 프로그램을 조사할 때는 다음 명령을 사용합니다.

    furive package status <name>
furive package logs <name> --lines 200

    패키지 내부의 상세 진단은 해당 기능 화면과 로그에서 확인합니다. A-ECU의 전체 Dashboard에서도 같은 운용 문제 목록을 볼 수 있습니다.

    furive dashboard --web

    Dashboard의 Package Manager에서 main/edge 패키지 상태와 패키지별 로그를 확인합니다. 정상 운용 중인 기본 화면이 Launcher인 차량에서도 이 명령은 전체 진단 화면을 브라우저로 엽니다.

    📄 로그 보기¶

    Furive 서비스의 최근 100줄을 본 뒤 새 로그를 계속 따라갑니다.

    furive service logs

    Ctrl+C는 로그 보기를 끝낼 뿐 서비스는 중지하지 않습니다. 최근 로그만 출력하고 바로 끝내려면 다음처럼 실행합니다.

    furive service logs --no-follow --lines 200

    개별 패키지는 furive package logs <name> --lines 200으로 최근 로그를 읽거나 전체 운영 화면에서 확인합니다. 패키지 로그 명령은 출력 후 끝나고, 서비스 로그 명령은 기본적으로 새 로그를 계속 따라갑니다. 개발 또는 차량 배포 폴더에서 파일을 조사할 때는 다음 경로를 봅니다.

    logs/<package>.log        실행 로그
logs/<package>.build.log  준비·빌드 로그

    파일 이름에서는 패키지 이름의 하이픈이 밑줄로 바뀝니다. 예를 들어 ota-updater의 실행 로그는 logs/ota_updater.log입니다.

    🛠️ 정비 중 서비스 제어¶

    차량을 안전한 정비 상태로 만든 뒤에만 전체 Furive 서비스를 중지하거나 재시작합니다.

    furive service stop
furive service start
furive service restart

    stop은 Furive 서비스와 그 패키지를 멈추며 PC 전원을 끄지는 않습니다. restart 뒤에는 furive status와 전체 Dashboard에서 필요한 동작을 다시 확인합니다.

    소스 코드 개발 실행은 systemd 서비스와 흐름이 다릅니다. ./furive dev main을 Ctrl+C로 끝낸 뒤 코드를 수정하고 같은 명령을 다시 실행합니다.

    🧩 주요 구성요소와 설정 위치¶

    차량 플랫폼에 따라 실행되는 패키지는 달라집니다. 아래 이름을 모두 외울 필요는 없고, 문제가 생긴 기능이 어느 항목인지 찾을 때만 사용합니다.

    이름 하는 일 바꾸거나 확인하는 곳
    운영 화면(Dashboard) 여러 기능의 상태와 로그를 한 화면에 모음 평소 설정 없음. 전체 화면은 furive dashboard --web; 개발 포트는 config/master.yaml의 dashboard_port
    프로그램 실행 관리자 (Package Manager) 프로그램을 순서대로 시작·중지하고 상태·재시작·로그 관리 프로그램 조합은 config/capability-profiles.yaml; 상태는 Dashboard의 Package Manager
    Autoware 실행 프로그램(Furive Launcher) 지도와 차량/센서 모델을 준비하고 Autoware 시작·중지 운용 선택은 실행 화면; 소스 버전은 config/external-workspaces.yaml
    ota-updater 새 버전을 검증·전환하고 실패하면 이전 정상 버전으로 복구 목표 버전은 furive vehicle; 개발 확인 주기는 config/master.yaml 또는 config/agent.yaml의 self_update.check_interval; 상태는 OTA 화면과 furive status
    system-manager main PC의 CPU·메모리·네트워크·GPU 수집 사용자 설정 없음; Dashboard의 시스템 상태와 logs/system_manager.log
    zenoh-bridge main↔edge ROS 데이터를 암호화해 전달 주소와 인증서는 설치가 정함; 통합 개발 설정은 해당 package의 config/; 확인은 양쪽 상태와 logs/zenoh_bridge.log
    ros2-domain-bridge Autoware와 전송 영역 사이에서 허용한 ROS 경로만 전달 중앙 플랫폼 설정에서 파생; 운용 변경은 furive topic; 확인은 양쪽 전달 상태
    integration-gateway 같은 PC의 프로그램 사이 요청·응답·이벤트 전달 사용자 설정 없음; 사용하는 프로그램이 의존성으로 연결

    Furive에서 실행하는 각 프로그램을 패키지라고 부릅니다. zenoh-bridge의 보안 연결과 ros2-domain-bridge의 전달 경로는 중앙 통신 설정에서 관리합니다. 경로를 바꾸면 수신 상태를 확인하고, 플랫폼 기본값을 바꾼 통합 개발자는 양방향 제어까지 시험해야 합니다.

    각 구성요소의 정확한 소유권, 통신 흐름, 설정과 로그 위치는 실행 구성요소에서 필요한 항목만 확인합니다.
