    변경 검증¶

    코드나 설정을 바꾼 뒤 어디까지 확인해야 완료인지 정할 때 사용합니다. 모든 변경에 실차 시험과 고객 배포 증적을 한꺼번에 요구하지 않고, 변경이 도달한 단계까지만 검증합니다.

    세 단계만 고르기¶

    단계 언제 필요한가 완료 조건
    일상 개발 모든 변경 가까운 작은 테스트와 furive check 통과
    한 차량 시험 설치·업데이트·장치·차량 데이터 흐름을 바꿈 한 차량 test의 실제 기능과 이전 정상 버전 복구 확인
    고객용 normal 고객 차량에 공용판을 배포함 시험 증거와 이번 변경에 해당하는 운영 항목 확인

    뒤 단계는 앞 단계를 대체하지 않습니다. 한 차량 시험이 필요한 변경도 먼저 일상 개발 검사를 통과해야 합니다.

    1. 일상 개발¶

    바꾼 코드와 가장 가까운 작은 테스트부터 실행합니다.

    python3 -m pytest -q tests/contracts/test_user_cli.py
./furive package check

    독립 패키지를 바꿨다면 그 저장소의 자체 테스트도 먼저 실행합니다. 실제 접근 정보, 개인정보나 고객 데이터를 테스트용 입력에 사용하지 않습니다.

    마지막에 개발 저장소의 최상위 폴더에서 공통 검사를 실행합니다.

    ./furive check

    이 검사는 코드, 설정, 문서 링크, 프로그램 연결 정보와 차량 배포 기본 규칙을 확인합니다. 최상위 테스트와 패키지 테스트는 동시에 실행되며, 패키지 내부의 임시 파일과 cache는 서로 섞이지 않습니다. 센서, CAN, GPU, NAS가 없는 개발 PC에서 해당 장치가 동작했다는 뜻은 아닙니다.

    구조가 복잡해지는 회귀도 같은 검사에서 확인합니다. tests/contracts/test_core_dependencies.py는 공통 Python 코드가 nodes, package, scripts 구현을 직접 import하거나 순환 의존을 만드는 변경을 예외 없이 거부합니다. 설치 복구 전 OTA 상태 판정도 후보 적용·확정·복구를 담당하는 core/release_activation.py가 소유합니다. 동적 로딩·shell 호출과 상태·정책의 중복 소유까지 증명하는 검사는 아니므로, 변경 검토에서는 기존 소유자와 사용자 개념이 늘었는지도 확인합니다. 새 예외를 추가해 검사를 통과시키기 전에 기존 소유자 안에서 해결합니다.

    속도는 CI/CD의 변경 범위 검사와 이미지 재사용, 업데이트 복구는 이전 정상 버전 계약을 따릅니다. 검사 시간 단축과 실제 차량의 준비·전환·복구 시간은 구분해서 기록하며, 재사용은 해당 검증·산출물의 identity가 맞을 때만 허용합니다. 변경량과 무관한 속도나 무장애를 보장하는 것으로 해석하지 않습니다.

    Autoware 소스 버전 또는 빌드 입력을 바꿨고 해당 작업 공간을 빌드할 수 있는 PC라면 선택 진단을 추가합니다.

    ./furive check --platform <플랫폼>

    일상 개발은 여기서 끝날 수 있습니다. 장치 시험이 아직 필요한 경우 결과를 실패로 숨기지 말고 “개발 PC에 장치 없음, 한 차량 시험 필요”라고 제한을 남깁니다.

    2. 한 차량 시험¶

    설치·OTA·복구, Autoware 실행, CAN·센서·GPU·화면·NAS, 녹화·외부 전송·차량 제어 또는 여러 패키지를 잇는 실제 데이터 흐름을 바꿨을 때 한 차량 test를 추가합니다.

    시험 순서는 고정합니다.

    현재 normal과 정상 결과 기록
  → test 적용
  → 정상 입력 확인
  → 대표 실패 입력 확인
  → 이전 normal 복구
  → 정상 결과 재확인

    PASS는 프로그램이나 컨테이너가 떠 있는지만 보지 않고 바꾼 기능의 실제 결과로 판단합니다. API 응답, ROS 메시지, 생성 파일, 화면 또는 장치 결과 중 관련된 것을 남깁니다. 적용 절차는 차량 업데이트를 따릅니다.

    차량이나 장치가 없어 실행하지 못했다면 일상 개발은 완료할 수 있지만 한 차량 시험을 PASS로 기록할 수는 없습니다.

    3. 고객용 normal¶

    한 차량 시험을 통과한 같은 소스 코드와 결과물만 normal로 승격합니다. 다음 중 이번 변경과 관련된 항목만 추가로 확인합니다.

    • 목표 차량과 플랫폼, 서명된 배포 버전과 Docker 이미지·소스 버전 일치 여부
    • normal 적용 뒤 프로그램 정상 상태와 실제 기능 결과
    • 이전 정상 버전 복구 가능 여부
    • 접근 정보·권한을 바꿨다면 전달, 저장, 회수·교체 담당자
    • 위치·영상·고객 데이터 또는 외부 전송을 바꿨다면 목적, 수신자, 보유·삭제와 승인
    • 차량 제어를 바꿨다면 안전한 시험 조건, 실패 상태와 수동 복구

    문서·테스트처럼 차량 실행 결과물을 바꾸지 않은 변경에 normal 배포 버전을 만들지 않습니다. 개인정보, 권한이나 외부 전송을 바꾸지 않았다면 전체 보안·법적 검토를 반복하지 않습니다. 필요한 경우만 보안·개인정보 기준을 봅니다.

    배포 버전과 설치 묶음 판단 및 승격 절차는 차량 업데이트와 CI/CD 기준을 따릅니다.

    결과 기록¶

    판정 뜻
    PASS 현재 단계의 검사를 실행하고 기대한 실제 결과를 확인함
    FAIL 필요한 검사가 실패했거나, 필수인데 실행하지 못함
    N/A 이번 변경에는 적용되지 않으며 그 이유를 기록함

    PR, 차량 시험 기록 또는 배포 기록 한 곳에 다음만 남깁니다.

    변경:
단계: 일상 개발 | 한 차량 시험 | 고객용 normal
대상: Git commit / 패키지 / 플랫폼 / 차량 버전
실행한 명령:
확인한 실제 결과:
판정: PASS | FAIL | N/A
남은 제한:

    미래 인증 계획이나 이번 변경과 무관한 운영 자동화를 완료 조건으로 만들지 않습니다. 실행하지 않은 검사는 PASS로 쓰지 않고, 해당하지 않는 항목은 이유와 함께 N/A로 남깁니다.
