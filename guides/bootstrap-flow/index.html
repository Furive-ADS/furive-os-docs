    bootstrap 설치 흐름¶

    차량 설치 묶음에서는 다음 명령 하나만 실행합니다.

    ./bootstrap.sh

    시작할 때 Furive OS 로고를 한 번 표시합니다. 넓은 터미널에서는 큰 블록 로고를, 좁은 터미널에서는 작은 마크를 표시하고 기본 설정 확인 → 설치 계획 확인 순서로 진행합니다. 처음 설치하는 자율주행 PC는 Furive OS + Autoware와 A-ECU가 선택된 상태에서 Enter를 누르면 됩니다. 설치 항목과 역할을 각각 선택할 필요가 없습니다. q로 취소할 수 있습니다.

    Furive OS만 또는 Autoware만 필요하면 설치 항목 변경, 별도 HMI-ECU에 설치한다면 설치할 PC 변경을 엽니다. 변경 화면에서는 방향키나 숫자로 선택하고 Enter로 확정한 뒤, 설정 요약에서 계속합니다.

    설정 요약의 기본 설치 방식은 새 PC에서 Recommended installation이며 현재 기본 동작을 유지합니다. 이미 Furive OS가 설치된 PC는 이전 설치가 남긴 상태를 그대로 두도록 Minimal installation이 기본으로 제시되고, 명시적으로 고르면 그 선택을 따릅니다. 설치 방식 변경에서 Minimal installation을 고르면 Chrome·VS Code·Codex·htop·한글 입력 같은 부가 개발 도구만 생략하고 Node/Electron, OS/runtime 의존성, source build 전제와 필요한 인증 key는 그대로 준비합니다. 이미 설치된 사용자 도구는 제거하지 않습니다.

    설치할 항목 범위 선택을 건너뛰는 옵션 Autoware 처리
    Furive OS + Autoware 기본값; 자동화는 PC 대상을 함께 지정 A-ECU에서 준비, HMI-ECU에서는 생략
    Furive OS만 --furive-only 기존 작업공간·이미지·NVIDIA 환경 유지
    Autoware만 --autoware-only Furive OS·PC 배정 없이 준비

    --skip-autoware-setup은 --furive-only와 같은 기존 호환 옵션입니다. 비대화형 실행은 기존 기본 설치 범위를 유지하며 신규 PC에는 기존처럼 --mode main 또는 --mode edge가 필요합니다.

    기존 설치가 있으면 기존 배정 유지를 표시하고 그 PC에 재설치합니다. 차량·플랫폼·버전은 묻지 않고, 선택한 PC의 구성이 서명된 배포 버전과 맞는지 확인한 뒤 적용합니다.

    설치 계획은 이 PC 역할에 실제로 적용되는 항목만 보여줍니다. HMI-ECU(edge) 계획에는 Autoware·NVIDIA driver 행이 나오지 않고, 이 PC에 적용할 plugin package에 서명된 배포판이 그 역할에 배정한 패키지 목록이 표시됩니다.

    1PC에서는 A-ECU 설치 하나에 자율주행·운영·필요한 HMI·로깅 패키지를 함께 배정합니다. 현재 기본 묶음의 A-ECU에는 HMI·로깅 패키지가 없으므로, A-ECU 설치 후 bootstrap을 다시 실행해도 HMI-ECU 기능이 추가되지 않습니다. 차량용 1PC는 해당 기능을 A-ECU에 배정한 배포판으로 묶음을 만들어 설치합니다. 개발 PC에서 개별 기능을 추가하는 기존 경로와 검증 범위는 1PC 구성 방법을 참고합니다.

    이 흐름은 새 PC 설치 계약을 포함한 배포 버전부터 사용할 수 있습니다. 이전 역할별 묶음은 선택 없이 고정된 PC에 설치합니다. 배정과 연산 분리의 기준은 ECU 설치 설계를 따릅니다. 설치 방식 selector를 지원하지 않는 이전 signed policy는 기존 2-line 응답과 기본 Recommended 설치를 호환합니다. Minimal에는 그 selector를 포함한 새 signed release bundle이 필요하며, 이전 policy가 새 --installation-profile을 받는다고 가정하지 않고 capability를 확인한 뒤 기존 Recommended 경로만 legacy 계약으로 처리합니다.

    이미 설치된 PC도 같은 채널의 상위 버전 묶음으로 업데이트할 수 있습니다. 새 묶음의 ./bootstrap.sh가 현재 서비스를 계속 실행한 채 서명된 checkout·Source Unlock checkout·의존성· image·package build를 독립적으로 준비합니다. 준비가 끝난 뒤에만 차량을 안전하게 주차하고 자율주행·차량 제어를 해제했는지 확인하는 짧은 취소 가능 안내를 거쳐 기존 서비스를 잠시 중지하고 atomic activation·재시작·health 확인을 진행하므로, 업데이트 전에 furive service stop을 실행할 필요가 없습니다. 차량 상태를 자동으로 감지하거나 주행 중 업데이트를 보장하는 흐름은 아닙니다. 준비 단계에서 취소·실패하면 현재 PID·checkout·runtime을 유지하고, activation·시작· health가 실패하면 이전 정상 버전으로 복구한 뒤 오류를 보고합니다. 성공 표시는 요청한 target commit과 version이 실제 active 상태로 확인된 뒤에만 출력합니다.

    기존 furive-os-deploy 폴더를 삭제할 필요가 없습니다. 설치 위치와 보존 대상 설정을 이어받고, 이미 준비된 호스트 도구와 정확히 같은 immutable Autoware image를 재사용합니다. htop·Chrome·한글 입력처럼 선택적인 workstation 도구가 없는 것은 현재 서비스를 중단하지 않고 기존 상태를 그대로 유지합니다. 반대로 새 image seed load·registry pull·필수 runtime prerequisite·NVIDIA driver 교체처럼 live 준비 계약 밖의 변경은 준비 시작 전에 거부하고, 필요한 기존 host repair 명령을 안내합니다. 계획에 표시된 host delivery를 적용하지 않은 채 성공으로 표시하지 않습니다. NVIDIA driver 교체, Docker host 변경, 재부팅이 필요한 driver-repair 같은 disruptive 단계는 이 live update 계약에 포함되지 않으며, 화면에 표시된 재부팅 후 계속 절차를 따라야 합니다. 버전 전환 후 설치가 실패하면 기존 전환 복구 절차로 이전 버전을 복원합니다. 이전 OTA 기록이 없는 설치도 현재 버전과 경로를 확인한 뒤 업데이트를 준비합니다. 휴지통 안의 설치 경로는 준비 단계에서 거부합니다. --target-dir로 휴지통 밖의 위치를 지정할 수 있으며, 휴지통에 남은 파일은 자동으로 이동하거나 삭제하지 않습니다.

    첫 signed fetch가 인터넷 단절로 중단되어 furive-os-deploy에 .git만 남은 경우에는 같은 묶음의 ./bootstrap.sh를 다시 실행합니다. bootstrap이 만든 origin과 unborn Git 상태를 확인한 뒤 기존 로그·설정·credential을 보존하고 fetch를 재시도합니다. 이미 설치 표식이 있는데 HEAD를 읽을 수 없거나 다른 Git 저장소·임의 파일이 남은 경로는 자동으로 덮어쓰지 않고 중단합니다. Git checkout의 추적 파일을 사용자가 수정한 경우 일반 업데이트는 [y/N] 확인 뒤 승인할 때만 추적 변경을 stash에 보존하고 진행합니다. untracked/ignored 설정·로그·credential은 건드리지 않으며, 승인된 Source Unlock 변경은 기존 정책에 따라 유지합니다.

    업데이트 채널이 다르거나 같거나 낮은 버전인 묶음은 업데이트에 사용하지 않습니다. 동일 버전의 설치 복구에는 furive setup --repair를 사용합니다. 중간 호환 버전이 필요한 경우에는 해당 버전을 먼저 설치하고 서비스 시작 뒤 일반 OTA가 묶음의 목표 버전까지 이어갑니다.

    Autoware만 설치하기¶

    Furive OS 없이 Autoware 작업공간을 준비하려면 이 옵션을 지원하는 새 배포판의 설치 묶음에서 실행합니다.

    ./bootstrap.sh --autoware-only

    PC 선택 없이 서명된 배포판의 Autoware 소스 버전·이미지를 사용합니다. Docker, NVIDIA 실행 환경, DDS 설정, Node/Electron·vcstool과 Autoware 소스·데이터·빌드를 준비합니다. Recommended installation에서는 VS Code·Dev Containers도 준비하고, Minimal installation에서는 이를 생략합니다. Furive OS 서비스·대시보드·OTA·PC 배정은 설치하지 않으며 기존 Furive 설치도 전환하지 않습니다. 설치 코드를 읽는 임시 배포 checkout은 종료할 때 정리합니다.

    기본 작업공간은 ~/Documents/Autoware입니다. 기존 폴더나 symlink가 있으면 내용을 보존하고 설치 없이 종료합니다. 설치기가 동봉 지도를 준비한 뒤 재부팅으로 중단된 작업공간은 이어서 처리합니다. 재부팅이 필요하면 미완료 상태로 종료하므로 PC를 재부팅한 뒤 같은 --autoware-only 옵션으로 다시 실행합니다. 단독 설치는 자동 재부팅이나 Furive의 부팅 후 자동 완료 서비스를 등록하지 않습니다. 성공 시 Autoware 단독 설치 완료와 작업공간 경로가 표시됩니다.

    일반 PC는 Ubuntu 22.04·amd64를 사용합니다. Jetson Thor는 Ubuntu 24.04·JetPack/BSP가 준비된 장비에서 development 묶음과 --autoware-only를 사용하면 Thor 소스·CUDA 13 ARM64 이미지를 자동 선택하고 BSP 드라이버를 유지합니다. Thor의 Furive OS 전체 설치는 아직 검증 전입니다. 자세한 범위는 Autoware 호환 기준을 따릅니다.

    flowchart TD

  PC --> Change["필요할 때만 설치 항목·PC 변경"]
  Change --> PC
  PC --> Plan["설치·유지·건너뜀과 정확한 image·driver 등 주요 영향 표시"]
  Plan --> Agree{"한 번 승인"}
  Agree -->|아니요| Stop["변경 없이 종료"]
  Agree -->|예| Host["필수 도구 · Toolkit · DDS · Furive 준비"]
  Host --> GPU{"Furive가 NVIDIA driver를 설치했나?"}
  GPU -->|아니요| Service["Furive 서비스 시작"]

  Final --> Service
  Service --> Done["설치 완료"]

    단계별로 하는 일¶

    단계 하는 일 멈추는 경우
    사전 확인 Ubuntu와 CPU 아키텍처, 묶음 내용, 차량·역할을 읽기 전용으로 확인 다른 PC용 묶음, 손상된 파일
    기본 설정 확인 설치 항목·PC를 한 화면에서 확인. 신규 A-ECU 기본, 기존 배정 유지. 필요할 때만 변경 메뉴 사용 입력 중단, 설치 기록 충돌, 기존 PC와 다른 대상
    계획과 승인 설치·유지·건너뜀 항목, 정확한 Autoware image와 NVIDIA package, 재부팅 여부를 표시하고 y/N을 한 번 받음 대상을 확정할 수 없음, 사용자가 승인하지 않음
    PC 준비 필요한 검증 도구를 설치하고 서명·업데이트 경로를 확인한 뒤 Docker, 역할 설정, 자동 실행과 Furive 서비스를 준비 검증되지 않은 버전, 프로그램 설치 실패, 실행 중인 Docker 프로그램 때문에 안전한 Docker 재시작이 불가능함
    Autoware 호환 확인 플랫폼 또는 GPU 규칙으로 CUDA·driver·Docker 실행 이미지를 고르고, 새 PC만 제한된 자동 판정을 사용 호환표 밖의 GPU/OS, 가능한 driver 없음, 검증값 충돌
    적용 기존 설치는 보존 가능한 설정을 이어받고, 새 설치는 정해진 배포 위치에 준비 사용자가 수정한 배포 파일을 안전하게 보존할 수 없음
    시작 driver 변경이 없으면 서비스를 바로 시작. driver를 설치했으면 다음 부팅의 최종 작업이 성공한 뒤 시작 GPU나 Autoware container 최종 검증 실패

    설치가 중간에 실패하면 첫 오류를 해결한 뒤 같은 ./bootstrap.sh를 다시 실행합니다. 완료된 안전한 단계는 재사용하며, setup.sh, install.sh, run.sh를 대신 실행하지 않습니다.

    새로 설치하는 Autoware 저장소의 origin은 원래 GitHub 주소로 저장합니다. 저장소별 번들 키를 고르는 SSH 별칭은 설치·동기화 명령의 전송 환경에서만 적용합니다. 이 주소·인증 구분은 core/autoware/repositories.py가 소유하며 사용자 Git의 전역 설정을 바꾸지 않습니다. 이전 설치의 SSH 별칭과 GitHub 주소가 섞여 있어도 같은 저장소이면 소스 동기화가 가능합니다. 기존 작업공간을 보존하는 A-ECU 재설치에서도 번들 키와 SSH 연결 설정은 준비합니다. 개발용 쓰기 키를 제거한 뒤에는 읽기 전용 키 설정을 복원하며 작업공간 내용은 변경하지 않습니다. 실제로 다른 저장소를 가리키면 기존 작업공간을 덮지 않고 중단합니다.

    운영 화면에서 소스 동기화가 성공하면 진행 로그 창은 자동으로 닫힙니다. 실패하면 오류를 확인할 수 있도록 열어둡니다. Furive Launcher의 일반 로그에서 실행·빌드·소스 동기화의 최근 기록을 함께 확인할 수 있으며, 동기화 창을 닫아도 기록은 유지됩니다.

    설치 중에는 진행률 옆에 현재 작업과 이유가 계속 바뀝니다. 이미 준비된 프로그램은 유지, 새로 받는 프로그램은 설치, 사용하지 않는 기능은 건너뜀으로 표시합니다. Autoware image는 정확한 이름과 함께 번들에서 불러오기, 로컬 검증본 재사용, 레지스트리에서 받기 중 실제 동작을 보여줍니다. 승인 뒤 image나 NVIDIA package 후보가 달라지면 다른 대상을 설치하지 않고 중단합니다.

    패키지 이미지는 이미지 2/5처럼 현재 순서와 완료 후 남은 개수를 표시합니다. 전체 설치 진행률과 별도로 다운로드, 압축 해제, 불러오기의 처리량·속도·예상 시간을 보여줍니다. 예상 시간은 현재 확인된 레이어의 남은 용량 합계와 합산 처리속도로 계산하므로 새 레이어가 발견되면 바뀔 수 있습니다. 발견된 레이어 중 용량을 모르는 것이 있으면 남은 시간 계산 중으로 표시합니다. 새 레이어가 처음 보고한 용량은 속도 측정에서 제외합니다. 다운로드가 100%여도 압축 해제와 저장이 남을 수 있으며, Docker가 성공적으로 끝나야 다음 이미지로 넘어갑니다. 10초 이상 출력 변화가 없으면 마지막 변경 이후의 대기 시간과 남은 시간 계산 불가를 표시합니다. 대기 표시만으로 실패를 뜻하지는 않습니다.

    묶음이나 이전 설치 시도로 정확히 같은 digest의 패키지 이미지가 이미 준비되어 있으면 레지스트리 인증·다운로드 없이 재사용합니다. 최초 설치에 필요한 이미지가 없으면 다운로드는 필요합니다. 설치 후 일반 시작은 준비된 로컬 버전을 먼저 실행합니다. OTA 다운로드와 사전 빌드는 별도 공간에서 진행하며, 준비가 끝난 업데이트만 다음 재시작에 적용합니다.

    NVIDIA driver가 필요한 main PC¶

    RmInitAdapter failed 같은 kernel 오류가 있으면 GPU 조회를 생략하고 호환 드라이버 복구를 설치 계획에 제안합니다. 계획에 표시된 패키지·버전을 확인하고 승인하면 설치합니다. 인터널 개발 PC처럼 GPU 정보를 읽어야 Autoware 이미지를 선택할 수 있는 경우에는 드라이버만 먼저 설치합니다. 안내에 따라 PC를 재부팅한 뒤 같은 ./bootstrap.sh를 다시 실행하면 GPU를 확인하고 나머지 설치 계획을 표시합니다. 재부팅 후 검증이 끝나기 전에는 복구 완료가 아닙니다. --autoware-only로 시작했다면 재실행에도 같은 옵션을 사용합니다.

    설치기는 ubuntu-drivers autoinstall을 사용하지 않습니다.

    • 1차로 별도 호환표에서 OS, CPU 아키텍처, GPU Compute Capability, Autoware CUDA와 driver 하한을 정확히 맞춥니다.
    • 아직 driver가 없어 GPU 상세값을 읽을 수 없을 때만, 호환표와 실제 GPU 지원 설치 파일 후보의 공통 범위에서 정확한 이름과 버전을 자동 선택합니다.
    • 표에 없거나 재부팅 뒤 GPU가 연결된 Docker 실행 시험을 통과하지 못하면 Autoware 설치를 중단합니다.

    이미 기준을 만족하는 driver는 바꾸지 않습니다. 교체가 필요하면 이유, 기존 driver와 설치할 driver를 보여주며 시작할 때 받은 한 번의 승인 범위에서 계속합니다. 상세 규칙과 표를 바꾸는 방법은 Autoware 호환 기준을 따릅니다.

    Furive가 driver를 설치하면 NVIDIA Toolkit·DDS·credential·서비스 등록을 먼저 끝냅니다. 화면을 구동하는 driver를 바꾼 뒤 Toolkit이나 Docker 설정을 계속하지 않도록 driver 설치를 마지막 큰 작업으로 실행하고 10초 뒤 재부팅합니다. 카운트다운 중 Ctrl+C를 누르면 재부팅만 취소할 수 있습니다. 다음 부팅에서는 로그인 전에 지정된 Furive 사용자로 GPU 확인, furive_autoware_main clone, 하위 source vcs import, 선택한 base image를 이용한 Furive Autoware container build와 colcon build를 마칩니다. 로그인하면 같은 진행률 형식의 최대화 터미널이 현재 단계를 보여줍니다. 비밀번호를 저장하거나 자동 로그인을 켜지 않고, 추가 sudo 입력도 받지 않습니다. 이 작업이 실패하면 Furive 서비스가 먼저 시작되지 않습니다.

    Secure Boot를 사용하는 PC는 운영체제가 재부팅 중 NVIDIA kernel module의 MOK 등록을 요구할 수 있습니다. 이 화면은 PC 자체의 보안 절차라 설치기가 대신 입력할 수 없습니다.

    설치 뒤 확인¶

    정상 설치는 별도 실행 명령이 필요 없습니다. 문제가 있을 때만 확인합니다.

    furive status
furive service logs

    furive status는 Furive 서비스·업데이트 상태와 함께 main PC의 Autoware CUDA 매핑, driver 기준과 현재 충족 여부를 보여줍니다. GPU driver가 없어도 GPU를 쓰지 않는 Furive OS 기능과 Docker 외의 일반 기능은 사용할 수 있습니다. 새 docker 그룹 권한은 새 로그인 세션이나 재부팅 뒤 사용자의 docker ps 같은 명령에도 적용됩니다.

    PC에 설치되는 package, 그룹, 파일과 서비스의 전체 목록이 필요할 때만 호스트 영향을 확인합니다.
