    🛠️ Furive OS 개발 시작¶

    이 문서는 처음 이 저장소를 수정하는 개발자를 위한 순서입니다. 목표는 바꿀 코드 한 곳을 찾고, 작은 변경을 테스트한 뒤 다시 실행하는 것입니다. 평소 소스 개발에는 영구 설치가 필요하지 않습니다. 차량 설치 ZIP을 받았다면 차량 PC 설치로 시작합니다.

    활용 팁

    첫 실행 → 코드 한 곳 수정 → 작은 검사 → 전체 검사. 설치한 차량의 운용 명령은 CLI 명령어 표에서 찾습니다.

    1. 준비하고 저장소 받기¶

    Linux 개발 PC에 Git, Python 3.10 이상과 코드 검색용 ripgrep(rg)이 필요합니다. 아래 SSH 주소와 연결된 패키지 저장소를 읽을 GitHub 권한도 필요합니다. 전체 화면·패키지 실행에 필요한 도구는 각 패키지의 README를 따릅니다. Docker·GPU·차량 장치가 필요한 패키지는 해당 환경에서 실행합니다.

    git clone --recurse-submodules git@github.com:Furive-ADS/furive-os.git
cd furive-os

    --recurse-submodules는 package/ 아래 연결된 별도 저장소까지 받습니다. 이미 받은 저장소에서 패키지 폴더가 비어 있을 때만 git submodule update --init --recursive를 실행합니다.

    Python 검사 환경이 없는 새 PC에서는 한 번 준비합니다. 아래 환경은 공통 Python 코드의 작은 테스트용이며, 각 패키지의 빌드·실행 의존성은 해당 패키지가 관리합니다.

    python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install PyYAML pytest

    새 터미널에서는 저장소 최상위 폴더에서 source .venv/bin/activate로 같은 환경을 사용합니다. venv를 만들 수 없다면 OS의 Python venv 패키지를 준비합니다.

    이후 ./furive 명령은 이 저장소의 최상위 폴더에서 실행합니다. 설치한 PC의 furive는 설치된 저장소를 가리키므로, 지금 수정 중인 source를 실행할 때는 ./furive를 씁니다.

    2. 한 번 실행해 기준 동작 확인하기¶

    아직 Furive를 설치하지 않은 개발 PC의 첫 실행입니다.

    ./furive dev main

    터미널에 개발 실행 안내가 나오고 main 운영 화면과 선택된 패키지가 시작됩니다. 화면과 로그에서 바꾸려는 기능의 현재 동작을 확인하고 Ctrl+C로 종료합니다.

    dev는 개발 중 원격 업데이트를 잠시 보호하고, 종료할 때 자신이 만든 임시 보호를 해제합니다. 기존 Furive 서비스가 실행 중이면 개발하는 동안 멈추고 종료 뒤 다시 시작합니다.

    edge 동작을 개발하는 미설치 PC에서만 ./furive dev edge를 사용합니다. 이미 설치된 PC에서는 ./furive dev가 그 PC의 역할을 읽습니다. 화면 없는 PC 등 예외 옵션은 ./furive dev --help에서 확인합니다. 하드웨어가 필요한 기능은 코드의 작은 테스트부터 진행할 수 있습니다.

    3. 바꿀 코드 한 곳 찾기¶

    처음에는 세 가지만 구분합니다. 패키지는 연결한 독립 프로그램, 플랫폼은 차량·센서 모델과 패키지 조합, main/edge는 프로그램을 실행하는 PC의 역할입니다. 관계가 궁금할 때만 한눈에 보기를 읽습니다.

    먼저 루트 폴더 지도에서 담당 폴더를 고릅니다. 공통 코드를 수정한다면 공통 소스 안내에서 기능별 시작 파일과 실행 순서를 확인합니다. 아래는 첫 변경에 가까운 테스트를 찾는 예시입니다.

    바꾸려는 것 처음 열 곳 가까운 테스트
    명령·도움말 core/cli.py test_user_cli.py
    패키지 실행·종료 core/package_manager.py test_package_manager_lifecycle.py
    차량·플랫폼 배정 core/fleet_assignment.py test_fleet_assignment.py
    프로그램 자체 기능 해당 package/ 저장소의 README 그 저장소의 테스트
    Autoware·Unity 소스 해당 프로그램의 별도 개발 저장소 그 저장소의 테스트

    다른 작업의 정확한 담당 파일은 개발 계약의 수정 위치를 기준으로 합니다. 담당 폴더 안에서 함수와 가까운 테스트를 검색합니다. 예를 들어 CLI의 개발 실행을 찾으려면:

    rg -n 'command_dev' core/cli.py tests/contracts/test_user_cli.py

    같은 상태나 실행 규칙을 새 helper·설정·화면 코드에 다시 만들지 않고 기존 담당 코드를 수정합니다. 상세 호출 관계가 필요할 때만 기술 구조를 엽니다.

    4. 수정하고 검사하기¶

    먼저 git status --short로 기존 변경을 확인합니다. 문제를 재현하는 작은 테스트를 찾거나 추가한 뒤 담당 코드를 수정하고 그 테스트를 실행합니다. 예를 들어 CLI를 바꿨다면:

    python3 -m pytest -q tests/contracts/test_user_cli.py

    패키지 기능을 바꿨다면 해당 저장소에서 자체 테스트를 먼저 실행합니다. 통과한 뒤 Furive OS 최상위 폴더에서 전체 검사를 실행하고 2단계의 개발 명령으로 바꾼 동작을 다시 확인합니다.

    ./furive check

    일상 개발의 완료 조건: 바꾼 동작과 대표 실패를 확인하고, 가까운 테스트와 전체 검사가 통과하며, 사용 방법이 달라졌다면 해당 가이드를 함께 고칩니다. 실제 장치 등 실행하지 못한 검증은 남겨 둡니다. 검사의 범위와 테스트 배치는 테스트 안내를 봅니다.

    package/를 수정했다면 그 저장소에서 테스트하고 commit·push합니다. Furive OS가 새 버전을 사용해야 할 때 최상위 저장소에 그 패키지의 commit 변경을 반영합니다.

    막혔을 때¶

    증상 다음 행동
    저장소 받기가 권한 오류로 실패 실패한 저장소 주소의 GitHub·SSH 접근 권한 확인
    패키지 폴더가 비어 있음 1단계의 submodule 초기화 실행
    Python 모듈을 찾지 못함 가상 환경 활성화 확인; 공통 검사 환경은 1단계, 패키지 의존성은 해당 README 확인
    패키지가 시작하지 않음 개발 터미널 안내와 패키지 로그 확인
    전체 검사 실패 출력에서 처음 실패한 검사·패키지를 찾고 테스트 안내에서 범위 확인

    변경을 차량에 전달할 때만¶

    문서·테스트만 바뀌었다면 코드 변경으로 끝냅니다. 차량의 실행·설치 내용이 바뀌었다면 차량 업데이트의 test → 실차 확인·복구 → normal 순서를 따릅니다. 접근 정보·지도 같은 설치 전달물만 바뀌었을 때의 판단도 그 문서에 있습니다.

    새 프로그램을 연결하려면 프로그램 연결, 새 차량·센서를 지원하려면 차량 플랫폼 만들기를 이어 읽습니다.
